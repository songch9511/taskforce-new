# 연동: 원문을 자동으로 가져오기

관련 문서: [플랫폼](PLATFORMS.md) · [바이브코딩 플랜](VIBE_CODING_PLAN.md) · [진실 판정](TRUTH_RULES.md)

사용자는 원문을 직접 넣지 않는다. Notion · Gmail · Slack에서 원문을 가져와 지금의 파이프라인(추출 → 검증 → Jev)에 넣는다.
`/lab`의 직접 입력은 엔진을 시험하는 용도다.

## 구조

### 입력은 두 가지 형태다

소스가 늘어도 파이프라인을 고치지 않으려고, 모든 연동은 아래 두 형태 중 하나만 만든다. 둘 다 Claim이 되어 같은 매칭 · 진실 판정을 거친다.

```
글 원문   (회의록 · 메일 · 메모 · 메시지)       ─▶ LLM Claim 추출 → 검증 → Jev ─┐
구조화된 할 일 (Notion 할 일 DB · 미리 알림 · 이슈) ─▶ 속성 → Claim (코드, 순수 함수) ─┼─▶ 매칭 → 진실 판정 → Action
                                                                                ┘
```

- **글 원문**: 누가 무엇을 약속했는지 글에서 읽어야 한다. 지금의 파이프라인이다.
- **구조화된 할 일**: 담당 · 기한 · 상태가 이미 필드로 있다. LLM으로 다시 읽지 않고 코드가 그대로 Claim으로 옮긴다 (비용 0, 원칙 5). 설계는 아래 [Notion 할 일 DB](#notion-할-일-db-설계).

### 가져오는 방법

| 방법 | 소스 | 비고 |
|---|---|---|
| 서버 OAuth (주기 동기화) | Notion, Slack, Gmail (구현). Calendar, Meet 전사 (1단계, 아직 없음) | 아래 구조. GitHub 등 2단계 연동은 아직 "원해요"만 받는다([다음 연동](#다음-연동)) |
| 기기 안 (Apple 앱이 전달) | 미리 알림(EventKit), Apple 메모 (아직 없음) | Apple 메모는 공개 API가 없다. 공유 시트와 단축어(App Intents)의 "Taskforce로 보내기"로 받을 계획이다 (둘 다 아직 없음) |
| 범용 입구 | 메일 전달 주소, 붙여넣기 | 연동이 없는 소스를 대신한다 |

### 서버 연동

```
외부 서비스 ─(OAuth 연결 · 주기 동기화)─▶ 연동 모듈 ─▶ IngestItem ─▶ ingest.ts ─▶ sources ─▶ 파이프라인
             src/lib/connectors/<서비스>/          (공통 형태)   (중복 · 안정화 · 상한)
```

- **연동 모듈은 외부 항목을 `IngestItem`(원문 · 관련자 · 원본 링크 · 외부 id · 버전)으로 바꾸기만 한다.** 파이프라인은 건드리지 않는다.
- **토큰**은 `connection_secrets`에 AES-256-GCM으로 암호화해 둔다(`CONNECTOR_TOKEN_KEY`). 이 테이블은 RLS 정책이 없어 앱 · 웹 클라이언트는 읽을 수 없고, 서버의 service role만 읽는다.
- **연결 목록**(`connections`)은 사용자가 보고 끊을 수 있다. 만들기 · 동기화 기록은 서버가 한다.
- **주기 동기화**: `GET /api/cron/sync`(`Authorization: Bearer $CRON_SECRET`). `vercel.json`에 15분마다로 걸려 있다.
  Vercel Hobby 요금제는 cron이 하루 1회로 제한되므로, 15분 주기는 Pro 요금제나 Supabase `pg_cron` + `pg_net`으로 이 주소를 부른다.
- **수동 동기화**: `POST /api/v1/connections/sync` (로그인한 사용자의 연결만, 연결마다 1분에 한 번). 연결 끊기: `DELETE /api/v1/connections/:id`.
- **동시 실행 방지**: 동기화 전에 연결을 잡는다(`sync_started_at`, 10분 뒤 자동으로 풀림). cron과 수동 동기화가 같은 연결을 겹쳐 돌리지 않고, 실행 시간 한도에 가까워지면 남은 항목은 다음 차례로 미룬다.
- **한도**: 연동 원문도 직접 입력과 같은 한도(본문 20만 자, 제목 200자, 관련자 200명)를 따른다. 사용자에게는 짧은 오류만 보이고 자세한 내용은 서버 로그에만 남는다.
- **토큰 폐기**: 연결 끊기(`DELETE /api/v1/connections/:id`) · 계정 삭제 모두 서비스 쪽 토큰도 폐기한다 (Notion · Slack, `src/lib/connectors/registry.ts`의 `tokenRevokerFor` · `revokeConnectorTokens`). 폐기가 실패해도 끊기 · 삭제는 계속하고, 우리 쪽 토큰은 연결과 함께 지운다.

### 넣는 규칙 (`src/lib/connectors/ingest.ts`)

| 규칙 | 이유 |
|---|---|
| 마지막 수정 후 30분이 지난 항목만 | 회의록은 회의가 끝난 뒤 AI 요약이 채워진다. 쓰는 중인 페이지를 넣지 않는다 |
| 한 항목은 한 번만 (글 원문) | 고쳐진 페이지를 다시 넣으면 같은 약속이 두 번 생긴다. 구조화된 할 일은 버전마다 바뀐 필드만 넣는다 ([Notion 할 일 DB](#notion-할-일-db-설계)) |
| 한 번에 20건까지, 오래된 것부터 | 비용 · 실행 시간 상한. 나머지는 다음 동기화에서 |
| 30자 미만은 넣지 않음 | 빈 페이지 |

## Notion

- 읽는 범위: 사용자가 Notion 권한 화면에서 고른 페이지 · 데이터베이스만. 하위 페이지는 함께 공유된다 (앞으로 생길 것 포함).
  연결은 워크스페이스를 스스로 둘러볼 수 없다. 두 가지를 주의한다 (2026-09-27 실제 워크스페이스에서 확인):
  - **팀스페이스 맨 위의 데이터베이스**(예: Meeting · Action Items · Action)는 위에 페이지가 없어 **데이터베이스 자체를 골라야** 한다.
  - **링크된 보기**(예: 회의록 템플릿 아래의 "View of Action Items")는 원본 데이터베이스의 권한을 주지 않는다. 원본을 따로 골라야 읽힌다.
- **확인 전 데이터베이스는 글 원문으로 읽는다.** 약속이 나오지 않는 DB(목표 · 투표 등)는 `/lab`에서 "가져오지 않음"으로 끈다.
  단 할 일 DB로 보이고 속성이 분명한 DB는 동기화가 자동 확인해 할 일로 읽는다 (아래 [자동 확인](#자동-확인-2026-09-28)).
  확인 전 DB를 보류하는 안(회의록처럼 보이는 DB만 읽기)을 만들어 검토했다가 되돌렸다 (2026-09-27): 이름으로 회의록 DB를 못 알아보면("Weekly", "Notes" 등)
  핵심 원문이 경고 없이 끊기고, 커서가 지나가 되살릴 수 없다. 반면 막으려던 비용은 작다 (원문 1건 추출 · 판정 약 $0.0007, 하루 200건이어도 약 $0.14).
  그래서 공유는 넓게가 아니라 **필요한 DB만**(회의록 · 할 일 DB) 고르도록 안내한다.
- **새로 공유된 · 되돌아온 DB는 최근 14일을 다시 훑는다**: 공유되지 않은 동안에도 커서는 지나가므로, 그대로 두면 그 사이 고친 페이지(끊겨 있던 동안의 회의록)를 영영 놓친다.
  처음 보는 DB(설정 없음)나 `health.unreachable`에서 되돌아온 DB가 있으면 그 동기화만 커서를 14일 전으로 되돌린다. 이미 넣은 페이지는 걸러진다 (2026-09-27 실제로 회의록 9건 복구).
- **공유가 끊긴 DB 알림**: 동기화는 처음 본 DB를 연결 설정에 남기고(`seenAt`), 전에 읽던 DB를 읽을 수 없게 되면 `settings.health.unreachable`에 남긴다.
  `/lab`(이후 앱)이 경고를 띄운다. 다시 연결할 때 선택 화면에서 체크가 빠지면 원문이 조용히 끊기기 때문이다 (2026-09-27 실제로 회의록 DB가 빠져 있었다).
- 동기화: `POST /v1/search`로 최근 수정순 페이지를 훑고, 커서(`sync_cursor.after`) 이후의 새 페이지만 `GET /v1/pages/{id}/markdown`으로 본문을 받는다. 첫 동기화는 최근 14일.
- 변환 (`notion/map.ts`, `notion/markdown.ts`): 제목 · 회의 날짜 속성 · 사람 속성(참석자) → `participants.attendees`. 본문의 AI 요약 근거 각주 · 이미지 · 태그를 걷어 내고 사람 언급은 이름으로 바꾼다. AI 회의록 블록이 있거나 제목에 회의 · meeting이 있으면 `meeting`, 아니면 `doc`.
- 녹음 전사는 가져오지 않는다. API의 전사 블록(`meeting_notes.children.transcript_block_id`)은 화자 표시 없는 문단뿐이다 (연결된 회의록 9개 전부 확인, 2026-09-26). AI 요약과 메모만 쓴다.
  그래서 AI 요약의 담당자 없는 액션 아이템은 Notion만으로는 담당을 알 수 없다. 같은 회의의 Meet 전사가 있으면 그쪽 Claim으로 정하고, 없으면 확인을 받는다.
- 할 일 DB에 속한 페이지는 글 원문이 아니라 구조화된 할 일로 처리한다 (아래 설계).
- 속도 제한: 연결당 분당 180회(Business 이상 600회). 429면 `Retry-After`만큼 기다린다.
- Notion API 버전: `2026-03-11`.

### Notion 연결 만들기 (한 번)

1. https://www.notion.so/profile/integrations → **새 연결** → 유형 **Public**.
2. 필수 항목: 회사 이름, 웹사이트(`https://www.taskforcelabs.dev`), 개인정보 처리방침 · 이용약관 주소, 이메일.
3. **Redirect URIs**: `http://localhost:3000/api/connectors/notion/callback` (배포 후 배포 주소도 추가).
4. **Capabilities**: 콘텐츠 읽기만 켠다 (업데이트 · 삽입은 끔). 사용자 정보는 **이메일 포함**으로 (참석자 이메일로 사용자를 알아본다).
5. 발급된 OAuth client ID · secret을 `.env.local`의 `NOTION_CLIENT_ID`, `NOTION_CLIENT_SECRET`에 넣는다.
6. `.env.local`에 `SUPABASE_SERVICE_ROLE_KEY`(Supabase → Project Settings → API Keys)도 넣는다.
7. `supabase/migrations/`의 마이그레이션을 최신까지 적용한 뒤(연결 · 동의 · 속도 제한 · 보관 기간이 여러 파일에 걸쳐 있다, `docs/go-live/runbook.md` 4장) `/lab` → **Notion 연결** → 회의록 데이터베이스를 고른다 → **지금 동기화**.
   앱에서 연결할 때는 `/lab`이 아니라 `POST /api/v1/connections/notion/start` → 권한 화면 → callback이 만드는 완료 대기(handoff) → `POST /api/v1/connections/notion/complete`로 마친다([GO_LIVE.md](GO_LIVE.md) 1장).

## Notion 할 일 DB (설계)

상태: 구현 (2026-09-27). 켜는 방법은 아래 [할 일 DB 켜기](#할-일-db-켜기).

### 왜 필요한가

모든 Action이 회의에서 나오지는 않는다. 구두로 정한 일을 누군가 Notion 할 일 DB에 적고, 그 페이지에서 상태를 바꾸며 일을 진행하는 경우가 많다.
지금 커넥터는 이런 흐름을 따라가지 못한다.

| 할 일 페이지 | 지금 커넥터 | 문제 |
|---|---|---|
| 제목만 있고 본문이 비어 있음 | `# 제목`을 글 원문으로 추출기에 넣음 (30자 미만이면 아예 건너뜀) | 약속하는 말투가 없어 추출되지 않을 수 있다 |
| 담당 (사람 속성) | 모든 사람 속성을 참석자로 넣음 (`pagePeople`) | 담당 정보가 참석자로 바뀐다 |
| 기한 (날짜 속성) | 읽지 않음 | 기한이 사라진다 |
| 상태 → 완료 | 한 번 넣은 페이지는 다시 넣지 않음 | **완료 · 취소 · 기한 변경을 알 수 없다** |

### 원칙

- **LLM 추출과 Jev 판정을 쓰지 않는다.** 속성 값을 코드(순수 함수)가 Claim으로 옮긴다. 첫 등장 때 기존 Action과 맞춰 보는 매칭만 Jev를 쓴다.
- **바뀔 때마다 근거가 남는다.** 바뀐 버전마다 원문(sources) 한 줄과 바뀐 필드의 Claim · Evidence를 남긴다. 근거 인용은 속성 값을 적은 줄이고, 출처 링크는 Notion 페이지다.
- **Notion 요청을 늘리지 않는다.** 속성은 `POST /v1/search` 결과에 이미 있어서 본문(markdown)을 받지 않는다. DB 스키마만 동기화마다 DB당 한 번 읽는다.

### 1. 어느 DB가 할 일 DB인가

페이지의 `parent.data_source_id`로 DB를 구분하고, DB마다 역할과 속성 매핑을 연결 설정(`connections.settings.dataSources`)에 둔다.

```ts
type DataSourceSetting = {
  role: "tasks" | "text" | "ignore";   // 할 일 DB · 글 원문(회의록 · 문서, 지금과 같음) · 가져오지 않음
  props?: { title: string; assignee: string; due?: string; status?: string }; // 속성 id
  statusMap?: Record<string, "open" | "done" | "dropped">;                 // 상태 옵션 id → 값
  confirmedAt?: string;                                                     // 확인한 시각
  confirmedBy?: "auto";                                                     // 동기화가 자동 확인함 (없으면 사용자가 확인)
};
```

- **자동 추정** (`GET /v1/data_sources/{id}`의 속성 스키마로):
  - 할 일 DB(tasks)로 제안하려면 사람 속성 + (상태 또는 "완료" 체크박스)가 있고, 이름이 할 일 같고(Action · Task · 할 일 등), 회의 DB가 아니어야 한다.
    **회의 DB에도 Owner · Status · Date가 있는 경우가 흔하고**(참석자 속성 · 회의 이름으로 가린다), 목표 · 방향 DB도 담당 · 상태가 있어서 속성 타입만으로는 제안하지 않는다 (연결된 워크스페이스에서 실제로 확인).
  - 나머지는 text(지금처럼 글 원문). 사용자는 어느 DB든 할 일 DB나 "가져오지 않음"으로 바꿀 수 있다.
  - 속성 고르기: 이름 우선(담당 · Assignee · Assign · Owner / 기한 · 마감 · Due · Dates / 상태 · Status · Done). 이름으로 못 고르면 그 타입의 속성이 하나뿐일 때만 쓴다.
- **상태는 옵션 단위로 매핑한다.** Notion의 상태 그룹(To-do / In progress / Complete)을 기본값으로 쓰되 (To-do · In progress → open, Complete → done), Complete 그룹에 Done과 Cancelled가 함께 있는 경우가 있어 이름이 취소 · Cancel · Won't do인 옵션은 dropped로 둔다. 체크박스는 체크 → done.
- **확인한 뒤에만 할 일로 처리한다.** 추정 결과는 `/lab` 연결 패널에서 확인 · 수정한다 (앱 화면은 이후). 확인 전 DB는 지금처럼 글 원문으로 다룬다.
  매핑이 분명하면 동기화가 대신 확인한다 (아래).

#### 자동 확인 (2026-09-28)

앱에 확인 화면이 없어 실제 사용자는 할 일 DB를 확인할 수 없었다. 그래서 확인 전 할 일 DB의 페이지가 글 원문으로 들어갔고, 담당 · 상태 · 기한이 본문이 아니라
속성에 있어 Jev가 사용자의 일인지 알 수 없어 모두 기각했다 (실제 연결: 할 일 DB 3개, 확인 0개). 그래서 **할 일 DB로 보이고 속성 매핑이 분명하면 사용자 확인 없이 확인한다.**

- 조건 (`notion/tasks.ts` `autoConfirmSetting` · `unambiguousProps`, 순수 함수): 사용자가 확인한 설정이 없고, 할 일 DB로 제안되고(`suggestSetting`: 회의 DB가 아니고 이름이 할 일 같음), 아래가 모두 하나로 정해진다.
  - 이름: 제안보다 좁게 본다. 영어는 단어로만(Action · Action Items · Tasks · To-do · Issues. Transactions · Customer Interactions · Satisfaction은 아님), 한국어는 할 일 · 액션(리액션은 아님) · 업무 · 이슈.
    업무일지 · 업무 로그 · Task log · 매뉴얼 · 가이드 · 위키 같은 기록 · 문서 DB 이름이면 자동 확인하지 않는다.
    `/lab` 확인 화면의 제안(`suggestSetting`)은 그대로 느슨하다: 기본값일 뿐이고 사용자가 확인하기 전에는 할 일로 읽지 않는다.
  - 담당: 이름이 담당 · Assignee · Assign · Owner · 책임인 사람 속성(참석자 · 요청자 · 검토자 · 참조 · 작성자 등으로 보이는 이름은 빼고)이 딱 하나.
    사람 속성이 하나뿐이어도 이름이 담당 같지 않으면(참여자 · Participants · Approver · 결재자 · Team · Members) 자동 확인하지 않는다. `/lab` 제안은 하나뿐이면 그것을 고른다.
  - 상태: 상태 속성 + 이름이 상태 · Status · 진행인 선택 속성 + 이름이 Done · 완료인 체크박스를 모두 후보로 두고, 하나뿐이거나 여럿이면 이름이 상태 · Status · 진행인 것이 딱 하나.
    고른 것이 선택 속성이면 자동 확인하지 않는다(할 일로 읽을 수 없음). 상태 속성이면 기본 매핑에 열린 옵션과 완료 · 취소 옵션이 모두 있어야 한다 (완료를 가를 수 없으면 끝난 일까지 열린 할 일로 들어온다).
  - 기한: 날짜 속성 중 시작 · 만든 · 고친 날짜와 끝낸 날짜(완료일 · 완료 일시 · Completed at · Done date)로 보이는 이름을 뺀다. 완료 예정일 · 완료 목표일 · Target completion 같은
    예정 · 목표 날짜는 빼지 않는다. 남은 것이 하나면 그것, 여럿이면 이름이 기한 · 마감 · Due · Deadline인 것이 딱 하나. 날짜 속성이 아예 없으면 기한 없음.
    날짜 속성이 있는데 모두 빠졌으면(시작일 · 완료일뿐) 기한이 어디 있는지 몰라 자동 확인하지 않는다.
  - 하나라도 못 정하면 자동 확인하지 않는다 (지금처럼 글 원문, `/lab`에서 확인).
- 설정: 사용자 확인과 같은 모양에 `confirmedBy: "auto"`. 상태 매핑은 기본값(`defaultStatusMap`). `/lab` 목록에 "자동 확인됨"으로 보이고, 사용자가 역할 · 매핑을 저장하면
  사용자 확인으로 바뀐다 (같은 매핑이면 다시 훑지 않는다). 사용자가 확인한 설정(가져오지 않음 · 글 원문 포함)은 자동 확인이 덮지 않는다.
- 언제: 동기화마다, 공유된 DB 목록(`POST /v1/search`, 이미 받는 것)을 받은 직후 처음 보는 DB와 확인 전 DB에 적용한다. 같은 동기화에서 바로 할 일 경로로 읽고
  처음 훑기도 한다. 그래서 그 DB의 페이지를 글 원문으로 또 넣지 않는다. 설정은 동기화 끝에 `recordNotionHealth`가 남기고(그 사이 사용자가 확인했으면 덮지 않음),
  그 뒤 `markBackfilled`가 같은 `confirmedAt`으로 처음 훑기를 표시한다. DB 목록을 못 받은 동기화, 연결 설정을 읽지 못한 동기화(사용자가 정한 역할을 모름, 설정 내용 없이 로그만)는 자동 확인하지 않는다.
- 다시 보기 (`recheckAutoConfirmed`): 동기화마다 자동 확인한 DB를 지금 규칙 · 지금 스키마로 다시 본다. 맞으면 두고(매핑이 바뀌었으면 새 `confirmedAt`으로 다시 확인해 다시 훑는다), 더는 맞지 않으면 확인 전 설정(제안 역할 · 이름 · `seenAt`, 매핑 · `backfilledAt` 없음)으로 되돌려
  같은 동기화부터 글 원문으로 읽고 `recordNotionHealth`가 남긴다 (로그는 연결 id와 개수만). 사용자가 확인한 설정은 보지 않고, 이미 만든 Action은 그대로 둔다. 규칙을 좁히기 전에 담당 속성 "Person"으로 자동 확인된 회의 액션 아이템 DB가 남의 일을 계속 만들었다 (2026-09-28).
- 전에 글 원문(`doc`)으로 들어온 같은 페이지는 그대로 둔다. 할 일 경로는 이를 건너뛰지 않는다: 할 일 원문 버전은 `task:<last_edited_time>`라 원문 고유 조건에 걸리지 않고,
  할 일 상태(`task_source_states`) · 다시 처리(`pendingTasks`)는 `kind = 'task'`만 본다.
  그 글 원문이 Action의 근거가 됐으면(대개 기각돼 없다) 처음 등장 때 매칭 없이 그 Action에 잇는다 (`merge-task.ts` `actionFromTextSource`: 같은 연결 · 같은 페이지의 `task`가 아닌 원문의 근거가
  가리키는 Action이 딱 하나일 때). 새 Action · 중복 확인을 만들지 않는다. 사용자가 앱에서 지운 Action이면 잇기만 하고 값을 붙이지 않는다. 여럿이면 지금처럼 매칭한다.

### 2. 어떤 페이지를 넣나

| 페이지 | 처리 |
|---|---|
| 처음 보는 페이지: 담당에 사용자가 있고(`isNotionUserMe`, 아래) 상태가 open | 넣는다 → 새 Action 또는 기존 Action에 병합 |
| 처음 보는 페이지: 남의 일이거나 이미 끝남 | 넣지 않는다 (원문도 저장하지 않는다) |
| 이미 Action과 연결됨 (담당에서 사용자가 빠졌거나 끝난 경우 포함) | 넣는다 → 바뀐 필드의 Claim |

사용자인가(`notion/tasks.ts` `isNotionUserMe`, 담당과 마지막으로 고친 사람에 같이 쓴다): 연결한 사람의 Notion user id(`settings.notionUserId`, 봇 주인)를 알면
그 id이거나, 다른 id면 이메일이 프로필과 맞을 때만 사용자다. 이름 · 별칭은 보지 않는다 (같은 이름의 팀원 할 일이 내 할 일이 되고, 그 수정이 사용자 권한 `tracker`가 된다).
연결한 사람을 모를 때만 `isUser`(이메일 · 이름 · 별칭)로 본다.

담당이 비어 있는 페이지는 아직 넣지 않는다. `created_by`는 id만 와서 사용자인지 알려면 사람 조회가 더 필요하고, 넣더라도 확인 요청만 늘어난다 (원칙 3).

### 3. 속성 → 스냅샷 → 원문

페이지 버전마다 매핑한 속성만 뽑은 스냅샷을 만든다. 스냅샷은 `sources.structured`(jsonb)에 두고, 원문(`raw_text`)은 스냅샷을 정해진 형식으로 적는다.
근거 인용이 원문에 그대로 있으므로 기계 검증(`verify.ts`)을 그대로 통과한다.

```
# UI 레이아웃 이미지 보내기
담당: 청혁
기한: 2026-09-30
상태: In progress
```

- 기한: 날짜 범위면 끝 날짜, 시각이 있으면 한국 시간 날짜.
- 본문은 쓰지 않는다 (본문의 추가 약속을 글 원문으로도 넣을지는 이후에 정한다).

### 4. 바뀐 필드만 Claim으로

- 새 버전은 `last_edited_time`으로 안다. 스냅샷이 직전 버전과 같으면 저장하지 않는다 (본문 편집 · 댓글 같은 잡음). `sources`의 고유 인덱스가 이미 `(connection_id, external_id, external_version)`이다.
- **첫 등장**: 회의에서 이미 생긴 같은 일일 수 있어 기존 열린 Action과 매칭한다(임베딩 + Jev, 지금과 같음). 같은 일이고 확신이 높으면(0.6 이상) 붙인다.
  **확신이 낮으면 합치지 않는다**: 합치면 이 할 일의 값(사용자 권한일 수 있음)이 다른 Action을 덮고 이후 완료까지 그쪽에 붙는다. 따로 만들고 "중복 확인 (45%): 비슷한 Action 제목"으로 확인을 받는다.
  결과를 연결 표 `action_links (user_id, connection_id, external_id, action_id)`에 저장한다.
- **이후 버전**: 매칭 없이 연결 표로 바로 해당 Action에 붙인다. 비교 기준은 **마지막으로 처리를 마친 버전**이다.
- **처리에 실패한(또는 10분 넘게 멈춘) 버전은 다시 처리한다.** 원문에 스냅샷과 "고친 사람이 사용자인가"를 함께 저장해 두어, 페이지가 다시 보이지 않아도(커서가 지나감) 동기화마다 최근 3일 안의 실패를 20건씩 다시 처리한다. 그보다 새 버전이 처리를 마쳤으면 그 변화까지 이미 반영됐으므로 건너뛴다.
  Action을 만든 뒤 연결 직전에 멈췄던 원문은 다시 처리할 때 그 Action에 다시 잇는다 (중복을 만들지 않는다).
- **사용자가 앱에서 지운 Action**은 더 따라가지 않는다. **이미 닫힌 Action**에도 바뀐 값을 쌓는다: 확인 큐 · 알림은 열린 Action만 보여서 확인 요청이 늘지 않고, 다시 열리면 닫혀 있던 동안 바뀐 기한 · 담당이 살아 있다.

| 바뀐 것 | Claim | Evidence 인용 · 역할 |
|---|---|---|
| 첫 등장 | scope(제목) · owner · status · due | 스냅샷 전체 · created |
| 제목 | scope | `# 새 제목` · updated |
| 담당에 사용자가 들어오거나 빠짐 | owner = me / other | `담당: …` · updated |
| 기한 | due | `기한: …` · updated |
| 상태 → done / dropped / 다시 open | status | `상태: …` · completed / updated |

### 5. Claim 속성

| 속성 | 값 | 이유 |
|---|---|---|
| occurredAt | 페이지 `last_edited_time` | 규칙 4의 발언 시점 = 수정 시각 |
| channel | `task` (새 원문 종류, 채널 신뢰도는 doc과 같은 3) | 지표에서 글 원문과 나눠 보려고 |
| certainty · directness · audience | firm · first_hand · shared | 팀이 보는 기록에 직접 적은 값 |
| speakerRole / origin | 아래 결정 | |

**규칙 0(결정권)과의 관계 (2026-09-26 결정).** 규칙 0은 대화 속 약속을 위해 만들었다. 할 일 DB의 수정에 그대로 쓰면 내가 내 할 일의 제목을 고칠 때 확인 요청이 오고, 기한을 늦추면 무시되어 Notion과 Taskforce의 값이 어긋난다. 그래서:

- `last_edited_by`가 사용자면(`isNotionUserMe`: 연결한 사람의 Notion user id이거나 이메일이 맞음, 연결한 사람을 모를 때만 이름도) 사용자가 다른 도구에서 직접 고친 값으로 보고 origin을 `tracker`로 둔다. 권한은 `user`와 같게 즉시 반영하되, 앱에서 고친 것이 아니므로 AI 오판(PRD 지표 1)으로 세지 않는다.
- 다른 사람이 고친 값은 `counterpart`로 둔다(팀 기록을 관리하는 쪽의 결정). 담당 변경은 지금처럼 확인을 받는다.
주의: `last_edited_by`는 페이지 단위라, 안정화 시간 안에 두 사람이 서로 다른 속성을 고치면 마지막 사람의 수정으로 기록된다.

### 6. 동기화 변경

- `syncNotion`이 페이지를 DB 역할로 나눈다: 확인한 `tasks`(사용자 확인 또는 자동 확인)면 스냅샷 경로(`syncTasks`), 아니면 지금의 글 원문 경로. 할 일 페이지는 본문(markdown)을 받지 않는다.
- 연결한 사람의 Notion user id(봇 주인)는 넣을 글 원문이나 할 일이 있을 때만 묻고 연결 설정에 남긴다 (다시 연결하면 지운다).
- 할 일 DB는 안정화 시간이 5분이다 (회의록은 AI 요약을 기다려야 해서 30분). 막 고친 페이지가 있으면 커서를 그 앞에 둔다.
- **처음 켤 때 한 번 열린 할 일을 훑는다** (`POST /v1/data_sources/{id}/query`, 상태 매핑에서 done · dropped인 옵션을 거르는 필터, 한 번에 최대 2,000개). 커서 이전에 고친 열린 할 일은 검색 커서로는 다시 보이지 않기 때문이다.
  끝까지 훑고 다 넣었을 때만, 그리고 그 사이 사용자가 설정을 다시 확인하지 않았을 때만(`confirmedAt` 비교) 설정에 `backfilledAt`을 남긴다. 매핑을 바꿔 다시 확인하면 다시 훑는다.
- 할 일 DB 하나를 읽지 못해도(공유 해제 · 삭제) 그 DB만 건너뛰고 나머지 동기화는 계속한다.
- "가져오지 않음"으로 확인한 DB의 페이지는 건너뛴다.
- 휴지통으로 간 페이지는 Claim을 만들지 않는다 (완료된 일 정리일 수 있다).
- 할 일 원문의 버전 값은 `task:<last_edited_time>`이다. 할 일 DB로 확인하기 전에 같은 페이지가 글 원문으로 들어왔으면 수정 시각만으로는 원문 고유 조건(연결 · 페이지 · 버전)에 걸려 저장되지 않아서다 (QA에서 진행 중인 할 일 3건이 빠진 원인).
- `last_edited_by`는 id만 오므로 사람 정보(이메일)를 조회해 사용자인지 가린다. 동기화 한 번 안에서는 캐시한다.

### 알려진 한계

- Claim 시각은 페이지 단위 `last_edited_time`이다. 한 동기화 사이에 Notion에서 기한을 바꾸고, 앱에서 기한을 고치고, 누군가 Notion 본문을 고치면 Notion 값이 더 최근으로 기록된다.
- 커서 이후 고친 페이지가 한 번에 300개(`maxScan`)를 넘으면 오래된 쪽은 건너뛴다 (글 원문과 같은 기존 한계).
- `backfilledAt` 기록과 `/lab`의 설정 저장은 둘 다 설정 JSON을 읽고 고쳐 쓴다. 동시에 일어나면 한쪽이 덮일 수 있다(드묾). 필요하면 DB 함수로 한 항목만 고치게 바꾼다.
  자동 확인 · 공유 상태 기록(`recordNotionHealth`)도 같다: 다시 읽어 사용자가 그 사이 확인한 DB는 건너뛰지만, 읽고 쓰는 사이의 `/lab` 저장은 덮일 수 있다 (고치려면 DB 함수 · 마이그레이션).
- `/lab`의 데이터베이스 목록 · 저장은 동기화 잠금 밖에서 토큰을 갱신할 수 있다. Notion은 갱신할 때마다 갱신 토큰을 바꾸므로, 늦게 갱신한 쪽은 `invalid_grant`를 받는다. `withNotionClient`는 이때 저장된 토큰을 다시 읽고(그대로면 1초 기다렸다 한 번 더) 바뀌었으면 그 토큰으로 이어 간다. 먼저 갱신한 쪽이 그 사이에도 저장하지 못했으면 연결이 `reauth`(다시 연결 필요)로 남을 수 있다(드묾).
- 갱신 토큰이 만료 · 거절되면(`invalid_grant`: 처음 승인 뒤 180일, 30일 동안 갱신 없음, 권한 취소) 연결을 `reauth`로 남기고 다시 연결할 때까지 동기화하지 않는다. 앱은 "Reconnect to keep syncing"을 보인다.
- 담당이 비어 있는 할 일, 본문의 추가 약속은 넣지 않는다.
- 열린 할 일이 2,000개를 넘는 DB는 처음 훑기가 끝나지 않아 동기화마다 앞 2,000개를 다시 훑는다. 그런 DB가 생기면 훑기 커서를 설정에 남긴다.
- 공유가 끊긴 할 일 DB는 동기화마다 한 번 실패를 로그에 남긴다. `/lab` 목록에는 "읽을 수 없음"으로 남아 있어 "가져오지 않음"으로 바꾸거나, Notion에서 그 데이터베이스의 ··· → 연결에 Taskforce를 다시 추가하면 된다.
  **Notion 연결을 다시 하면(OAuth) 페이지 선택 화면에서 고른 것만 남는다**: 실제로 다시 연결한 뒤 할 일 DB 두 개의 공유가 빠졌다 (2026-09-27 QA).
- "중복 확인"을 받은 두 Action을 합치는 기능은 아직 없다. 사용자는 하나를 지울 수 있고, Notion과 이어진 쪽을 지우면 그 할 일은 더 따라가지 않는다.

### 7. 측정 (원칙 6)

- Action의 출처(글 원문 / 할 일 DB)별 AI 오판율을 나눠 본다.
- 완료 경로를 나눠 센다: Notion 상태 변경으로 닫힘 / 앱에서 사용자가 닫음. 앱에서 닫는 비율이 높으면 상태 매핑이 틀렸다는 신호다.
- 매핑 · 스냅샷 · 비교 · Claim 생성은 순수 함수라 단위 테스트로 고정한다. 골든셋 eval은 첫 등장 매칭에만 해당한다.

### 8. 이번 범위 밖

- Taskforce → Notion 쓰기 (앱에서 완료하면 Notion 상태도 바꾸기). 연결 권한에 쓰기가 필요하고, 자동 수행 단계에서 다룬다.
- 관계 속성(프로젝트), 하위 항목, 본문의 추가 약속.

### 할 일 DB 켜기

1. Notion 연결 권한에 할 일 데이터베이스를 추가한다 (`/lab` → **Notion 다시 연결 · 페이지 추가**).
   선택 화면에서 상위 페이지를 고르면 하위 페이지 · 데이터베이스(앞으로 만들 것 포함)가 함께 공유된다. 단 **팀스페이스 맨 위에 있는 데이터베이스는 그 자체를 골라야** 하고,
   링크된 보기만 있는 데이터베이스는 원본을 골라야 한다 (위 "Notion" 절).
   선택 화면은 이미 공유한 페이지를 기억하고, 사용자가 전체 권한을 가진 페이지만 보여준다.
   Notion이 운영하는 MCP 서버는 공유 없이 사용자 권한으로 읽지만, 대화형 도구용이라 백그라운드 동기화 기반으로는 쓰지 않는다 (2026-09-27 검토).
2. 속성이 분명한 할 일 DB는 다음 동기화가 자동 확인한다 ([자동 확인](#자동-확인-2026-09-28)). 그 밖에는 `/lab` → 연결 → **데이터베이스 역할 설정**에서
   할 일 DB로 제안된 데이터베이스의 담당 · 기한 · 상태 속성과 상태 매핑(open · done · dropped)을 확인하고 **확인**을 누른다. 자동 확인된 DB도 여기서 바꾸거나 **가져오지 않음**으로 둘 수 있다.
   필요 없는 데이터베이스(목표 · 투표 등)는 **가져오지 않음**으로 확인하면 LLM 비용이 들지 않는다.
3. **지금 동기화**. 처음 한 번은 데이터베이스 전체를 훑어 내 열린 할 일을 가져온다. 단 **최근 60일 안에 고쳤거나 기한이 아직 오지 않은 것만** 가져온다.
   오래 손대지 않은 열린 할 일은 방치된 경우가 많아, "지금 할 일" 맨 위를 묵은 일로 채우지 않는다 (다시 고치면 그때 들어온다).
4. 템플릿 안의 견본 데이터베이스(예: Action 템플릿의 "Tasks Tracker")는 **가져오지 않음**으로 둔다.

| 방식 | 쓰는 곳 | 페이지 공유 | 백그라운드 동기화 |
|---|---|---|---|
| 공개 OAuth + 권한 화면에서 고르기 (**우리 방식**) | Dust · Guru · Sunsama · Akiflow · Morgen · Zapier · Glean(내부 연결) | 필요 (한 번) | 가능 |

## Notion에 얼마나 더 투자할까 (2026-09-27 판단)

실제 워크스페이스(Dimension)에서 잰 숫자:

| 항목 | 값 |
|---|---|
| 최근 60일 회의(Meeting DB) | 69건 |
| 같은 기간 Action Items DB에 새로 적힌 할 일 | 34건, 그중 회의와 이어진 것 10건 (**할 일이 적힌 회의 4건, 약 6%**) |
| Action Items DB의 열린 할 일 | 113건 (기한 지남 54 · 기한 없음 57) |
| 회의 AI 요약의 "액션 아이템" | 회의마다 있음 (예: 9/22 Weekly meeting 5건 → DB에는 0건) |

- **약속은 회의록(AI 요약)에 남고, 할 일 DB에는 거의 옮겨지지 않는다.** 팀 가이드("Action Items DB 가이드")가 회의 중 즉시 적으라고 하지만 실제로는 6%만 적힌다.
  Taskforce의 가치는 여기서 나온다: 적히지 않은 약속을 회의록에서 찾는 것. 그래서 **회의록(글 원문)이 1순위**이고 할 일 DB는 보조다
  (이미 적힌 일과 중복을 만들지 않고, 완료를 따라가는 용도).
- 할 일 DB 연동은 지금 수준에서 멈춘다: 확인한 DB만, 최근 60일, 속성 매핑. DB마다 다른 속성 · 템플릿 · 링크된 보기를 더 자동으로 맞추는 작업은
  워크스페이스마다 모양이 달라 끝이 없다("지지고 볶기"). 베타 사용자의 실제 설정 실패가 보이면 그때 고친다.
- Notion MCP로 바꾸지 않는다: 권한은 넓지만 180일마다 다시 로그인해야 하고, 응답 형식이 보장되지 않으며, 대화형 도구용이다. 전사에도 화자가 없다.
- 회의록만으로 안 되는 것: **담당(화자 없음)과 참석자**(Meeting DB에 참석자 속성이 없음). 이건 Notion을 더 파서가 아니라 다른 소스로 푼다 → 아래 순서.
