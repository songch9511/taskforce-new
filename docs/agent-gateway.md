# 에이전트 게이트웨이 (0.2.0 D1a–D1d) — 결정 기록과 위치

2026-10-13 · 구현 계획 D1a · 근거: Assistant 계약 v3 3.4 · 3.6 · 3.8 · 4.2, 런타임 계약 5장(`agent_tasks` · `agent_sessions` · 사건 봉투), 아키텍처 9.1(bridge), I16 · AC-20.
**1–6장은 D1a 당시 기록이다. 현재 턴 준비 경로는 8장(D1c-1)을 따른다.**
**D1a는 표 · 열 · 제약 · 인덱스 · RLS · 권한뿐이다. 에이전트를 실행하는 코드, route, gate, 앱 화면이 없다. 운영 DB 적용 전.** 이 문서는 "무엇을 만들었고, 무엇을 일부러 안 만들었고, 어디 있는가"만 적는다. 일반 규칙은 [FEATURE_MAP.md](FEATURE_MAP.md), 실행의 기본 계약은 [EXECUTION.md](EXECUTION.md), 같은 원칙의 앞 묶음은 `20261109000000_execution_additive_contract.sql`(C1)이다.

## 2. 새 표 넷

넷 모두 `user_id` + RLS(`owner_all` 정책, 앱은 `select`만 · 쓰기는 서버(service role)만) + 부모와 `(id, user_id)` 복합 외래키다. 남의 행을 가리키지 못한다.

| 표 | 무엇 | 지킬 것 |
|---|---|---|
| `bridges` | Mac bridge 최소 identity. `device_ref`(기기 식별의 해시, 사용자당 유일) · `status`(`active` · `revoked`) · `capabilities`(bridge가 보고한 "설치돼 있고 이 버전" 값, JSON 객체) · `last_heartbeat_at` · `revoked_at` | 이메일 · 토큰 열이 없다. 이름은 표시용 `device_name`(OA F1s, 11장) 하나뿐이고 식별 · 판정 · 조인에 쓰지 않는다. `revoked` ↔ `revoked_at` |
| `agent_connections` | 에이전트 연결. `adapter`(registry 문자열 `agent:<이름>`, 64자 이하) · `bridge_id` · `device_ref` · `status`(`active` · `error` · `revoked`) | v1 `connections`를 넓히지 않는다(AC-20). 로그인 계정 · 이메일 · 토큰 열이 없다(I16). bridge가 지워지면 `bridge_id`만 빈다 |
| `agent_sessions` | 세션 binding. `connection_id` · `external_session_id` · `workspace_ref` · `display_name` · `status`(`bound` · `external` · `unreachable` · `closed`) · `bound_action_id`("처음 맡긴 이슈" 기록뿐) · `last_turn_seq` · `last_event_seq` | 연결 안에서 외부 세션 유일. 연결이 지워지면 세션도 지워진다. Action이 지워지면 `bound_action_id`만 빈다 |
| `agent_tasks` | 원격 작업(턴 하나 또는 맡긴 작업 하나). `run_id` · `step_id` · `agent_session_id` · `message_id` · `state`(아홉 값, `idle` 포함) · `last_live_state`(열린 상태 넷 중 하나, `state = 'unreachable'`이면 필수) · 지시 버전 · 결과 회차 · `pending_question` · `result_refs` | `idle`은 `completed`가 아니다(턴의 끝). 열린 상태만 `unreachable`이 된다 — `idle` 작업은 끊긴 것으로 바꾸지 않는다(AC-21). `awaiting_answer`이면 `pending_question`이 있다. 질문 모양은 서버 zod가 검증한다 |

## 3. 기존 표 확장

- `execution_runs`: `kind`(`task` 기본 · `conversation`) · `agent_session_id`(세션이 지워지면 비움) · `reviewed_turn_seq`(마지막 검토가 본 턴). `conversation`은 goal `agent`뿐. 부분 unique `(agent_session_id, action_id) where kind = 'conversation' and state not in ('done','failed','stopped')`: 세션 × 이슈마다 열린 대화 run은 하나.
- `execution_events`: `type`에 `'agent'` 추가 + `external_event_id` · `external_seq` · `directive_version` · `turn_seq` · `bridge_id` · `payload`. `type = 'agent'` ↔ `external_event_id` 있음(1–200자, 빈 문자열 불가). 부분 unique `(run_id, external_event_id) where type = 'agent'`: 같은 사건은 run마다 한 번만. **`payload`에 글을 담지 않는다**(질문 글은 `agent_tasks.pending_question`, 결과 글은 산출물에만) — 검증은 서버 코드(D1c-2)이고 DB는 JSON 객체인지만 본다. 앱은 `execution_events`를 읽지 못한다.
- 기존 트리거(`execution_runs_log` 등) · 함수는 바꾸지 않았다.

## 4-1. 서버가 지킬 것 (D1c) — DB가 막지 않는 것

복합 FK는 "같은 사용자의 행"까지만 보장한다. 아래는 DB가 막지 않으므로 서버 코드(D1c)와 시험이 지킨다.

- (a) 세션 · 연결을 지우기 전에 그 세션의 열린 대화 run을 먼저 `stopped`로 끝낸다. 세션을 지우면 `execution_runs.agent_session_id`가 null이 되고, 열린 대화 run의 부분 unique는 null을 구분하지 않아 세션 없는 열린 run이 쌓일 수 있다.
- (b) `agent_tasks.step_id`는 같은 run의 단계여야 하고, 대화 run(`kind = 'conversation'`)의 작업이면 `agent_tasks.agent_session_id`가 그 run의 `agent_session_id`와 같아야 한다. 복합 FK는 사용자만 맞춘다.
- (c) 글 보관 기한 정리(런타임 계약 V08)가 `agent_tasks.pending_question`과 `agent_sessions.display_name`까지 닿도록 넓힌 뒤에 D1을 켠다. 지금 정리 함수는 이 두 열을 모른다.
- (d) 사건 `payload`에는 글을 담지 않는다. DB는 JSON 객체인지만 본다.

## 5. 하지 않은 것 — 실행 입구는 D1c가 연다

이 묶음 뒤에도 goal `agent` run은 만들어지지 않고 어떤 에이전트 단계도 실행되지 않는다.

- `create_run`(goal `draft`만) · `append_step`(`plan` · `draft` · `external`만) · `begin_call` · `approve_*` · 실행기는 한 글자도 바꾸지 않았다. 이 파일은 함수를 만들지도 바꾸지도 않는다.
- `execution_tools` · `execution_controls`에 `agent:*` 행을 더하지 않았다(D1c-1은 별도 대화 run 함수와 막힌 message 도구만 더한다. `create_run`의 goal 검사는 유지한다).
- 이 묶음에 없는 것: `bridge_commands`(D2a) · `agent_path_leases`(D3c) · `context_members`의 agent_session 종류 · `execution_artifacts` 열 · route · gate · 앱 화면. (`conversations` · `conversation_messages` 열은 D1b가 더했다 — 7장.)
- 사건 `payload`의 "글 없음" 규칙, `pending_question`의 모양, `turn_seq` 직렬화는 서버 코드가 한다(위 4장).

## 6. 적용

운영 DB에는 병합 직전 승인을 받고 `supabase db query --linked -f supabase/migrations/20261113000000_agent_gateway_core.sql`로 한다(`db push` 금지). 한 트랜잭션이고 `lock_timeout 5s`라, 잠금을 오래 기다리면 실패한다(그대로 다시 적용한다). `execution_events.type`의 기존 CHECK가 정확히 하나가 아니면 아무것도 바꾸지 않고 실패한다.

## 7. 대화 대상과 에이전트 글 (D1b) — 결정 기록과 위치

2026-10-13 · 구현 계획 D1b · 근거: Assistant 계약 v3 3.1 · 3.2 · 3.4("질문에 대한 답") · 3.5 · 8장. D1a(`20261113000000`) 위에 쌓는다.
**저장과 SQL 함수만이다: 열 · 제약 · 트리거 · 서버 전용 함수 둘 · 기존 함수 셋의 교체. route · zod 계약 · 앱 · bridge · 턴 시작 · 전달 단계는 없다(D1c-1 · D1c-2 · D1d). 운영 DB 적용 전.**

### 7-2. 대상별 규칙 (`conversation_post_message`, 시그니처 · 반환 모양 그대로 교체)

| | 대상 `taskforce` | 대상 `agent` |
|---|---|---|
| 새 메시지 | B2 그대로: 처리 표시(`reply_lease_until`)를 건다, 전달 열은 null | 처리 표시 없음, `delivery_state = 'queued'`, `delivery_expires_at = 저장 + 24시간`, `delivery_reason = null` |
| 같은 `client_message_id` | `mismatch` · `refs_mismatch` → `answered` → `stale` → `in_progress` → `retry` | `mismatch` · `refs_mismatch`는 그대로, 그 밖에는 `exists`(기존 id · seq)이고 행을 고치지 않는다. 뒤에 새 메시지가 있어도 앞 메시지를 버리지 않는다(`stale` 없음) |
| 코디네이터 사건 | 사용자 메시지마다 `user_message` 한 건(생산자 트리거, 삼키면 회수 sweep이 메운다) | 없다: `coordinator_on_user_message`가 건너뛰고 `coordinator_recover_missing`도 이 대화의 메시지를 회수하지 않는다. 그 메시지는 전달 경로가 처리한다 |
| Taskforce 모델의 답(`reply_to`) | 쓴다 | 쓰지 못한다(백스톱 트리거가 거절 — `conversation_finish_turn`도 같다) |

### 7-3. 함수 (새 서버 함수 둘은 service role 전용, 앱 · 익명은 실행 불가)

- `conversation_append_agent_message(p_user_id, p_conversation_id, p_agent_task_id, p_turn_seq, p_event_id, p_text, p_kind in ('reply','question','event'))` → `(status, message_id, seq)`. 대화 행을 잠그고 `seq = max + 1`로 `assistant`(reply · question) 또는 `event` 행을 쓴다. `reply_to`는 null, `external_event_id = p_event_id`, `content = { author: { kind: 'agent', adapter }, kind, turn_seq?, truncated? }`(`turn_seq`는 null이면 키가 없다).
  - 결과: `created` · `duplicate`(같은 event id가 있으면 기존 id · seq, 아무것도 쓰지 않음) · `not_found`(대화 · 작업이 없거나 남의 것) · `wrong_target`(대상이 `agent`가 아님) · `wrong_session`(작업의 세션 ≠ 대화의 `agent_session_id`, 세션이 아직 안 묶인 대화 포함) · `wrong_conversation`(reply · question인데 작업의 `message_id`가 이 대화의 메시지가 아님). `event`는 세션만 맞으면 된다. 인자가 어긋나면 `22023`.
  - 글은 20,000자와 32,768바이트(UTF-8) 이하로 글자 단위로 자른다(멀티바이트를 가르지 않는다). 잘랐으면 `content.truncated = true`. 전문은 Mac bridge 원장에 있다.
  - `agent_tasks` · `agent_sessions` · `execution_*`는 쓰지 않는다. 잠그는 것은 대화 행 하나.
- `conversation_expire_agent_messages(p_now timestamptz)` → 바꾼 수. `delivery_expires_at < p_now`인 `queued` · `not_sent`를 `expired`로(이유는 남긴다). `dispatched` · `cancelled` · 이미 `expired`는 건드리지 않는다. 사용자 경계 없이 전체(cron용), 한 번에 최대 1,000행(가장 오래된 만료부터)이라 호출자가 0이 될 때까지 반복한다. 다른 트랜잭션이 잡은 행은 기다리지 않고 건너뛴다(다음 sweep이 본다). `p_now`가 null이면 `22023`.
- 교체한 기존 함수(권한 · 시그니처 유지): `conversation_post_message`(7-2), `coordinator_on_user_message`(`agent` 대화는 적재하지 않는다), `coordinator_recover_missing`(**코디네이터 결정으로 추가**: 본문은 `20261110000000_coordinator_core`의 정의를 그대로 옮기고, 사용자 메시지 회수의 안쪽 select에 대상 `agent` 대화 제외 조건 한 줄만 더했다. `limit`이 제외 뒤의 메시지를 센다).

| `agent` 대화의 메시지는 코디네이터 사건이 아니다 | 생산자 트리거 + 회수 sweep 둘 다 건너뜀 | — |

### 7-5. 서버가 지킬 것 (D1c · D1d) — DB가 막지 않는 것

- (a) 세션이 대화의 연결에 속하는지(`agent_sessions.connection_id = conversations.agent_connection_id`)는 복합 외래키가 보장하지 않는다(같은 사용자의 다른 연결 세션을 묶을 수 있다). 첫 전달에서 묶을 때 확인한다.
- (b) `agent_session_id`의 값 → null은 DB가 막지 않는다(세션 삭제의 `set null`과 직접 갱신을 구별하지 않는다). 앱은 쓰기 권한이 없고 서버만 쓴다.
- (c) 연결 삭제는 그 연결의 대화가 있으면 거절된다(`restrict`). 대화를 `archived_at`으로 보관해도 대화 행이 남아 있으므로 거절은 그대로다. 그래서 연결 해제 경로는 대화를 삭제하거나, 대화를 보존하려면 연결을 지우지 않고 `revoked`로 둔다(D1c 결정). 계정 삭제(`auth.users`)는 사용자 cascade로 둘 다 지워지며 시험이 확인한다(PGlite · 실제 Postgres).
- (d) 세션 단위 `event`(중단 확인 · 연결 끊김 · 결과 검토)는 그 세션에 묶인 **모든 대화**에 한 줄씩 쓴다 — append는 대화 하나에만 쓰므로 반복은 D1c-2의 몫이다. 같은 event id는 대화마다 따로 유일하다.
- (e) `delivery_state` 전이(`queued` → `dispatched` · `not_sent`, 되돌리기, `cancelled`)는 이 묶음에 없다. 전달 단계의 intent를 만드는 트랜잭션(D1c-1 · D1d)이 같은 트랜잭션에서 바꾼다. DB는 값의 모양과 이유 ↔ 상태만 본다.
- (f) 글 보관 기한 정리(V08)가 `delivery_reason` · `external_event_id`를 어떻게 다룰지는 정하지 않았다(`external_event_id`는 남기는 쪽이 계약 3.5). D1을 켜기 전에 정한다.

### 7-6. 하지 않은 것

- 측정 이벤트(계약 8장 `metric_events.props` · 새 type)는 첫 사용 WP(D1c-1)가 더한다. 이 묶음의 새 쓰기 경로는 8장 표에 대응하는 이벤트가 없다.
- `conversation_finish_turn` · `conversation_release_lease` 변경 · 턴 시작 · 전달 단계 · `agent_tasks` 쓰기 · route · `contract.ts` · Swift · 앱.

### 7-7. 적용

운영 DB에는 병합 직전 승인을 받고 `supabase db query --linked -f supabase/migrations/20261114000000_conversation_agent_target.sql`로 한다(`db push` 금지). `20261113000000_agent_gateway_core` 뒤에 적용한다. 한 트랜잭션이고 `lock_timeout 5s` 뒤에 `conversations` · `conversation_messages`를 정해진 순서로 `NOWAIT`으로 먼저 잠근다 — 두 표 중 하나라도 이미 잠겨 있으면(진행 중인 대화 쓰기 포함) 기다리지 않고 바로 `55P03`으로 실패하고 롤백한다(그대로 다시 적용한다). 기다리면 B2 답 저장(`conversation_finish_turn`: 메시지 표를 먼저 읽고 대화를 잠금)과 순환 대기가 되어 `40P01`이 날 수 있어서다(`lock_timeout`은 교착을 막지 못한다; 시험 `tests/pg` T13). 기존 행은 새 열이 기본값(`taskforce` · null)이라 영향이 없다.


## 8. 턴 시작 · 이슈 결정 · 대화 run (D1c-1)

`20261115000000_agent_turn_start.sql`과 `src/lib/agents/{registry,capability,turns,delivery}.ts`가 대화 메시지를 `prepared`까지 만든다. 실제 provider 호출 · bridge 명령 · route는 없다. `create_run`은 여전히 draft만 받으며 `EXECUTABLE_GOALS` · `EXECUTABLE_STEP_KINDS`도 그대로다.

- `start_agent_turn(user, message, added_action_ids, added_context_ids, access, live_limit)`: 메시지 소유자/대상/상태/만료 → 세션 잠금 → 보류 판단 → Action 결정/생성 순서다. 보류 중에는 메시지 상태/정규화 칩과 필요한 pending 세션만 저장한다. 후보가 여럿이면 세션 생성/바인딩도 하위 트랜잭션으로 되돌리고 `refs.referent_candidates` 최대 셋과 응답 `candidates`를 남긴다. `set_agent_message_referent`는 후보 중 내 열린 Action만 저장하며 시작 시 다시 검증한다.
- 세션이 없으면 `bound`, `external_session_id = pending:<conversation_id>`로 만들고 대화에 한 번 묶는다. 필수 `workspace_ref`도 같은 임시 식별자다. `display_name`은 메시지 첫 비어 있지 않은 줄의 공백 정리 + 80자(없으면 `Untitled`)다. 실제 세션/작업공간 증거는 bridge 사건 WP가 교체한다.
- 칩 없는 메시지는 직전 턴의 열린 Action을 재사용한다. 직전 Action이 done/dropped이거나 첫 턴이면 실제 시작할 때만 결정적 Action/note id, 위 제목 규칙, scope/owner/status user Claim, 원문 note와 `created` Evidence를 `write_action`으로 쓴다. 이벤트는 `user_created/assistant_agent`, `source_id=null`. 칩 id는 중복을 제거하며 active context 칩 하나만 사용자 멤버십 RPC로 붙인다.
- `open_agent_conversation_run`은 기존 `create_run`과 같은 정책/예산/초기값을 쓰되 `kind=conversation`, `goal=agent`, 세션과 최초 `conversation_id`를 지정하고 plan을 만들지 않는다. `request=''`, 단계 `body=''`, `args={message_id}`이며 bridge 명령 생성 시 보관 기한 내 메시지 행을 읽는다. 열린 세션×Action 부분 unique 충돌은 기존 run 재조회로 처리한다. conversation의 `append_step`은 `agent_message`만 허용한다.
- 직접 에이전트에게 보낸 메시지의 전달은 사용자 결정이므로 `prepare_step`의 conversation `agent_message`는 `needs_approval=false`다. task 외부 단계의 승인과 실제 에이전트 도구 호출 정책은 별개다. 접수/실패로 대화 run을 닫지 않으며 task 완료/실패는 유지한다.
- 잠금 순서는 메시지 → 사용자 advisory → 대화 `FOR NO KEY UPDATE` → 세션 `FOR UPDATE` → run이다. 외부 작업 한도는 TS가 `MAX_LIVE_EXTERNAL_TASKS`를 인자로 넘기고 SQL이 사용자 잠금 안에서 검사한다. `dispatched/accepted/running/unreachable`만 세며 `idle/awaiting_answer`는 제외한다. 진행 중 세션은 `session_busy`, external은 `session_external`, 한도는 `live_limit`, 앞선 메시지는 `queue_order`로 queued다. closed는 `not_sent/session_closed`다.
- FIFO는 각 대화의 만료 전 queued/not_sent 중 seq가 작은 메시지를 먼저 고른 뒤, 대화 머리끼리 created_at/seq/id로 정한다. `created_at`은 트랜잭션 시작 시각이라 같은 대화의 seq를 뒤집는 데 쓰지 않는다. 미확정 referent와 영구 제외 사유(`invalid_referent/session_closed/not_found/already_dispatched`)는 순서를 막지 않는다.
- 메시지 `dispatched`, 작업 `dispatched`, 단계 `prepared` + `intent_key`, `agent_message_sent` 지표는 원자 저장한다. `execution_intents` 표식/lease/`calling`은 만들지 않는다. 실패가 확인된 재시도만 purpose `message:<id>:<n>`을 쓰며 unknown 결과는 재전송하지 않는다.
- `next_queued_agent_message(user,session)`은 id 또는 null만 읽고 반환한다. SQL에 adapter registry는 없다. TS `startNextQueuedTurn`이 현재 registry/정책/연결로 등급을 계산하고 `startAgentTurn`을 부른다. 시작 불가 결과 not_found/already_dispatched는 소유자·대상·상태·만료 검증을 거쳐 같은 reason의 not_sent로 제외한다. 재시도 칩은 `refs.agent_turn`의 added 칩을 우선하고 없으면 `selected`를 쓴다. 호출자는 세션/작업 잠금을 쥐지 않아야 하며 API WP는 selected에 auto 칩을 섞지 않는다.
- registry: Claude Code는 2026-10-21 실제 CLI R1 증거(R1-04 `revocation` · R1-02/02b `read_only` · R1-03/03b/03c `target_scope`, 기록 `docs/rollouts/claude-code-r1-evidence.md`와 `registry.ts`의 evidence)로 쓰기 등급이다(S0 초기값은 등급 없음/`direct_chat=unsupported`였다). Codex는 `read_only`. bridge 보고는 검증 증거가 아니다. 버전 범위 자체 점검/프로토콜 hash는 adapter WP 책임이다. 두 adapter의 message 도구는 external, provider control은 blocked다.

모든 새 RPC는 `SECURITY INVOKER`, `search_path=''`, service_role만 실행한다. metric 확장 블록은 코디네이터 원문 그대로이며 앱 insert 정책은 app_opened/assistant_opened만 허용한다. 마이그레이션은 한 트랜잭션, lock_timeout 5초, metric_events 잠금은 NOWAIT이다.

검증 위치: `tests/db/agent-turn-start.scenarios.ts` · `.test.ts`, `tests/pg/agent-turn-start.test.ts`, `src/lib/agents/*.test.ts`. PG 경합 시험은 샌드박스에서 작성만 했으며 실행 증거는 별도다. 질문/중단/사건·bridge API·대화 API 연결은 후속 WP다. 특히 실패 재시도의 앞 failed 단계와 기존 begin_call의 앞 단계 검사는 bridge API에서 맞춰야 한다; 이 WP는 prepared에서 멈춘다.


## 9. 에이전트 사건 반영 (D1c-2a)

`20261116000000_agent_events.sql`의 `apply_agent_event(user,event)`와 `src/lib/agents/events.ts`가 bridge 사실을 적용한다. 서버 내부 봉투는 `{adapter,session_ref:{agent_session_id},agent_task_id?,external_task_id?,event_id,seq?,turn_seq?,type,payload?,text?,question?,observed_at}`다. 기존 bridge DTO와 route 연결은 다음 WP가 맡는다.

- 사용자·세션·adapter·run·step 귀속을 잠금 후 다시 검사한다. 잠금 순서는 메시지 → 대화 → 세션 → run → task → step이며 기존 표 migration 잠금은 execution_runs → agent_tasks 순서로 둘 다 NOWAIT다. `(run_id,external_event_id)` 중복은 쓰기 0이다. seq는 1 이상, observed_at은 ISO 시각이며 last_seen_at과 seq는 역행하지 않는다. accepted는 seq-late에서, session_bound는 seq/turn late에서 제외한다.
- dispatched의 첫 accepted/progress/message/question/artifact는 calling+lease를 확인한 뒤 `settle_step(called)`로 접수부터 정산한다. prepared는 step_not_calling/기록 0이다. 같은 턴의 첫 활동은 seq-late여도 접수 사실을 먼저 정산한다. 해당 활동의 나머지 상태·질문·산출물 효과는 late로 억제하며, 다른 turn은 접수하지 않는다. 사건의 external_task_id는 task 잠금 아래 최초 바인딩하고 receipt에 남긴다. 다른 값이나 같은 세션의 다른 task와 충돌하면 conflict/변경 0이다. `progress`는 accepted→running, 반복 progress는 ignored+heartbeat이며 accepted→awaiting_answer도 허용한다. `turn_completed`는 idle이며 먼저 온 완료도 접수를 정산한다. 같은 상태 재적용은 ignored로 기록해 event 줄을 중복 생성하지 않는다. 접수 전 failed는 4종 reason과 not_sent, cancelled는 failed 단계·cancelled receipt·cancelled delivery를 원자 저장한다. 접수 뒤 failed reason은 생략 또는 agent_error이며 대화 run은 닫지 않는다. 접수 뒤 접수 전 reason 4종이 오면 22023 예외 대신 원장에 conflict로 기록하고 상태는 바꾸지 않는다.
- **Claude Code synthetic assistant는 활동이 아니다.** S0 CC-8의 미로그인 흐름은 `system:init` → `assistant`(`model: <synthetic>`, “Not logged in…”) → `result is_error`다. Bridge · Claude Code adapter WP는 `model`이 `<synthetic>`인 assistant를 `message`나 접수 신호로 보내지 않고, 그 턴을 `failed {reason: sign_in_needed}`로 보낸다(접수 전 실패 → 메시지 `not_sent`). 계약 3.2 · 13.2의 “첫 assistant 사건 = 접수”에서 synthetic은 제외한다.
- 질문은 별도 `question={provider_request_id,kind,structured,questions[1–4]{id,header,text,options[{label,description}],multi_select,allow_other,secret}}`다. TS strict zod와 SQL CHECK가 검증하며 서버는 `question_key=[agent_task_id,provider_request_id]`, `asked_at=observed_at`을 붙여 pending_question에 저장한다. 기존 질문은 question_conflict로 보존한다. 질문 글·선택지는 pending_question에, 봉투 text는 D1b의 question 대화 줄에 저장한다. 원장에는 question_key/kind/question_count 메타데이터만 남긴다. request id 1–200자, 질문 id/header 200자, text 4000자, option label/description 500/1000자, 질문당 선택지 10개와 고유 질문 id를 검사한다. task id와 question_key[0]가 같아야 하며 metadata 포함 pending_question은 JSONB UTF-8 32KB 이하다.
- message/question의 대화 글은 그 턴을 시작한 대화에만 D1b append로 저장하고 UTF-8 32KB를 넘으면 자른다. seq-late reply도 같은 turn이면 event id당 한 번 저장하되 not_sent 턴과 다른 turn의 글은 기록만 한다. payload는 허용 키만 받으며 입력과 최종 원장 모두 JSONB 표현 기준 4KB다. 길이 제한은 Unicode 문자 수(SQL char_length)로 맞췄다. 세션 event 줄은 TS가 고정 문구로 모든 연결 대화에 쓰며 부분 실패 뒤 duplicate 재시도가 누락된 줄을 보완한다. 원래 사건 복구는 at/id 순서로 선택한다(동시 fanout 전체 순서를 직렬화하는 것은 아니다).
- `unreachable`은 열린 상태의 last_live_state만 보관하고 idle은 바꾸지 않는다. reconcile은 last_live_state로만 복원한다. payload.state가 다르면 reconcile_conflict/쓰기 0이다. bridge는 끊긴 동안의 원래 사건을 원래 event_id로 재생해 단계와 task를 정상 경로로 옮긴 뒤 reconcile한다. reconcile이 접수나 실패 reason을 만들지 않는다.
- `session_bound`는 pending id를 실제 id로 바꾸되 기존 세션 id 충돌은 conflict다. 세션을 합치지 않으며 이미 같은 실제 id면 ignored다.
- 산출물은 새 `agent_artifacts`에 run/task/turn/path/content_hash/summary(≤2000자)만 저장한다. 같은 run/path의 이전 산출물에 superseded_at을 붙이고 늦은 이전 턴이 최신을 대체하지 않는다. 본문·diff는 저장하지 않는다. authenticated owner_all RLS와 `(agent_task_id,run_id,user_id)` 복합 FK 및 user/task/run 인덱스를 쓰며 앱은 SELECT, 서버만 쓴다. 기존 `execution_artifacts`와 Swift 읽기는 바꾸지 않았다. 후속 Review의 result_ready 계산은 agent_artifacts를 읽어야 한다.

새 함수는 INVOKER, search_path='', service_role 전용이다. 사건 적용용 metric type은 Assistant 계약 8장에 없어 새로 만들지 않았다. 검증은 `events.test.ts`, `tests/db/agent-events.*`, `agent-artifacts-rls.test.ts`; `tests/pg/agent-events.test.ts` 경합 시험은 작성만 했으며 실제 PostgreSQL 실행 증거는 없다. D1c-2b가 질문 답 CAS·Stop/Done·정리, bridge API가 인증된 입구·lease/calling·provider 접수 신호·재생/fanout 재시도를 연결한다.

D1c-2a 정정 2 인계: lease 만료 unknown_outcome 뒤 접수는 bridge API의 readback 설계 대상이다. pending_question 글·agent_artifacts.summary는 현재 purge_expired_execution_text 밖이며 보관 기한(V08)·처리방침(DEC-4 gate)에서 정한다. agent_connections.bridge_id와 발신 bridge 대조는 인증 route가 맡는다.

## 10. 질문 답 · Stop · Done (OA D1c-2b)

`20261116120000_agent_questions_stop.sql`과 `lib/agents/{questions,tasks,turns}.ts`는 서버 내부 입구다. 실제 route·bridge 전달은 아직 없다. 단계는 `prepared`까지만 만들며 provider 차단과 기존 실행기의 제한을 유지한다.

- `answer_agent_question(user,task,provider_request_id,answers,answered_locally,answer_message_id=null)`는 현재 질문 열쇠를 잠금 아래 비교한다. 질문이 바뀌면 `question_stale`, 같은 답의 재전송은 `duplicate`와 최신 step id다. 답은 질문 id→문자열/비어 있지 않은 선택지 배열, 승인 질문은 allow/deny다. 공백 Other는 거절하고 승인 event는 Allowed/Denied다.
- 질문은 `pending_question`에서 `answered_question`으로 옮긴다. 답 단계가 calling에서 failed로 정산되면 카드를 복원한다. 재시도마다 새 단계와 `answer:<task>:<request>:<n>` intent(n=0부터 실패마다 +1)를 만들며 이전 실패 원장은 남긴다. 수정한 선택 label은 기존 event 한 줄에 반영한다. 접수 뒤 일반 실패와 unknown_outcome은 카드 복원 대상이 아니다. 이전 seq의 활동은 답의 접수 증거가 아니다.
- TS는 `question`을 필수로 받고 비밀 질문이 하나라도 있으면 값을 RPC로 보내지 않는다. SQL도 잠금 뒤 현재 질문으로 검사하며 `{answered_locally:true}`만 기록한다. `answeredLocally`의 증거는 14장의 `POST /api/v1/bridge/answer-local`(OA F2: 기기 secret + 세션의 연결이 그 bridge)이며 요청 body의 boolean을 그대로 넘기지 않는다. 혼합 질문도 전체 답을 로컬에서 주입한다.
- `startAgentTurn`은 `route_agent_message`를 부른다. 그 턴을 시작한 대화에서 서버가 매긴 메시지 `seq`가 그 턴의 마지막 질문 줄보다 큰 메시지만 input 질문 하나·allow_other·비밀 아님 조건으로 답이 된다. 자유 글 단계 args는 `{agent_task_id,provider_request_id,answer_message_id}`뿐이고 본문은 대화 메시지 보관 기한을 따른다. 카드 답의 `args.answers`는 `purge_expired_execution_text`가 지우고 id·상태·버전·intent는 보존한다. bridge의 `observed_at`과 서버 `created_at`은 이 판정에 비교하지 않는다. 다른 대화·질문 전 메시지·다중 선택 등은 `question_open`으로 대기한다. 대기 경로의 칩 소유권·FIFO·한도 검사는 기존 start 함수를 재사용한다.
- `stop_agent_session(user,session,surface,cancel_scope)`는 `{tasks:[{agent_task_id,cancel,processes?}]}`를 반환한다. lease되지 않은 pending/prepared 최초 턴은 단계 skipped·task cancelled·메시지 cancelled로 즉시 confirmed, cancel 단계 0이다. Claude Code 보류(unreachable의 마지막 상태가 awaiting_answer인 경우 포함)와 답을 받았지만 아직 pending/prepared이고 lease·intent·calling 이력이 없는 턴은 deny 기록과 confirmed다. 후자는 answered_question의 열쇠를 버리고 답 단계를 skipped로 정리하며 cancel 단계는 만들지 않는다. 나머지는 `cancel:<task>` prepared와 requested_only, Codex의 requested_only에는 processes=may_continue가 붙는다.
- Stop·Done은 버린 질문의 열쇠만 `abandoned_question`에 남기고 `pending_question`을 비워 카드를 숨긴다. abandoned_question은 null 또는 해당 task의 `[task id, request id]`만 허용한다. 어느 adapter든 미전달 답이 skipped가 되면 answered_question의 열쇠를 기록하고 자유 글 답 메시지는 cancelled로 바꾸며 `refs.answer_for`는 보존한다. task가 idle/completed/failed/cancelled가 되면 그 task의 남은 pending/prepared 단계도 skipped다. lease·intent·calling 이력이 있는 단계는 미전달로 확정하거나 skipped로 정리하지 않는다. 일반 Stop은 열린 run·대기 메시지를 멈추고 event와 stop_requested를 남긴다. external 세션은 run만 멈추며 대기 메시지를 그대로 보존한다.
- 잠금은 메시지→대화→세션→run→task→step이다. Stop의 메시지 잠금은 보류 중 사용자 메시지와 진행 중 task의 원문만 잡는다. 세션 잠금 뒤 새 행을 NOWAIT로 재확인하며 55P03은 전체 롤백, TS는 최대 3회 시도한다. 답은 잠금 뒤 run 상태·세션 external/closed·연결 active·귀속을 다시 검사한다.
- Done/dropped는 사용자 status Claim 트리거에서 해당 이슈의 열린 대화 run만 gate `action_closed`, stopped_at=null로 멈춘다. 세션 삭제는 gate `session_deleted`로 같은 중단을 하며 둘 다 stop_run/코디네이터 run_stop 결정을 만들지 않는다. Done은 Action→run→task로 진행하며, 질문이 없는 작업은 세션·원 메시지를 잠그지 않는다. 질문이 있는 작업은 작업 행을 한 트랜잭션에서 두 번 갱신해 PostgreSQL의 FK 재확인이 세션·원 메시지 KEY SHARE를 기다리므로(15장) 그 갈래 첫 줄에서 둘을 FOR KEY SHARE NOWAIT로 먼저 쥔다. 미전달 원문·답 메시지를 cancelled로 바꿀 때도 메시지 NOWAIT로 잠금 순환을 피하며 충돌 시 Done 전체가 롤백된다. `writeAction`·`writeProgress`는 SQLSTATE 55P03(NOWAIT 실패)과 40P01(교착으로 물림, 안전망)만 50ms·150ms 뒤 최대 두 번 재시도하고, 세 번째 실패와 다른 오류는 그대로 전달한다. 다른 이슈 턴과 검토 단계는 건드리지 않는다.

후속 대화 API·읽기 모델은 cancelled 메시지 Send again, Stop route/응답, `refs.answer_for` 메시지의 전달 표시와 Codex Stop 뒤 카드 숨김을 연결한다. Done·Stop이 로컬에서 확정한 뒤 같은 세션의 대기 메시지를 이어 보내는 `startNextQueuedTurn` 호출은 대화 API WP가 연결한다. Bridge API는 stopped run에 prepared로 남은 `agent_cancel`도 lease할 수 있어야 한다(Codex 진행 중 취소에 필요). Bridge API의 대화 run lease는 run을 잡은 뒤 Action을 잠그면 안 된다(Done은 Action→run). 답/취소의 실제 전달은 lease가 먼저다. 답이 prepared일 때 프로세스가 죽어 요청이 닫힌 경우를 `failed/agent_error`로 보내면 `step_not_calling`이며, 이 요청 종료 reason과 정산 경로는 후속 bridge WP가 정의해야 한다. 로컬 비밀값 주입과 Claude Code deny 닫기 모드 resume도 후속 구현이다. answered_question은 pending_question과 함께 V08 보관 기한 대상이다. PG 시험은 작성만 했으며 실제 잠금/교착 검증은 코디네이터에게 인계한다.

## 11. Bridge 서버 API (OA D2a)

`20261118000000_bridge_commands.sql`, `lib/bridge/`와 `/api/v1/bridge/{register,commands,ack,events,heartbeat}`가 D1c의 prepared 단계를 로컬 bridge에 연결한다. 새 DTO는 `contract.ts` 끝 `// --- D2a ---`의 `bridgeV1*`이며 기존 bridge 뼈대/v1 계약은 그대로다. 이 서버 구현의 검증 범위는 단위·route·PGlite fixture다. Mac 프로세스 실행·실제 provider·지연 실측은 D2b/D3a/D3b가, PostgreSQL 잠금 경합은 코디네이터가 확인한다.

- **자격:** 모든 route는 기존 Bearer 또는 같은 출처 쿠키 인증 → 본문 읽기·파싱 → 기기 확인 순서다. register 외 네 route는 `X-Taskforce-Bridge-Secret`도 요구한다. 등록은 32바이트 난수의 base64url secret을 한 번 응답하고 SHA-256만 저장한다. `device_ref=sha256(user_id + ':' + device_id)`라 계정별로 분리된다. 앱은 hash 열을 읽지 못한다. 행 없음/남의 기기는 404, secret 불일치는 401, revoked는 403이며 기존 v1 오류 코드만 쓴다.
- **등록·폐기:** adapter 보고는 설치·버전·로그인 상태·managed settings뿐이고 verified 권한은 서버 registry가 정한다. 연결 생성은 명시적 `connect`에서만, 같은 bridge+adapter의 revoked 아닌 연결은 하나다. 같은 기기 재등록은 secret 회전, 폐기한 기기는 `reactivate:true`가 필요하며 옛 세션은 closed로 남는다. DELETE는 사용자 인증만으로 다른 기기를 폐기한다. 살아 있는 로그인 세션의 재등록까지 막는 수단은 아니다. 등록은 시간당 사용자별 20회다. 새 기기 등록과 폐기한 기기의 재활성화는 사용자 active bridge가 10개 이상이면 HTTP 409(`conflict`, message=`too_many_bridges`)로 거절한다. 이미 active인 같은 기기의 secret 회전은 허용한다. D2b·D4a는 10개가 찼을 때 오래된 Mac을 폐기할 화면을 제공해야 한다. events·ack·commands는 기기별 각각 분당 120·240·90회이며 초과하면 429와 Retry-After를 반환한다. 폐기한 진행 중 task는 external 세션도 포함해 cancelled로 정리해 live 한도를 해제하고 last_live_state를 보존한다. 응답의 cancel=requested_only와 task의 cancel_requested_at·last_live_state는 외부 프로세스가 아직 돌고 있을 수 있음을 남긴다. 중단 범위는 기존 registry의 cancel_scope로 표시한다. 재활성화 뒤에도 옛 closed 세션의 사건·정산을 받을 수 있다. 이는 새 턴의 전달 허용이나 프로세스 종료 증명이 아니며, 기존 task/turn/intent의 reducer 조건을 그대로 적용한다.
- **명령과 글:** agent message/answer/cancel 단계가 prepared가 되는 같은 트랜잭션의 트리거가 `bridge_commands`를 한 번 넣는다. 표는 경로·cursor·lease/outcome 시각만 보관하고 상태는 `execution_steps`에서 계산한다. 목록·Realtime에는 글이 없고 lease 응답에서만 보관 기한 안의 메시지를 읽는다. 답의 자유 글도 `answer_message_id`로 읽으며 로컬 비밀값은 `answered_locally` 표식만 있다. 답 내용이 만료됐으면 expired로 거두고 task가 running일 때만 질문 카드를 복원한다. unreachable 등 다른 task 상태는 보존한다.
- **lease:** 새 message/answer만 기존 실행 플래그·adapterEnabled·현재 registry 등급/정책·actor·global/provider/mode controls·message tool을 다시 확인한다. 꺼진 adapter의 응답 이유는 `adapter_disabled`다. calling·intent·lease_owner/expiry·명령 leased_at을 원자 기록하며 대화 run을 waiting_approval로 바꾸지 않는다. 같은 lease 재요청도 현재 gate를 다시 확인한다. 닫혔으면 쓰기 없이 stale이며, 열렸으면 payload와 만료 시각을 연장 없이 replay한다. bridge는 원장으로 실행 여부를 판단한다. 아직 lease되지 않은 메시지의 전달 기한이 지났으면 단계/task failed, 메시지 expired로 거둔다. cancel은 stopped run과 닫힌 새 전달 gate에서도 가능하다.
- **결과 확인:** lease 330초가 지나면 unknown_outcome/readbacks가 되며 새 명령·단계·intent를 만들지 않는다. `received`는 기존 단계만 called, `not_received`는 반드시 `process_ended:true`여야 하며 단계는 failed(reason=not_received)로 정산하고 outcome/outcome_at을 기록한다. 메시지 명령의 task·메시지는 task가 dispatched 또는 unreachable일 때만 실패/미전달로 바꾸며, Stop 뒤 cancelled 등 다른 상태는 그대로 둔다. 소유 명령의 stale readback은 lease된 적이 있고 아직 정산 전일 때만 outcome_at을 남긴다. lease 전 또는 이미 정산된 명령은 변경하지 않는다. 단계가 lease·다시 붙임으로 calling에 들어가면 outcome과 outcome_at을 비워, 다시 만료될 때 readbacks에 다시 나오게 한다. 답 명령은 열린 run의 중단 요청이 없을 때 카드를 복원한다. `unknown`은 판정을 유보한다. outcome_at이 있는 readback은 긴 대기를 즉시 끝내는 항목에서 제외한다. cancel은 readback 대신 멱등 중단을 다시 시도하고 complete한다. `request_closed`는 lease된 답만 닫으며 카드 복원 없이 abandoned_question을 남긴다. 모르는 kind의 prepared 명령은 decline/unsupported로 거둔다.
- **사건:** 사용자·세션·연결의 bridge와 task/turn을 대조한 뒤 기존 `apply_agent_event`를 재사용한다. 같은 bridge가 보유한 unknown 단계만 calling으로 다시 붙여 원래 event_id를 적용하며 재dispatch하지 않는다. 원장의 중복 범위는 run+external_event_id다. 결정적 거절은 상태로 반환하고, 일시 실패는 retry 목록에 넣으며 같은 세션의 뒤 사건도 보류한다. 사건 본문은 1MB/100개, text는 UTF-8 32KB가 상한이고 payload에 글을 넣지 않는다. 사건은 개별 검증해 잘못된 사건만 rejected로 반환한다.
- **heartbeat·cron:** 30초마다 heartbeat를 보내며 같은 bridge의 마지막 heartbeat가 5초 이내면 잠금·쓰기·kick 없이 지난 결과와 throttled:true를 돌려준다. 지난 결과는 서버 전용 heartbeat_result 메타데이터 열에 보관한다. 90초 누락 시 bound 세션과 진행 중 작업만 unreachable이다. idle과 lease 전 dispatched는 그대로다. 복귀는 세션만 bound로 하고 task는 원래 사건 재생/reconcile을 기다린다. process_alive인 동일 bridge의 calling lease만 연장한다. 끊김·단계 lease sweep은 SQL db_now()를 기준으로 삼는다. 끊김 sweep은 bridge별 하위 트랜잭션에 오류를 가두고 실패마다 bridge id만 WARNING에 남긴다. 내부 결과의 failure_count를 TS sweep.errors에 합산하며 실패 집계 행은 unreachable 수에서 제외한다. 끊김 감지·대화 단계 lease 만료·gate 재개는 execution 플래그 조기 반환 전에 각각 실패를 가둬 실행한다. retention은 끝난 명령만 30일 후 지우며 calling/unknown은 남긴다.
- **자동 전달:** 턴 종료/확정 실패 뒤 ⓪, heartbeat 복귀 ①, 연결 active·로그인 복귀 ②는 FIFO 머리가 queued일 때만 SQL commit 뒤 시작한다. kick은 SQL이 고른 message id를 그대로 `startPinnedAgentMessage`에 넘기며 머리를 다시 선택하지 않는다. `start_agent_turn_auto`가 잠금 안에서 자동 시작 자격을 다시 검사하므로 그 사이 실패한 메시지는 재시도하지 않는다. 지워진 Action은 처리용 칩에서만 제외하며 원래 selected는 보존한다. 시작 결과가 not_found·already_dispatched이면 `mark_agent_message_not_sent_auto`가 queued일 때만 이유를 기록하여 동시 실패 이유를 덮어쓰지 않는다. not_sent는 gate 계열(write_gate_closed·not_connected·adapter_disabled)만 ③에서 connectionContext·databaseGatesOpen·adapter 플래그·bridge 보고를 다시 확인해 재개한다. gate로 거둔 ack는 kick하지 않는다. not_received·unsupported·접수 전 실패(sign_in_needed·usage_limited·spawn_failed 등)는 사용자 Send again을 기다리고 뒤 메시지도 FIFO대로 기다린다. 세션 없는 대화의 머리도 대상으로 하며 selected의 added 칩을 보존한다. external 세션·만료 메시지는 제외하고 실패는 다음 heartbeat/sweep에서 복구한다. Resume here ④와 Stop/Done 로컬 확정 뒤 호출은 D1d다. `turns.ts`는 수정하지 않는다.
- **자동 시작 재확인(F1s 항목 6):** `start_agent_turn_auto`의 재확인은 queued 또는 gate 이유 not_sent를 받는다. ⓪①②가 queued 머리를 고른 뒤 다른 경로가 같은 메시지를 gate 이유 not_sent로 바꾸는 좁은 경합에서는 그 메시지를 시작하지만 전달은 일어나지 않는다 — 정본 gate는 lease이고 lease 재확인(연결 · 실행 주체 · 통제 · 도구)이 `not_connected` · `write_gate_closed`로 되돌린다. 만료한 메시지의 lease 회수(`expired`)는 상태만 `expired`로 두고 `delivery_reason`을 쓰지 않는다(null, 20261127000000).
- **기기 이름(OA F1s):** `register` · `heartbeat` 본문의 선택 필드 `device_name`(원문 ≤ 256 코드 포인트, 넘으면 400)을 `normalizeDeviceName`(NFC · 제어 · 서식 · 양방향 문자 제거 · 공백 하나 · 글자소 단위 64 코드 포인트)으로 정규화해 새 SQL `set_bridge_device_name`으로 `bridges.device_name`에 쓴다(`register_bridge` · `bridge_heartbeat`는 교체하지 않는다. 스로틀 응답에서도 쓴다). 같은 이름이면 SQL이 행을 잡지 않는다. 쓰기 실패는 삼키고 로그에는 `bridge_device_name_failed`만 남긴다. 이름은 개인정보라 로그 · 지표 · 오류 문구 · AI 입력에 넣지 않고, 그 Mac의 폐기(트리거 `bridges_clear_device_name`)와 계정 삭제 때 지운다. 앱은 열 단위 select로 자기 행만 읽는다. 새 플래그 · 지표 type 0. Mac이 이름을 싣는 F1m은 F1s 운영 배포와 처리방침 갱신 시행 뒤에만 낸다(옛 서버는 모르는 키를 400으로 거절한다).
- **잠금:** 메시지→세션→run→task→step→명령 순서, bridge heartbeat/폐기/sweep은 bridge를 맨 앞에서 no-key-update로 잡는다. lease는 Action을 잠그지 않는다(Done은 Action→run). 작업 행을 한 트랜잭션에서 두 번 갱신하면 PostgreSQL이 FK(세션·메시지)를 다시 확인하며 KEY SHARE를 기다리므로(15장), 앞 순서 행을 기다릴 수 없는 Done·폐기는 그 둘을 NOWAIT로 먼저 쥔다. 명령은 bridge/step 복합 FK만 두고 session/task FK는 두지 않는다. 트리거는 세션/task를 잠그거나 쓰지 않는다. heartbeat 세션 잠금은 bound·unreachable, run·task 잠금은 진행 중 또는 보고된 task에 한정하고 연결은 register 포함 no-key-update다. unknown/missing id는 잠금 없이 조회한다. 마이그레이션은 bridges·rate_limit_events의 ACCESS EXCLUSIVE NOWAIT 잠금을 먼저 확보한다. 실제 경합은 PG P1–P16 작성 시험으로 코디네이터가 확인한다. 신규 등록·재활성화는 사용자별 advisory lock으로 열 번째 슬롯을 직렬화한다.
- **D2b 인계:** 재접속 후 lease 전에 heartbeat, lease 전 활동 사건 금지. ack replay는 로컬 원장으로 복구한다. Claude Code `close_before`가 있으면 다음 메시지 전에 닫기 모드 resume을 수행한다. Codex clientUserMessageId는 marker, external_task_id는 턴마다 다르다. synthetic assistant는 접수가 아니다. outbox는 계정 epoch별이며 인증 실패에 지우지 않는다. device_id는 128비트 이상의 무작위 값이며 device_id·secret은 계정별 Keychain ThisDeviceOnly로 저장하고 동기화하지 않는다. 비밀값은 요청/디스크/로그에 싣지 않는다. Realtime INSERT 구독과 `wait=25` 긴 대기(2초 재확인, abort 지원)를 사용하고 heartbeat tasks에 원장이 아는 모든 작업을 보낸다. Realtime DELETE는 RLS 필터 없이 PK만 전달되는 기존 표의 특성이 같으므로 삭제 통지를 행 읽기 권한으로 해석하지 않는다. 턴 중 앱 재시작 방지는 D2b다.

상태 줄 재시도는 기존 `execution_events`의 글 없는 lifecycle 기록(`bridge_restored`/`bridge_unreachable`, `fanout_pending`)으로 복구한다. heartbeat/sweep은 기록과 상태 전이를 같은 SQL 트랜잭션에 남기고, TS는 사용자·bridge 범위를 명시하고 type=agent 및 payload->>fanout_pending=true 부분 색인과 일치하는 조건으로 조회한다. 원래 task/turn과 멱등 event id로 대화 줄을 모두 쓴 뒤 pending을 해제한다. 정산 응답 유실/부분 fanout 실패의 동일 op 재시도도 기존 outcome을 확인해 누락된 줄을 복구한다. 한도 때문에 뒤 항목이 막히지 않도록 commands는 새 cursor를 replay보다 먼저, readbacks는 아직 결과를 보고하지 않은 것만 고른다. gate 재개 후보는 세션의 FIFO 머리를 유지하면서 서버 분마다 제한된 후보 창을 순환한다.

`bridgeOwnsSession(userId, bridgeId, deviceSecret, sessionId)`는 로컬 비밀값 답 증명용으로, OA F2의 `lib/bridge/answer-local.ts`가 TS 앞단 거름으로 쓴다(권위는 SQL이 같은 트랜잭션에서 다시 확인, 14장). `authenticateBridge`는 D3c-2 정책 API용 export다. D1d 읽기 모델은 unreachable+prepared를 queued로 표시하고(`delivery_expires_at`이 지나도 DB 행이 `dispatched/prepared`인 동안은 그대로다 — 표시만 `expired`로 바꾸면 Send again이 `not_eligible`이 되므로 읽기 모델은 시계를 보지 않고, OA F3이 1분 cron에서 잠금 아래 회수해 DB를 `expired`로 만든다, 15장) not_received/expired와 Send again을 연결한다. 새 서버 플래그·metric type은 없으며 ONE-TF-11의 서버 시각 원천은 명령 created_at/leased_at/outcome_at과 step 사건이다. 실제 지연 수치를 이 fixture 결과로 대체하지 않는다.

**전달 활성화 병합 조건:** 세션 단위 FIFO는 not_received·unsupported·접수 전 실패 머리 때문에 같은 세션의 다른 대화까지 기다리게 한다(D1c-1). 사용자가 이를 푸는 Send again·Stop은 D1d 대화 API에 있으므로 **D1d가 병합되기 전에는 bridge 전달을 켜지 않는다**. D1d 병합 뒤에도 운영 플래그·DB 스위치는 닫힌 상태를 유지한다. “보내지 못한 메시지 뒤에서 기다림” 표시는 D4a에 인계한다. 요청 한도는 현재 사건 행과 bridge 전용 색인으로 계산하며, 공개 전 분당 집계 행으로 바꾸는 작업을 인계한다.

### 11-1. Mac bridge (D2b)

위 서버 API의 Mac 쪽 상대다. 핵심은 `apple/Packages/TaskforceKit/Sources/TaskforceKit/Bridge/`(모두 `#if os(macOS)`, iOS 빌드는 그대로)에 있고, 앱(`apple/Taskforce/Mac/Bridge/`)은 연결만 한다. DTO는 `BridgeV1Contracts.swift`(`bridgeV1*`의 짝, 옛 `AgentBridgeContracts.swift` 뼈대는 쓰지 않는다). 계약 JSON은 `Tests/TaskforceKitTests/Fixtures/bridge-v1/*.json` 하나를 Swift 시험과 서버 `src/lib/bridge/swift-fixtures.test.ts`가 함께 읽는다. 실제 `claude`·`codex` 실행은 D3a·D3b가 `AgentProcess`를 구현해 붙인다. D2b는 가짜 agent(`FakeAgentProcess`, Debug 전용)로만 돈다. 이때 새 세션의 작업 폴더도 D4a가 정하기 전까지 가짜 값(`workspace-fake`)이고, 실제 빌드는 `WorkspaceResolver`가 없으면 짐작하지 않고 `spawn_failed`로 알린다.

- **원칙:** bridge는 전송이고 판단은 서버다. 등급·gate·상태 전이를 계산하지 않고 "내가 실제로 무엇을 했는가"만 원장에 적고 보고한다. 명령 하나는 실행 한 번이다: 원장이 `start_intent` 이상이면 lease도 실행도 다시 하지 않는다. 모든 외부 효과(lease 요청·프로세스 시작·중단·ack) 앞에 의도를 원장에 commit한다. 사용자 메시지 글은 디스크에 쓰지 않고(lease `replay`가 다시 준다) 비밀값 답은 메모리(`LocalSecretAnswers`)에만 있다.
- **원장:** 시스템 SQLite(WAL·synchronous=FULL), `<Application Support>/<번들 id>/Bridge/v1/<파티션>/ledger.sqlite`, 폴더 0700·파일 0600. 파티션 = `sha256(API origin + 사용자 id)` 앞 32자라 계정·서버(로컬/운영)가 섞이지 않는다. 열 때 `quick_check`에 실패하면 파일을 `ledger.sqlite.corrupt-<epoch>`로 옮기고(지우지 않는다) 빈 원장으로 시작하며, 그 뒤 모르는 명령의 결과 확인은 모두 `unknown`이다. 끝난 명령·죽은 outbox 행·보내지 못한 사건은 7일, 잘린 글 전체(View full)는 30일, 파티션당 50MB. 계정 삭제 성공 시 그 파티션 폴더와 Keychain 항목을 지운다.
- **자격:** device_id는 파티션마다 만든 32바이트 난수(43자), secret은 등록 응답이 준 43자 base64url이며 모양을 확인한 뒤에만 저장한다. 둘 다 Keychain generic password(service `taskforce.bridge`, `ThisDeviceOnly`·동기화 안 함·데이터 보호 Keychain·앱 전용 접근 그룹 `$(AppIdentifierPrefix)$(APP_BUNDLE_ID)`로 고정, App Group이 아니다)다. 서명 안 된 빌드는 팀 접두가 비어 그룹을 지정하지 않는다. 등록은 secret이 없을 때·401 회복·404 회복·사용자가 Connect를 눌렀을 때만 하고 실행마다 하지 않는다. `reactivate: true`는 사용자 행동(Reconnect this Mac)에서만 보낸다.
- **명령 처리:** 깨우기(Realtime `bridge_commands` INSERT, 끊기면 `wait=25` 긴 대기) → 결과 확인 → cancel → answer → message 순으로 처리한다. 같은 세션에 살아 있는 실행이 있으면 lease도 하지 않는다(writer 하나). 모르는 kind는 `decline`, payload의 모르는 값(access·policy_mode·question_kind)은 띄우지 않고 `readback not_received, process_ended: true`, 모르는 cancel 범위는 더 넓게(`turn_and_processes`) 멈춘다. adapter가 없거나 설치 안 됨·버전 밖·로그인 안 됨이면 `failed`로 정확한 이유(`spawn_failed`·`version_unsupported`·`sign_in_needed`)를 보낸다. lease 응답은 `leased`·`replay`(원장에 `start_intent`가 없을 때만 첫 실행), `withdrawn`(기록만), `stale/heartbeat_first`·`policy_changed`(한 번 다시), 그 밖의 `stale`(기록만), 404(`gone`)로 갈린다.
- **결과 확인:** 서버가 결과를 모르는 명령(lease 만료)은 원장·프로세스·접수 신호로 답한다(`Reconcile`, 순수 함수). `not_received`는 앞 프로세스가 끝난 것을 확인한 뒤에만 보내고 살아 있으면 보내지 않는다. 접수 신호가 있으면 outbox를 먼저 재생하고(서버가 다시 붙인다) 그래도 남을 때 `received`, 접수 신호 없이 살아 있으면 `unknown`을 한 번만 보고한다. 원장을 잃었거나 이 Mac이 모르는 명령은 `unknown`만 보내고 실행하지 않는다.
- **outbox:** 사건은 먼저 적고 보낸다. 묶음은 사건 ≤ 100개·본문 ≤ 900KB·세션 순서 유지, 지우는 신호는 응답의 `accepted_event_ids`뿐이다. `retry_event_ids`는 남기고 같은 세션의 뒤 사건도 보류, `rejected`는 dead-letter, 묶음 400은 반으로 나눠 다시 보낸다. 401·403·404·429·5xx에는 지우지 않는다. 글은 UTF-8 32KB로 유니코드 스칼라 경계에서 자르고 전체는 원장에, 질문은 상한(4개·선택지 10개·길이)에 맞춰 자르거나(원래 선택지 값은 원장에 두고 답은 원래 값으로 되돌린다) 담을 수 없으면 그 요청을 거절로 닫는다.
- **heartbeat·한도:** 30초(±2초)마다, 시작·깨어남·연결 복귀·자격 회복 뒤와 lease 전(마지막 성공이 90초보다 오래됐을 때)에는 바로 보낸다. `tasks`는 원장이 아는 끝나지 않은 작업 전부(50개 우선순위: 살아 있음 → 질문 대기 → 최근)이고 `app_version`·`adapters`는 시작 때와 probe 결과가 바뀔 때만 싣는다(키를 뺀다, null 금지). 클라이언트 예산은 서버 한도의 80%(events 96·ack 192·poll 72 /분), 429는 `Retry-After`(없거나 못 읽으면 30초) 동안 그 route만 멈춘다. 목록 사이 최소 2초, 돌아온 항목이 모두 처리했거나 미룬 것이면 5초.
- **종료·재시작·꺼짐:** 실행 중인 턴(또는 전달하지 않은 비밀값 답)이 있으면 종료 때 확인 창("Quit Taskforce?" / "Running agent turns will stop." / Quit·Cancel)을 띄우고, Quit이면 턴을 중단하고 끝남을 본 턴은 `cancelled` 사건으로 알린 뒤 outbox를 최대 3초 비우고 종료한다. **확인 뒤 앱이 기다리는 시간의 상한(OA D4a2-11, 보안 9차 F7):** 파티션마다 3초 유예 + 유예 안에 끝나지 않은 **세션마다** 최대 16초(`closeTimeout` 10초 + 시작 정산 6초, 세션 순서대로 이어서) + outbox 3초다 — 대기는 세션 수만큼 쌓인다. 확인 창 문구는 시간을 약속하지 않으므로 그대로 둔다(대기 중 표시 · 세션 병렬 끝내기는 실사용에서 대기가 문제가 되면 후속). 강제 종료로 남은 고아 프로세스는 (pid, 시작 시각, marker)로 찾아 재시작 때 끝내고 원장으로 정산한다(접수 뒤였으면 `cancelled`). 새 실행은 lease가 새로 성공한 명령에만 있다. 업데이트 재시작은 Sparkle 2.10.0이 `updaterShouldRelaunchApplication`에서 false를 받으면 설치를 접기 때문에 그 질문은 true로 두고 `shouldPostponeRelaunchForUpdate`에서 한가해질 때까지 미룬다. `BRIDGE_ENABLED`(Info.plist `TaskforceBridgeEnabled` ← 빌드 설정 `TF_BRIDGE_ENABLED`, 모든 구성 기본 NO, Debug는 실행 인자 `-TF_BRIDGE YES`도 필요)가 꺼진 빌드는 네트워크·프로세스가 0이고, 꺼졌는데 원장에 할 일이 남았으면 **마무리 모드**(새 전달 0·새 등록 0, 사건·cancel·결과 확인·heartbeat는 계속)로 올라 일이 끝나면 멈춘다.
- **작업 폴더 · 터미널 · 잊기 (OA D4a-2):** 작업 폴더는 **프로젝트마다 한 번** 사용자가 고른다(Assistant 창의 첫 보내기 직전, 세션이 아직 없고 대상이 이 Mac일 때. Ungrouped는 그 대화마다). 고른 폴더는 이 계정 파티션 폴더의 `workspaces.json`(0600, 원자적 쓰기, 계정 삭제가 파티션째 지움)에 realpath로 적힌다. 받아 주지 않는 폴더: `/` · 홈 자체와 조상 · `~/Library` · 앱 데이터 폴더 · 앱 번들(`/Applications` 밖에서 실행해도, 그리고 cwd별(`~/.claude/projects/<cwd>`)로 두고 `--add-dir` · `--settings`는 이어받을 때 되살아나지 않으므로, adapter가 띄운 세션 cwd(`ClaudeSessionFolder.cwd`, 띄우기와 같은 길로 구한다)에서 이어받고 작업 폴더만 다시 준다 (`--settings` · `--mcp-config`는 주지 없거나(잊었거나 지웠다) 기호 링크이면 열지 않는다(미리 조건 false, 서버 호출 0), 이 Mac이 아직 돌고 있다고 보는 턴이나 중단을 증명하지 못한(`unproven`) 턴이 있으면 `terminalTarget`이 nil이다(서버 `busy`에만 기대지 않는다). 10분 넘은 파일은 앱 시작과 새로 열 때 지우는데, 폴더를 한 번 열어(`O_NOFOLLOW`) 내 폴더인지 확인한 뒤 그 fd 기준으로만 지운다(`Terminal`이 기호 링크로 바뀌어도 가리키는 곳의 파일을 지우지 않는다). 계정 삭제는 `.command` 파일도 모두 지우고 그 파티션의 등록부 캐시를 비우며, 지워진 파티션 폴더에는 등록부가 쓰지 않는다(늦은 쓰기가 폴더를 되살리지 못한다). 세션 핀을 저장하지 못하면 작업 폴더를 `nil`로 닫는다(핀 없이 띄우면 다음 턴이 거절된다). 겹치는 폴더는 **상태 없는 두 규칙**으로 막는다(계약 13.13): ① 등록(폴더 고르기 · 바꾸기)은 다른 프로젝트의 지금 폴더하고만 겹침을 본다 — 그래서 프로젝트 폴더를 상위로 바꾸는 것은 옛 세션 핀과 상관없이 된다. ② 턴 시작은 세션 핀이 그 폴더이고 어떤 프로젝트의 지금 폴더와도 겹치지 않을 때만 띄운다(런타임이 접수 전에 `allowsTurn`을 묻고 아니면 기존 "Session didn't start"(`spawn_failed`)로 실패시킨다, 새 문구 없음; 핀을 모르면(읽지 못한 표 포함) 띄우지 않는다). 그래서 프로젝트 폴더를 겹치는 곳으로 바꾸면 그 프로젝트의 옛 세션은 이어 갈 수 없다(새 세션을 연다). 세션 핀은 풀지 않는다(수명 관리 없음, 계정 삭제 정리만). ③ 턴 시작은 이어서 **이 파티션의 다른 세션이 살아 있고 그 폴더가 이 폴더와 겹치면**(조상 · 자손, 같은 실제 경로는 아니다) 띄우지 않는다(같은 "Session didn't start", 새 문구 없음) — 프로젝트 없는 세션끼리도, 프로젝트 세션과 프로젝트 없는 세션 사이에서도 겹치는 두 폴더에서 세션이 동시에 돌 수 없다(경로 lease 키가 갈리는 것을 막는다). 살아 있음은 런타임의 기존 실행 상태다: 원장 `alive`(증명 못 한 중단 `unproven`은 늘 `alive`와 함께 있다) · 감독 중 · 확인 안 된 고아 · adapter 닫기 실행 · adapter의 세션 실행이 끝나지 않았거나 모름 · 다른 턴의 시작 예약. 상태를 읽지 못하거나 살아 있는 실행의 폴더를 모르면 막는다(fail-closed). 검사와 예약은 한 actor 단계(`reserveStart`, 사이에 await 없음)라 겹치는 두 턴이 둘 다 통과할 수 없다. 이미 도는 세션에 답을 주는 길은 기존 실행을 잇는 것이라 그대로다. **Resume here** 전 검사기는 이 Mac 상태가 묶은 Claude 세션 id로 프로세스를 훑는다(메인 스레드 밖, 못 찾음은 증명이 아니라 확인 카드는 늘 거친다). **중단 `.unknown`:** adapter가 신호를 보냈다고 증명하지 못하면(잠금을 끝내지 못함 · 정체 없음 · 고아를 끝내지 못함) 런타임은 `cancel_state`를 `unproven`으로 두고 실행을 그대로 감독 · 잠그며 ack는 `complete(sent)` 그대로다. **`forgetSession`:** 폐기(revoke)될 때 원장의 모든 세션을 adapter가 잊는다(비밀값 가리개 · 비밀 항목, 메모리뿐. 그 세션에 아직 프로세스가 있거나 끝난 턴의 마지막 출력이 정산되는 중이면 가리개는 남기고, 조용해지는 순간 이어서 지운다). - **인계:** D3a(`ClaudeCodeProcess`)·D3b(Codex)는 `AgentProcess`의 `probe`·`startTurn`·`deliverAnswer`·`closeRequest`·`interrupt`·`liveness`·`terminateOrphan`·`readback`을 구현하고, 접수 신호(`accepted`)를 언제 내는지는 adapter가 정한다. U2·D4a: 상태(`revoked`·`tooManyBridges`·`credentialRejected`·오프라인) 표시, Connect, Reconnect this Mac, 오래된 Mac 폐기 목록(10개 상한), `WorkspaceResolver`, `LocalSecretAnswers`에 비밀값 넣기, View full(원장 `full_texts`). 문서 정정(코디네이터): 아키텍처 9.3의 "모르는 kind는 `unsupported` 사건"은 "lease 전 `decline`"으로, "앱 종료 → 에이전트 프로세스 사망"은 "확인 종료는 중단, 강제 종료의 고아는 재시작 때 끝냄"으로, 런타임 12장 outbox 24시간은 "같은 파티션이면 7일까지 보낸다"로, 계획 D2b 행의 파일 위치는 Kit `Bridge/`로.
- **검토 반영(계약 7장):** (A) 한 task의 외부 작업 id는 처음 묶인 값을 바꾸지 않는다(답으로 새 프로세스를 띄워도, 서버는 다른 값을 final `conflict`로 버린다). 2xx인데 본문을 못 읽으면 일시 실패(물러섰다 다시, 행 유지)이고 묶음을 쪼개거나 dead-letter하는 것은 진짜 400뿐이다. 끝을 증명하지 못한 고아(`liveness == .unknown`)는 "확인 안 된 고아"다: heartbeat `process_alive` false, 결과 확인에는 `unknown` 한 번, Sparkle 재시작을 막지 않되 같은 세션의 다음 실행은 계속 막는다. `reactivate()`가 성공하면 루프를 다시 시작한다. (B) 마무리 모드는 할 일이 없으면 요청 없이 멈추고 호스트가 런타임을 놓는다. 원장 분실 · 기록 없음의 `declined` 기록과 `unknown` ack, run 시작(`start_intent`)의 task · 명령 두 행은 각각 한 트랜잭션이다. 나가는 값은 정리기 하나(`OutgoingValues`)가 서버 zod 한도(`sanitizer-limits.json`)에 맞춘다: `workspace_ref` 비어 있지 않음 · 500자, 외부 작업 · 세션 id 1–200자(자르지 않고 거절), 산출물 payload 4096바이트, NUL 제거, adapter version 50자, probe 보고가 없는 adapter는 connect하지 않는다. (C) 서버 숫자는 디코딩과 `recover()`에서 범위를 자른다(heartbeat 5–3600초 · unreachable 30–3600초 · long poll 1–25초, 음수 cursor는 건너뛰고 next_cursor는 본 cursor까지만). 서버가 준 작업 폴더는 `WorkspaceResolver.authorize`가 인정한 값(이 Mac이 고른 폴더)일 때만 쓰고 아니면 `not_received`로 거절하며, 재개 세션 id는 `^[A-Za-z0-9_-]{1,128}$`(맨 앞 `-` 제외)만 받는다. 종료 · 한가한 종료 · 계정 삭제는 중단 신호 뒤 3초 유예 다음에도 남은 실행을 `terminateOrphan`으로 끝낸다(턴이 `idle`이어도 프로세스가 남아 있으면 확인 창 없이 끝내고 종료). 계정 삭제는 끝낸 뒤에 원장 폴더 · Keychain을 지우고 지운 결과를 알린다. (D) WAL · SHM · 잠금 파일도 0600, 끝난 task · 질문 원래 값 · 세션 번호표 · 7일 지난 격리 파일을 정리, 자동 등록은 1시간 10회 예산과 점점 길어지는 간격(성공해도 초기화하지 않음), 401은 요청이 쓴 secret이 이미 낡았으면 다시 등록하지 않고 새 secret으로 재시도, bridge 요청은 https 또는 loopback만 · 리다이렉트 거절 · 응답 4MB 상한, 하위 프로세스 환경은 `HOME`·`PATH`·`LANG`·`USER`만, 가짜 agent는 서버 주소가 loopback일 때만, lease payload의 id · task · 세션이 lease한 항목과 다르면 거절하고 24시간 전달 창이 지난 명령은 띄우지 않는다, 더 새 원장 스키마는 손상과 구분해 열지도 옮기지도 않는다, 원장은 파티션 폴더의 `flock`으로 한 곳에서만 연다. **D4a 인계:** 비밀값 답은 질문 카드를 보인 때의 파티션에 묶어 넣는다(계정이 바뀐 뒤 다른 계정의 런타임에 들어가지 않게).
- **검토 반영 2(계약 8장):** Stop(cancel)은 24시간 전달 창의 적용을 받지 않는다: 언제 lease했든 돌고 있는 실행을 중단하고 `complete`로 정산한다(창은 message · answer의 `replay`에만). 모든 실행은 이 Mac이 승인한 작업 폴더가 있어야 한다: 서버가 폴더를 주지 않으면 재개(`external_session_id`)여도 `WorkspaceResolver`가 정하고, 없거나 비면 접수 전 `spawn_failed`다. 서버가 준 폴더는 resolver가 인정하거나 이 Mac이 그 세션에 기록한(`session_bound`) 값과 같을 때만 받는다. `AgentProcess`는 `workspaceRef == nil`이면 `startTurn` · `closeRequest`에서 `spawnFailed`를 던진다(D3a · D3b). marker는 UUID 모양만 adapter에 넘긴다. 답을 기다리던 task를 Stop으로 정산하면 원장도 `cancelled`로 닫고, 보관 정리는 살아 있지 않은 `dispatched` · `awaiting_answer` task도 7일 뒤 지운다. 응답 4MB 상한은 읽으면서 센다. 계정 삭제는 끝내지 못했거나 끝을 증명하지 못한 프로세스 수를 알리고(`CleanupResult.unterminatedProcesses`, 0이 아니면 `isComplete`가 false) 호스트는 런타임이 멈춰 있고 그 파티션이 다시 활성이 아닐 때(또는 마무리 모드)만 놓는다.

## 12. 대화 API v2 확장 (OA D1d-s)

`20261121000000_agent_conversation_api.sql`과 route 12개, 대화 handler 확장이다. 계약: Assistant 계약 v3 2–5장 · 8장. **운영 전달 gate는 닫힌 상태를 유지한다**. D2a와 통합되어 `prepared` 단계가 bridge 명령으로 이어지지만, 전달 활성화는 별도 작업이다.

### 12-1. gate

- 모든 새 route: `CONVERSATIONS_V2_ENABLED`가 꺼져 있으면 인증 · DB 전에 404. 에이전트 경로는 그 대화 · 세션 · 연결의 **adapter 플래그**도 켜져야 한다(꺼져 있으면 404): `AGENT_ADAPTER_CLAUDE_CODE_ENABLED`(기존) · **`AGENT_ADAPTER_CODEX_ENABLED`(새, 기본 꺼짐)**. 꺼진 adapter는 대상 목록에서 빠지고 만들기 · 보내기가 404라 Action · 세션 · run이 생기지 않는다. 이전에는 Codex가 플래그 없이 늘 켜져 있었다(B2 대화를 켜는 순간 열리는 fail-open이라 닫았다).
- **예외: 대화 Stop · 세션 Stop은 adapter 플래그와 무관하게 돈다**(롤백 규칙 — 새 전달 gate가 닫혀도 받기 · 멈추기는 계속 된다, `CONVERSATIONS_V2_ENABLED` route gate는 그대로). 멈춘 뒤 "다음 대기 메시지 시작"만 adapter 플래그와 `EXECUTION_ENABLED`를 따른다(꺼져 있으면 부르지 않는다).
- 인증은 `authenticateRequest`(Bearer + 쿠키, 쿠키 쓰기는 CSRF). 로그에는 이벤트 이름 · 오류 이름 · 코드만 남긴다(글 · 칩 id · 답 · 질문 0).

### 12-3. 전달 표시 계산 (`agentDeliveryView`, 순수 함수)

원문 메시지의 단계는 `task.step_id`(질문에 답하면 답 단계로 옮겨 간다)가 아니라 **그 메시지를 가리키는 최신 task의 `run_id` 안에서 `args->>'message_id'`가 그 메시지인 `agent_message` 단계 중 seq 최대**로 읽는다(run 구분 없는 seq 최댓값이면 옛 run의 실패가 새 run의 접수를 이긴다, 검토 반영 8-3)(검토 반영 7-4: 원문 `accepted` → 답 단계 실패여도 원문은 `accepted`, 답 메시지만 `not_sent`). 답 메시지는 그 답 단계(`args->>'answer_message_id'`)로 계산한다.

`cancelled` → `cancelled` · `refs.answer_for`(질문에 자유 글로 답한 메시지) → 답 단계가 `failed`면 `not_sent`(+ 단계 receipt 이유), `skipped`면 `cancelled`, 그 밖은 `answered` · `queued` + 후보 + 아직 안 고름 → `needs_referent`(제목 ≤ 3) · `queued`/`not_sent`/`expired` → 그 상태 + 이유 · `dispatched` → 단계 `prepared`/`calling` = `sent`, `called` = `accepted`, `unknown_outcome` = `unknown`, 그 밖 `not_sent`(방어). D2a 통합: 세션이 `unreachable`이고 단계가 `prepared`면 `queued`로 표시한다(OD-11). `calling` 이후의 전달 표시는 그대로 유지한다. 이유는 계약 9개 + SQL이 쓰는 8개 = 17개(`agentDeliveryReasonSchema`, 마이그레이션 문자열 정적 시험).

### 12-4. 새 SQL (서버 전용 invoker, service_role만 실행)

- `requeue_agent_messages(user, conversation, message_ids|null)`: 대상 상태만(`cancelled`는 끝 상태 · 결과 불명 `unknown_outcome` · 질문의 답 `refs.answer_for` 제외), 메시지를 id 순으로 `for update`. 이름을 준 id가 이 대화의 것이 아니면 `skipped/not_found`. **잠근 행의 id를 배열로 고정**해 그 행만 처리하고(일괄 호출의 두 번째 조회가 대상을 다시 고르면, 처음에 빠졌던 잠그지 않은 행이 섞여 들어 다른 요청이 재전송해 `dispatched`로 commit한 행을 `queued`로 덮는다 — 검토 반영 10-1), 갱신도 지금 `not_sent` · `expired`일 때만 한다.
- `open_agent_session_external` · `resume_agent_session_here`: 묶인 대화(id 순) → 세션 순으로 잠근 뒤 **세션을 잡은 직후 묶인 대화를 `for update nowait`로 한 번 더 확인한다**(검토 반영 7-2: 첫 조회와 세션 잠금 사이에 새 대화가 연결되고 다른 요청이 그 대화를 쥐면 서로 기다려 교착하므로 `55P03`으로 원자 실패, Stop과 같은 방식). 대화마다 `event` 줄("Opened in Terminal" · "Resumed here") + 지표. 진행 중 턴이 있으면 busy → `pending:` 세션 not_started → bound 아님 not_bound. 경로 lease 해제는 D3c-2가 `open_agent_session_external`에 건다.
- `start_agent_turn_auto(user, message, access, live_limit, action_ids, context_ids)`: 자동 시작(대기열 머리 · Resume here · Stop 뒤 · `queue_order` 뒤)의 입구 (검토 반영 8-1). TS가 고른 메시지 id를 그대로 받아 `route_agent_message`와 같은 순서로 그 메시지 행을 먼저 잠근 뒤 상태를 다시 읽는다 — `queued`이거나 `not_sent` + 이유가 gate 계열(`write_gate_closed` · `not_connected` · `adapter_disabled`)이면 같은 트랜잭션에서 `route_agent_message`를 부르고, 아니면 아무것도 하지 않고 `{status:'skipped'}`. 검사한 뒤 다른 요청이 상태를 바꿔도(앞 메시지가 만료돼 `not_sent/spawn_failed`가 머리가 되는 등) 낡은 상태로 새 회차를 만들지 않는다. 없는 · 남의 메시지는 `route_agent_message`의 `not_found` 그대로. **잠금 대상 고정(검토 반영 9-2)**: 메시지를 잠그기 전에 답 경로가 쓸 원문(질문을 낸 메시지) · 사건 기준을 한 번 읽어 두고, 잠금을 얻은 뒤 다시 읽어 달라졌으면(기다리는 사이 질문이 열리거나 닫힘) `route_agent_message`가 원문을 M 뒤에 잠그려다 (원문 → M 순으로 잠그는 다른 요청과) 교착하지 않도록 추가 잠금 전에 `40001`로 롤백한다. TS(`startPinnedAgentMessage` 외 D1d의 SQL 호출 전부)가 `40001` · `40P01` · `55P03`을 두 번까지 다시 부르고(`retryOnConflict`), 그래도 안 되면 handler가 409 `busy_retry`(교착 `40P01`도 500이 아니다). 래퍼가 읽고 `route_agent_message`가 읽기까지의 짧은 틈은 남는다 — 그때의 교착은 DB가 한쪽을 `40P01`로 끊고 같은 재시도 경로로 간다.
- `mark_agent_message_not_sent_auto(user, message, reason, from_gate)`: 자동 경로의 `not_sent` 표시(실행 kill switch 꺼짐 · 연결 · 등급 거절 · 진짜 `not_found` · `already_dispatched`)를 **메시지를 잠근 뒤 그때의 상태를 다시 보고** 한다 — 지금 `queued`일 때만 `mark_agent_message_not_sent_auto`를 부르고(`from_gate`가 참이면 gate 계열 이유의 `not_sent`도), 읽은 뒤 다른 요청이 전달 · `spawn_failed`로 만든 메시지의 이유는 덮지 않고 `{status:'skipped'}`(검토 반영 9-1). kill switch 꺼짐 표시는 `from_gate` 거짓(어떤 `not_sent`도 안 덮음).
- `answer_agent_question_recorded(…)`: D1c-2b `answer_agent_question`의 본문은 그대로 두고 그 결과가 `answered`일 때만 같은 트랜잭션에서 `question_answered`(kind · adapter만)를 쓴다 — `duplicate` · 잘못된 답 · 낡은 질문은 지표 0. `rename_agent_session(user, session, name)`: 실제로 바뀔 때만 `session_renamed`(adapter만); 같은 이름은 `unchanged`, 없거나 남의 세션은 `not_found`, 1–200자 밖이면 `22023`. 새 지표 다섯은 모두 상태 변경과 같은 트랜잭션이다(지표 insert가 실패하면 상태도 롤백). 자유 글 답(`route_agent_message`)은 지표 행이 없고 `/admin/metrics`가 답 단계로 센다(OA I-oa).
- 공통 metric 블록 **v2**를 글자 그대로 넣었다: type에 `message_resent` · `question_answered` · `session_renamed` · `session_opened_external` · `session_resumed` 추가. 앱이 직접 쓰는 type은 `app_opened` · `assistant_opened` 그대로.

### 12-7. 실행 kill switch 방어 (D2a 보안 검토 P1)

`EXECUTION_ENABLED`가 꺼져 있으면 에이전트 대상의 모든 전달 시작 경로(보내기 · Send again · referent · Resume here · Stop 뒤 다음 시작 · `queue_order` 뒤 다음 시작)가 턴을 시작하지 않고, 메시지(대기열 머리)를 기존 `mark_agent_message_not_sent_auto` 경로로 `not_sent`/`write_gate_closed`로 표시한다(HTTP 200, 보통 응답 모양). 꺼진 채 시작하면 전달될 수 없는 task · 단계 · 명령 · `agent_message_sent` 지표가 생기고, bridge가 거둔 것을 자동 계기가 다시 시작하는 끝없는 반복이 되기 때문이다. 확인은 `lib/agents/next-turn.ts`(`markWriteGateClosed` · `startNextAgentMessage`)와 `startAgentMessage`에 있고 `turns.ts`의 함수 본문은 바꾸지 않았다. DB 쪽 gate(`execution_controls` · 실행 주체 · 도구)는 여전히 bridge lease의 몫이다. **자동 시작 경로는 대기열 머리를 한 번만 고르고 그 id를 끝까지 고정한다**(`startNextAgentMessage` → D1d 자신의 시작 함수 `startPinnedAgentMessage` → SQL `start_agent_turn_auto`; `turns.ts`의 `startNextQueuedTurn`은 D1d 경로에서 쓰지 않는다 — 그 안의 머리 재선택이 만료 경합에서 실패한 `not_sent`를 시작했다). 시작 입력의 칩에서는 지워진 Action을 뺀다(저장된 `selected`는 그대로); 진짜 `not_found` · `already_dispatched`는 `mark_agent_message_not_sent_auto`로 대기열에서 뺀다. **표시는 지금 `queued`인 메시지만 한다 — SQL `mark_agent_message_not_sent_auto`가 메시지 잠금 안에서 현재 상태를 다시 보고 결정하며 TS가 미리 읽은 상태로 판단하지 않는다** — 이미 `not_sent`인 메시지의 이유(예: `spawn_failed`)는 덮어쓰지 않는다(검토 반영 7-1). 자동 시작 대상은 `queued`와 이유가 gate 계열인 `not_sent`뿐이라(`autoStartable`), 실패한 머리는 Send again 또는 Stop으로 풀 때까지 SQL FIFO(`queue_order`)가 뒤 메시지를 붙잡는다.

### 12-8. 다음 WP 인계

## 13. 승인 정책 · 경로 lease (OA D3c-2)

`20261123000000_agent_path_leases.sql`은 `20261121000000` 뒤에 적용한다. 공통 지표 블록 v3를 그대로 쓰며, CHECK 교체와 트리거 생성에 필요한 표와 `bridges`의 잠금을 처음에 NOWAIT로 확인한다. 새 서버 플래그는 없다. 초기 registry에서 Claude Code는 등급 없음, Codex는 `read_only`이므로 실제 쓰기 허용 증거는 아니다.

- `POST /api/v1/bridge/tool-decision`: 인증 → 64 KiB 이하 strict 본문 → 같은 기기 secret → 순수 결정표 → SQL 재검증 순서다. 명령·쓰기 본문을 저장하거나 로그에 남기지 않는다. 입력은 Bash·Edit/Write·Codex command/file-change 네 종류뿐이며, 응답은 `allow | deny | defer`, 정해진 reason, 필요한 parse·holder·카드 flag만 준다. `maxDuration=5`, `Cache-Control: no-store`. bridge별 600회/분은 결정 RPC 안에서 확인하고 초과는 `deny/rate_limited`로 기록한다.
- Manual에서도 작업 폴더 안 읽기 전용 단일 명령은 파서가 허용하면 자동 허용한다(사용자 결정 Q17). Manual 쓰기는 예약 후 승인 질문으로, Claude Code Auto/Full 쓰기는 lease 획득 후 허용한다. Codex Manual command는 최초 요청·읽기 action 종류·파서 허용을 모두 만족해야 한다. Codex Auto/Full 요청은 `defer`와 `runs_without_sandbox` 표시다. bridge 정적 판정이 먼저이며 서버에 명령 허용 목록은 없다.
- SQL은 사용자·bridge·adapter 귀속, 세션/run/task의 살아 있음, 정책 mode, 기존 DB gate와 workspace를 다시 확인한다. 정책 변경은 쓰기 없이 반환하고 TS가 한 번 다시 계산한다. 잠금 순서는 세션 공유 → run 공유 → task 공유 → 경로 열쇠 오름차순이며 Action은 잠그지 않는다. 잠금 대기 250ms 초과는 허용을 늘리지 않고 `defer/server_busy`로 내린다.
- `agent_path_leases` 열쇠는 사용자 × bridge × NFC 정규화·`ſ`→`s` 변환·ASCII 대소문자 접기를 한 절대 realpath다. 같은 run은 이어 쓰고 같은 세션의 다른 이슈도 양보한다. 여러 대상 중 하나가 다른 run의 것이면 이번 획득은 모두 롤백하고 그 holder의 waiter만 추가한다(중복 없이 최대 20). 응답의 `holder`에는 Action 번호·상대 경로만 있고 run id는 없다.
- **12장의 승인 답 409는 이 WP에서 열린다.** Assistant와 Review 모두 `POST /api/v2/agent-tasks/{id}/answer`에 `{provider_request_id, answers:{approval:"allow"|"deny"}}`를 보낸다. 질문은 id `approval` 하나여야 한다. `answer_agent_approval`은 기존 답 함수를 호출한 뒤 성공한 같은 요청의 예약만 승인하거나 해제하고 `question_answered {kind:approval}`를 한 번 기록한다. 입력 질문·비밀값·자유 글 답 규칙은 유지한다. 답 뒤 adapter resume는 원장의 답을 쓰고 결정 API를 다시 부르지 않는다.
- task가 `accepted/running/awaiting_answer`로 들어가면 만료를 지운다. `idle/failed/cancelled`이면 미승인 예약을 해제하고 승인·관찰 lease는 30분 뒤로 설정한다. `unreachable`은 유지한다. run 종료는 즉시 해제, external 전환은 해당 세션의 lease를 해제한다. 결정·산출물 처리도 만료되거나 끝난 run의 lease를 바로 해제한다. 실행 플래그와 무관하게 cron이 만료·종료 백업 정리를 한다. 해제 30일 뒤 삭제하되 미해소 충돌은 보존한다.
- 산출물의 경로가 비어 있으면 `observed` lease를 만든다. 다른 run의 경로를 실제로 썼으면 충돌을 기록하고 사건 commit 뒤 늦게 쓴 run을 멈춘다. 이 멈춤은 run → task → lease 순서, Action·세션 잠금 없이 `stopped_at=null`과 gate `path_conflict`를 사용한다. `55P03`은 최대 세 번 시도하고 남으면 cron이 재시도한다. `list_pending_path_conflict_stops`는 같은 사용자의 충돌 run이 `queued/running/waiting_approval`인 행만 한도 전에 고르므로 종료된 run이 다음 후보를 가리지 않는다. 파일 내용을 되돌리지는 않는다.
- 양보·해제·external·충돌 알림은 고정 id를 가진 대화 `event` 줄이다. 먼저 말을 거는 `agent_message`는 만들지 않는다. 알림이 전부 기록된 lease만 시각을 CAS 비교해 표시하므로 오래된 전달 확인이 뒤의 해제를 숨기지 않는다. 충돌 해소는 D4b-s가 연결했다: `POST /api/v2/path-conflicts/{lease_id}/resolve { keep, conflict_version }` → `resolve_path_conflict`(`conflict_version`은 충돌 발생마다 증가하는 정수 CAS, 옛 version · 이미 해소됨은 409 `conflict`로 쓰기 0 · 지표 0). Review 항목은 `path_conflict:<lease_id>`, version=`conflict:<lease_id>:<conflict_version>`이고, 읽기 전용 SQL `review_agent_inputs`가 같은 조건으로 직접 읽는다(`listPathConflicts`의 500 상한을 쓰지 않는다 — `list_path_conflicts`와 같은 lease 집합은 시험이 대조한다). 상세는 `docs/review-summary.md` JSON 계약 3-2.
- 결정·충돌 발견·해소와 승인 답 지표는 상태 변경과 같은 DB 트랜잭션에 있다. props에는 명령·경로·id가 없다. bridge 로컬 결정 및 1초 초과 로컬 defer는 이 서버 지표에 포함되지 않는다. TS는 RPC를 중간에 취소하지 않아 bridge 시간 초과 뒤 서버 결과와 다를 수 있으며, 사후 충돌 규칙이 늦은 쓰기를 처리한다.

검토 반영: 설정 파일(`.git/.claude/.codex/.vscode/.idea/.husky/.githooks/.cargo` 아래와 `.envrc/.mcp.json/.gitattributes/.gitmodules/.yarnrc.yml/.npmrc/.pre-commit-config.yaml/lefthook.yml`)은 접힌 경로로 검사하고 Auto/Full도 승인 예약한다. Codex 설정 파일 요청도 Auto/Full 또는 같은 item의 반복 요청이면 `runs_without_sandbox`를 표시한다. 작업 폴더의 일치·포함은 대소문자를 보존한 NFC 경로로 검사하고 상대 경로는 SQL이 만든다. `pending:` 실제 폴더는 두 단 이상이어야 하며 홈 자체(`^/Users/[^/]+$`)는 거절한다. 경로 길이는 NFC 뒤에 재며, 산출물의 절대 경로가 1,000자 또는 작업 폴더가 500자를 넘으면 사건을 적용하고 lease만 건너뛴다. 미승인 예약은 사후 충돌 근거에서 제외하고, 끝난 run에는 관찰 lease를 만들지 않는다. 실제로 멈춘 충돌만 중단 시각·알림을 남긴다.

승인 재사용: 같은 열쇠의 다른 답이나 다시 열린 질문은 `question_stale`(409), Codex의 이미 답한 결정 열쇠는 `deny/not_first_request`다. D3b는 같은 item의 두 번째 이후 승인 요청에 회차 `:<n>`을 붙인다. 같은 run의 재사용 lease 중 `requested`만 현재 요청에 다시 연결한다. 기존 `approved/observed`는 source·request_id를 보존하고 만료만 지우므로 새 요청의 Deny로 해제되지 않는다. 서버의 늦은 `allow`가 새로 넣은 행은 그 요청의 Deny로 해제한다. 인증·기기 확인 뒤 프로세스 내 사전 한도를 검사하며, DB 한도는 그대로 최종 검증한다. 사전 거절에도 SQL 경로와 같은 `agent_note`를 붙이며, DB 결정 지표에는 포함되지 않는다.

검증은 `lib/agents/{tool-decision,path-leases,approvals}.test.ts`, `lib/bridge/tool-decision.test.ts`, 새 route 및 기존 연결부 시험, `tests/db/agent-path-leases*`에 있다. `tests/pg/agent-path-leases.test.ts`의 P1–P12는 실제 잠금 경합용으로 작성했으며 코디네이터가 실행한다. Mac realpath·PATH·명령 재구성, 훅 1.5초/서버 왕복 1초 및 p95, 실제 provider는 D3a/D3b의 검증이다. ASCII 밖 대소문자 충돌과 D2a gate 조회의 중복은 남는다.

## 14. 비밀값 로컬 답 (OA F2)

`20261126000000_answer_agent_question_locally.sql`은 `20261121000000`(`question_answered` 지표) 뒤에 적용한다. 새 SQL 함수 하나(`answer_agent_question_locally`)뿐이다: 표·열·색인·트리거·지표 CHECK 변경 0, 기존 함수 본문 교체 0, 새 서버 플래그 0, 새 지표 type 0. 되돌리기는 파일 머리의 `drop function`이다.

- **목적:** 비밀값(`secret`)이 하나라도 있는 input 질문은 서버로 답할 수 없다(D1d 답 route는 409 `secret_requires_local`, RPC 0). 그 세션을 가진 Mac이 값을 메모리에 두고 "이 질문은 이 Mac에서 답했다"만 서버에 표시하면, 서버는 기존 `answer_agent_question`의 로컬 갈래를 지난다(질문 열쇠 CAS · 중복 수렴 · 답 단계 · bridge 명령 · 대화 줄 "Answered on this Mac"). 값은 서버에 오지 않고 저장되지 않는다.
- **route:** `POST /api/v1/bridge/answer-local { bridge_id, agent_task_id, request_digest }`. 사용자 토큰(Bearer 또는 같은 출처 쿠키) + `X-Taskforce-Bridge-Secret`. 본문은 UUID 둘과 `request_digest`(= `provider_request_id`의 UTF-8 SHA-256 소문자 16진 64자) 뿐인 strict 객체이고 512바이트를 넘으면 읽기를 끊는다. 글을 담을 자리가 없다(`provider_request_id`는 아무 글자 200자까지라 본문에 실을 수 없다). 쿼리 문자열 · 경로 인자는 읽지 않는다. 순서: gate → 인증 → 본문 → 기기 → 한도(`bridge_ack` 몫, 분당 240) → 일. `maxDuration` 15.
- **gate:** `CONVERSATIONS_V2_ENABLED` ∧ 켜진 adapter(`openAgentAdapters()`, D1d 답 route · Review 질문 항목과 같은 조건). 닫히면 404이고 인증 · DB 호출이 없다. 열린 adapter 목록은 SQL로 넘어가 그 세션의 adapter를 거른다. 실행 kill switch · DB gate는 보지 않는다 — 닫혀 있으면 답 명령이 lease에서 `write_gate_closed`로 거둬진다(D1d 답과 같다).
- **누가 표시할 수 있나:** 그 세션의 연결이 묶인 bridge의 Mac뿐이다(사용자 토큰 + 그 bridge의 secret). 같은 사용자의 다른 Mac · 폐기된 bridge · 남의 작업 · 존재하지 않는 작업은 모두 404 `not_found`이고 쓰기 0이다(다른 Mac이 표시하면 답 명령은 주인 Mac으로 가는데 거기엔 값이 없어 질문을 잃는다). 토큰만으로는 401이다. 증명은 두 겹이다: TS `bridgeOwnsSession` 앞단(세션이 `closed`/`external`이면 404) + SQL이 같은 트랜잭션에서 잠그기 전 · `answer_agent_question`이 세션 · 작업을 쥔 뒤 다시 확인한다(권위). 뒤의 확인이 어긋나면 `TF005`로 블록의 쓰기를 모두 되돌리고 `not_found`다. 두 정의의 차이는 시험이 표로 고정한다: 세션 `closed`/`external`은 TS가 거르고(404) SQL은 `stale`, 연결 `error`/`revoked`는 TS가 통과하고 SQL이 `stale`이다.
- **응답(도메인 결과는 200의 `status`):** `{status:"answered"|"duplicate", step_id}` · `{status:"stale", reason:"question_closed"|"not_live"|"not_secret"}`. `duplicate`(같은 요청을 다시 보냄)는 `answered`와 같게 본다. `not_live`는 heartbeat 공백으로 작업이 `unreachable`인 참고 이유다(Mac이 heartbeat · reconcile로 되살린 뒤 한 번 다시). `not_secret`은 비밀값 입력 질문이 아니다(승인 질문은 lease 확정이 있는 `answer_agent_approval`로만 답한다). HTTP 오류: 400 `invalid_request`(고정 문구 `Invalid local answer request.` — 틀린 필드 이름을 되돌려주지 않는다) · 401 · 403(폐기된 bridge) · 404 · 409 `conflict`(잠금 경합이 3번 시도 뒤에도, 멱등이라 다시 보내도 된다) · 429 `Retry-After` · 500. 새 오류 코드 0.
- **SQL 순서:** digest 모양(소문자 16진 64자, 틀리면 `invalid`) → 잠금 없이 풀기(작업 → 대화 run → 세션 → 연결 → bridge, 연결이 이 bridge · bridge `active` · adapter 목록 안) → 질문 고르기(열린 질문의 열쇠를 SHA-256 해 digest와 맞으면 그 질문, 아니면 이미 답이 간 질문, 아니면 `stale/question_closed`) → input · 비밀값 있음 → 작업 `unreachable`이면 `not_live` → `answer_agent_question(user, task, 원래 id, null, true, null)`(인자가 SQL 상수라 값이 들어갈 길이 없다) → 사후 소유 확인(세션 · 작업을 쥔 채 연결이 이 bridge에 묶였는지, bridge `active`, 답이 간 질문이 `input`인지 — 어긋나면 `TF005`로 되돌린다) → `answered`일 때만 지표. 원래 `provider_request_id`는 DB의 질문 열쇠에서 꺼낸다.
- **잠금:** `answer_agent_question`의 순서(메시지 → 대화 → 세션 → run → 작업 → 단계)뿐이다. 이 함수는 잠그기 전에 읽기만 하고 bridge · 연결 행을 잠그지 않는다 — `revoke_bridge`(bridge → 연결 → 세션 …)와 서로 반대 순서로 기다리지 않는다(명령 행의 FK는 bridge에 KEY SHARE만 건다). 함수는 `lock_timeout=2s`다: 넘으면 55P03, TS가 3번 시도한 뒤 409. 남의 호출(다른 Mac · 폐기된 bridge · adapter 목록 밖 · bridge 없는 연결)은 잠그기 전에 걸러져 다른 연결이 쥔 잠금을 기다리지 않는다. 알려진 기존 한계였던 Done ↔ 답 교착(F2 이전부터: Done이 run을 먼저 쥔 채 task 뒤의 메시지 · 세션 잠금을 기다리고, 답이 메시지 · 세션을 쥔 채 그 run을 기다리면 순환이라 PG가 한 쪽을 40P01로 물렸다)은 OA F3이 고쳤다(15장): Done은 풀린 직후 55P03으로 물러나고(`writeAction`이 다시 한다) 답은 끝난다. 평범한 `answer_agent_question`도 F2 래퍼도 같은 결과이며 `tests/pg/answer-local.test.ts` P5b가 이를 고정한다.
- **효과:** 표시가 `answered`면 `pending_question`이 비고 작업이 `running`이 되어 Review의 `agent_secret_question:<task>` 항목이 모든 기기에서 다음 읽기에 사라진다(복귀 요약 줄의 `needs_answer`도 D4b-s 규칙대로 다시 정해진다). 답 명령은 주인 bridge에 `{kind:"answer", answered_locally:true, answers:null, answer_text:null}`로 간다. 그 사이 Stop · Done이 오면 답 단계가 skipped가 되고 답 명령은 lease에서 `stale/not_prepared`로 거둬진다(Mac은 취소 명령을 받는다). 서버 답 route(D1d)는 표시 전후 모두 409 `secret_requires_local`이다.
- **측정:** `answered`일 때만 같은 트랜잭션에서 `question_answered {kind:"input", adapter, answered_locally:true}` 한 줄(새 type 없이 차원만 더한다, `answer_agent_approval`의 `decision`과 같은 선례). `duplicate` · `stale` · `not_found` · `invalid` · 롤백은 0이다. 측정 공백: ① 어느 화면(Assistant 카드 · Review)에서 입력했는지 ② 질문이 기다린 시간 ③ 표시 뒤 lease 때 값이 없어 닫힌 수는 지표가 아니라 `bridge_commands.outcome='request_closed'`가 원천이다.
- **남는 위험:** 표시 ~ lease 사이에 앱이 재시작하면 Mac에 값이 없어 요청이 거절로 닫히고 질문은 복원되지 않는다(D2a 정산 규칙, 사용자가 다시 시킨다 — Mac이 값을 먼저 넣고 부르는 순서로 창을 몇 초로 줄인다). 클라이언트가 URL에 값을 넣으면 플랫폼 요청 기록에 남는다(서버가 막을 수 없다 — 주소는 상수여야 한다). 값은 Claude Code 자체 기록에는 남는다(D3a 5.1 Q9, Taskforce 서버 · 원장 0). 연결의 `bridge_id`가 바뀌지 않는다는 사실은 강제되지 않는다(그래서 사후 확인이 있다).
- **D4b-m(Mac) 호출 순서:** ① heartbeat 성공 뒤에만(잠에서 깬 직후 `not_live` 방지) ② `LocalSecretAnswers.put`을 **먼저** ③ `POST /api/v1/bridge/answer-local`. 주소는 상수, 쿼리 · 경로 인자 0. ④ 결과: `answered` · `duplicate` → 값을 둔다(lease가 가져간다) / `stale(question_closed · not_secret)` · 404 · 401 · 403 → 값을 지우고 RLS로 질문을 다시 읽는다 / `stale(not_live)` → 값을 두고 heartbeat · reconcile 뒤 한 번 다시, 실패하면 지움 / 409 · 5xx · 네트워크 오류 → 값을 두고 같은 요청을 다시(멱등), 끝내 모르면 지우고 카드를 되돌린다. ⑤ `duplicate` 뒤에도 값이 메모리에 오래 남지 않게: `LocalSecretAnswers`에 TTL(질문 만료와 같게)을 두고, adapter가 그 요청을 더는 기다리지 않게 되면(전달 · 요청 닫힘 · 질문 교체 · 취소) 값을 버린다(답 명령의 정산은 값을 버리지 않는다, D4b-m-2 16.14). Swift DTO 기준 JSON은 `src/lib/bridge/answer-local.contract.test.ts`의 `ANSWER_LOCAL_REQUEST_JSON`이다.
- **D4b-m-2(Mac, 실제 연결):** 위 순서와 결과 표는 `AgentQuestionSecretFlow`(Kit)가 고정했고, 실제 포트는 `BridgeRuntime.submitLocalSecret`(`Bridge/BridgeRuntime+SecretAnswer.swift`)이 채운다. 앱의 `BridgeLocalSecretSubmitter`(`Mac/Bridge/BridgeSecretSubmitter.swift`)가 질문 저장소 뒤에서 활성 런타임을 골라 부른다: bridge가 꺼졌거나 런타임이 없으면 `unavailable`("Couldn't send"), 계정 경계는 질문 저장소와 같은 `AccountScope`의 토큰(계정 + 세대)으로 본다: 시작 · `put` 앞 · `POST` 앞마다 사용자 ≠ 런타임 파티션이거나 세대가 올랐으면(같은 사용자의 로그아웃 · 재로그인) 값을 지우고 보내지 않는다. 런타임은 더해서 자기 원장이 그 (task, request)를 이 런타임 adapter의 열린 비밀값 요청으로 알고 닫히지 않았을 때만 값을 둔다(아니면 값 없이 POST도 없다). `BridgeClient.answerLocal`은 10초 · 재시도 0(결과 표가 최대 3번)이고 `authed(.answerLocal, ackNotFound: true)`만 거치므로 401 회복 · 403 폐기 · 429 멈춤 · 늦은 응답 버리기를 그대로 타고, 404는 도메인 결과(세션이 닫혔다 · 질문이 바뀌었다)라 bridge를 지우지 않는다. 값은 `LocalSecretAnswers`(열쇠 = `(agent_task_id, provider_request_id)`, 값은 `description` · `customMirror`가 값을 말하지 않는 상자)에만 있고 TTL은 `deliveryWindow`(24시간)다. 값은 (task, request)마다 하나이고 `put`은 덮어쓴다(재입력). adapter가 바로 그 요청을 아직 기다리는 동안(원장: 그 task가 열려 있고 `openRequestID`가 그 요청이며 닫히지 않음)만 둔다. 그래서 되살림 정산(결과 확인 `not_received`)은 값을 버리지 않는다: 서버가 질문을 되살리고 adapter는 여전히 그 요청을 기다린다. 닫힘 정산은 **서버가 질문을 되살리지 않고 확실히 닫는 것만**이다(서버 SQL로 도출: `withdrawn/stale_answer` · `withdrawn/action_closed`(Done) · `stale/run_closed`). 되살릴 수 있거나 모르는 정산은 값을 둔다: 그 밖의 `withdrawn`(write_gate_closed · expired · session_* · not_connected) · `stale/not_prepared`(Stop/Done의 건너뜀과 되살림 뒤 failed 단계를 가를 수 없다 — Stop/Done 뒤 값은 TTL · quit · stop까지 남는 알려진 한계) · 그 밖의 stale · 404 · 거절 · 결과 확인. 닫힘 정산은 그 열쇠에 끝나지 않은 다른 제출이 없을 때(답한 POST 수 N ≤ 끝을 본 답 명령 수 M, 돌고 있는 제출 없음) 값을 버린다. 제출이 돌고 있어 못 버린 닫힘 정산(센 명령으로 설명되지 않는 것)은 표시해 두었다가 그 제출이 끝날 때 버린다(지연된 `answered`가 N만 올려 굳지 않게). 그 밖의 정산은 M만 올린다. `put`을 못 한 제출은 그 열쇠의 옛 값도 지운다(쉬던 옛 값이 새 제출의 POST로 나가지 않게). 버리는 때는 기다림이 끝날 때다: `closeRequestAndAck`, 버려진 요청, 전달이 끝난 뒤, 중단(`cancel`)이 열린 요청을 닫을 때, 보관 정리(원장이 그 요청을 더는 열린 것으로 보지 않거나 질문이 교체됐거나 task가 `cancelled`). `isBusy`(종료 확인)는 돌고 있는 제출이 있거나 N > M일 때만 참이다(옛 명령의 정산은 M만 올려 새 답의 바쁨을 끄지 못한다). 되살아난 질문을 기다리며 쉬는 값은 종료 때 그냥 버린다. 재시도 때 값이 없으면 원장을 본다: 닫힘 → 질문이 닫혔다, 이 제출이 이미 POST했고 요청이 열려 있지 않으면 전달된 것 → 보냈다. 전부 버리는 때: 계정이 떠남(`accountLeft` · `stop`) · 종료 · 계정 삭제 · 폐기. 값을 꺼내는 곳은 답 명령을 전달하는 `runAnswer`의 `take` 하나뿐이고 나머지 길은 버리기만 한다. 서버 · 마이그레이션 변경 0.

검증은 `lib/bridge/answer-local{,.contract}.test.ts`, route test, `lib/bridge/auth.integration.test.ts`의 한 행, `tests/db/answer-local*`(PGlite T1–T9), `tests/pg/answer-local.test.ts`(P1–P8, 실제 Postgres)에 있다.

## 15. 전달 정리 (OA F3)

`20261128000000_agent_delivery_fixes.sql`은 `20261127000000` 뒤에 적용한다. 새 표·열·정책 0, 새 지표 type 0, 새 서버 플래그 0. 새 SQL 함수 하나(`expire_unleased_agent_messages`)와 찾기용 부분 색인 하나 · 창 번호용 시퀀스 하나(`bridge_reclaim_scan_seq`), 기존 함수 일곱의 본문 교체(각각 잠금 방식 · 순서만 다름: 아래 세 함수와 `sweep_bridge_heartbeats` · `sweep_agent_step_leases` · `sweep_expire` · `purge_expired_execution_text`)와 읽기 함수 하나(`count_overdue_agent_step_leases`)다. 되돌리기는 파일 머리에 있다. 배포 순서는 마이그레이션 → 서버다(서버가 먼저 나가면 `sweepBridge`의 새 RPC가 "함수 없음"으로 실패해 `errors`로만 세어지고 다음 분에 다시 한다. 마이그레이션만 먼저면 회수가 돌지 않을 뿐 결함 1 수정은 바로 효과가 있다).

**결함 1 — Done ↔ 답 교착.**

- **원인:** 질문이 있는 작업을 Done이 취소하면 같은 트랜잭션에서 작업 행을 두 번 갱신한다. PostgreSQL은 FK 열이 바뀌지 않은 UPDATE의 FK 확인을 건너뛰지만, 옛 행을 같은 트랜잭션이 이미 갱신했으면 건너뛰지 않고 다시 확인하며 가리키는 행(세션 · 원 메시지)에 `FOR KEY SHARE`를 **기다리며** 건다. Done은 Action → run → task 순으로 쥐고, 답 · 사건 · lease는 메시지 → 대화 → 세션 → run → task 순이라(11장) 서로 기다리면 순환이다. 실제 PG에서 `pg_locks`로 확인했다: 둘째 갱신에서 Done이 세션(또는 원 메시지) 행의 tuple 잠금을 쥐고 그 행을 FOR UPDATE로 쥔 연결의 트랜잭션을 기다린다. 첫 갱신은 기다리지 않는다.
- **고침(세 함수, 각각 한 곳):** `request_agent_task_cancel`은 질문 갈래(`if v_question is not null then`) 첫 줄, 작업 행 갱신 앞에서 세션 · 원 메시지를 `FOR KEY SHARE NOWAIT`로 먼저 쥔다. 둘째 갱신의 FK 확인이 이미 쥔 KEY SHARE를 다시 잡을 뿐이라 기다리지 않는다. 남이 FOR UPDATE로 쥐고 있으면 즉시 55P03으로 Done 전체가 롤백되고 `writeAction`이 다시 한다. 질문이 없는 갈래는 갱신이 한 번이라 그대로다 — 사건이 흐르는 중에도 평범한 Done은 기다리지 않고 끝난다. `revoke_bridge`는 작업 고리 첫 줄에서 원 메시지를 같은 방식으로 쥔다(취소 뒤 `state='cancelled'` 갱신이 둘째 갱신이다, 세션은 폐기가 이미 쥔다). `stop_agent_runs_on_user_claim`은 run을 `agent_session_id, id` 순으로 잡는다(heartbeat · 폐기 · sweep과 같은 세션 → run 순서라 한 이슈에 같은 bridge의 두 세션 run이 열려 있어도 서로 run 하나씩 쥐고 기다리지 않는다).
- **안전망:** `writeRpc`(`writeAction` · `writeProgress`)와 `revokeBridge`는 55P03에 더해 40P01도 같은 인자로 다시 한다(한 트랜잭션이라 안전). 알려진 순환은 SQL이 55P03으로 끊으므로 SQL 단계 실제 PG 시험은 40P01 0을 단언한다.
- **대가:** Done이 짧은 남의 FOR UPDATE(heartbeat · lease · 사건 처리 중, 수 ms)와 겹치면 기다리지 않고 55P03 → 재시도(질문이 있는 작업에서만). 3번 모두 겹치면 v1 Action route가 500을 낸다(관찰, 후속: 오류 목록이 동결이라 이 WP에서 바꾸지 않았다).
- **잠금 순서(구현 후):** Done = Action → run(`agent_session_id, id` 순) → task → 원 단계 → [질문 갈래: 세션 · 원 메시지 KS NOWAIT] → (lease 전 dispatched: 원 메시지 FU NOWAIT / lease 전 답: 답 글 FU NOWAIT). 답 · lease · 사건 · heartbeat · 폐기는 11장 그대로(폐기는 작업 고리에서 원 메시지 KS NOWAIT가 더해진다). sweep은 11장 순서 그대로이되 세션 · run · task · 단계 잠금을 NOWAIT로 잡는다(아래 "백그라운드 작업은 기다리지 않는다"). 시작(`start_agent_turn`)은 반대 순서(세션 → Action 공유)지만 세션에 진행 중 task가 있으면 Action 전에 `session_busy`로 끝나므로 순환이 나지 않는다(`tests/pg/agent-delivery-fixes.test.ts` P14가 고정).

**결함 2 — 만료한 lease 전 `prepared`.**

- **문제:** Mac이 lease 전에 꺼지면 메시지는 `dispatched`, 단계는 `prepared`, 세션만 `unreachable`이 된다. `delivery_expires_at`(24시간)이 지나도 만료 sweep(`conversation_expire_agent_messages`)은 `queued` · `not_sent`만 보므로 행이 그대로고, Send again은 `not_sent` · `expired`만 받아 `not_eligible`이다. Mac이 돌아오면 lease가 만료를 보고 거두지만 꺼져 있는 동안은 AC3 "24시간 넘으면 expired, Send again이면 다시"와 어긋나고 진행 중 task가 세션의 진행 중 칸을 계속 차지한다.
- **회수:** `expire_unleased_agent_messages(p_limit 1–200)`를 1분 cron의 `sweepBridge`가 `sweep_agent_step_leases` 뒤 · 재전달 앞에서 `{p_limit: 50}`으로 부른다(실행 플래그와 무관). 후보는 잠금 없이 찾는다: message 명령 · lease 전 · outcome 없음 · 단계 `prepared` · lease 없음 · 메시지 `dispatched` · `delivery_expires_at <= db_now()`(lease의 만료 조건과 같다, 세션 · 연결 · gate는 보지 않는다 — 24시간이 지나면 이유보다 만료가 이긴다). 후보마다 하위 트랜잭션에서 메시지(`for update skip locked`) → `lock_bridge_command`(메시지 → 세션 → run → task → step → 명령) → 같은 조건을 잠금 아래 다시 확인 → `withdraw_bridge_command(…, 'expired')`. 끝 상태는 Mac이 돌아와 lease가 거둔 것과 같다(메시지 `expired` · 이유 null, 단계 `failed` + receipt `{never_sent:true, reason:'expired'}`, task `failed`, 명령 `withdrawn`). 지표 · 로그 0.
- **백그라운드 작업은 기다리지 않는다 — 재검토 반영:** 사용자 경로(Done · 답 · heartbeat · 폐기)는 기존 순서 하나로 잠그고(Done은 세션 → run id 순, heartbeat · 폐기는 bridge → 세션 → run), 백그라운드 작업(회수 · `sweep_bridge_heartbeats`)은 **사용자 경로가 쥘 수 있는 잠금을 기다리지 않는다**. 한 호출이 여러 bridge · 세션을 잠그고 성공한 부분의 잠금이 함수가 끝날 때까지 남아서, sweep(bridge id 순)과 회수 · Done(세션 id 순)처럼 순서가 어긋나는 쌍에서는 기다리는 순간 순환이 난다(sweep은 per-bridge 예외 처리 때문에 교착이 조용히 삼켜지기도 했다). 기다리지 않으면 순환의 한쪽이 될 수 없다. 회수는 메시지(skip locked) → 세션 → run → task → 단계 → 명령을 `lock_bridge_command`와 같은 순서로 **NOWAIT**로 먼저 쥐고(못 쥐면 그 후보만 `busy`), sweep은 세션 · run · task · 단계 잠금을 NOWAIT로 바꿨다(본문은 그 네 곳만 다르다, T2b). 못 쥔 bridge는 하위 트랜잭션이 롤백되어 다음 분에 처음부터 다시 하고, 그 수는 기존 `failure_count`(`sweepBridge`의 `errors`)로 세어진다. 안전망으로 `heartbeatBridge`도 40P01을 50 · 150ms 간격으로 최대 두 번 다시 한다. 시험: `tests/pg/agent-delivery-fixes.test.ts` P10c(회수 ↔ sweep) · P13b(Done ↔ sweep) · P10d(회수 ↔ heartbeat), bridge A < B 이고 세션 A > 세션 B인 여러 bridge 구성.
- **같은 cron의 나머지 sweep — 재검토 2 반영:** `sweepBridge`가 이어서 부르는 `sweep_agent_step_leases`와 실행 sweep의 `sweep_expire`는 단계를 먼저 잠그고 `calling → unknown_outcome` 트리거(`execution_steps_release_credits` → `release_run_credits`)가 그 run을 기다려 **step → run** 순서였다 — Done · Stop · 폐기 · heartbeat · lease/settlement/readback의 run → task → step과 역순이라 교착(40P01)이 났다(크레딧 예약이 없어도). 두 함수는 이제 run을 `NO KEY UPDATE SKIP LOCKED`로 먼저 쥐고 단계를 `FOR UPDATE SKIP LOCKED`로 쥔다(본문은 잠금을 쥐는 문장만 다르다, T2c). 보관 정리 `purge_expired_execution_text`(step → run)도 그때 run만 SKIP LOCKED로 바꿨으나 단계는 여전히 기다렸고, 재검토 3에서 다시 고쳤다(아래). 못 쥔 단계는 건드리지 않고 다음 분에 다시 후보가 되며, 5초 넘게 만료한 채 남은 에이전트 단계 수를 `count_overdue_agent_step_leases`로 세어 `sweepBridge` 결과의 `lease_busy`(숫자)로 보인다. 시험: P10f(두 sweep × Done · Stop · 폐기 · heartbeat · lease 재요청 · settlement, 건너뜀 → 다음 호출이 처리, 보관 정리). cron이 부르는 모든 함수의 잠금 목록은 `handoffs/oa-f3-notes.md`의 "재검토 2 반영" 표에 있다.
- **창 돌리기 — 검토 반영:** 후보를 만료가 오래된 순으로 `p_limit`개씩 창으로 나누고, 호출마다 시퀀스 번호가 가리키는 창 하나를 처리한다(후보가 `p_limit` 이하면 창이 하나라 늘 같다). 영구히 건너뛰어지는 후보(예: 연결의 bridge가 바뀐 명령)가 50개 이상 쌓여도 머리를 붙잡지 못하고 다른 창의 후보가 다음 호출들에서 처리된다(T12: 부적격 50 + 적격 1 → 두 번 안에 회수). 후보가 많으면 한 번에 `p_limit`개씩이라 모두 처리하는 데 창 수만큼 분이 걸린다.
- **막힘:** 메시지를 남이 쥐면 그 후보는 건너뛰고(`busy`, 다음 분), 세션 · run · task · 단계 · 명령도 NOWAIT라 쥘 수 없으면 그 후보만 `busy`다(트리거가 쓰는 다른 행 같은 남은 기다림은 `lock_timeout` 1초 뒤 `busy`). 나머지 후보는 계속한다. 10초 예산을 넘으면 남은 후보는 다음 분에 한다. 반환은 `{reclaimed, busy, sessions:[{user_id, agent_session_id}]}`(id 외 글 0).
- **TS:** `sweepBridge`가 결과를 strict zod로 검증하고 `reclaimed` · `reclaim_busy`(숫자)를 결과에 더해 cron 로그 `bridge_sweep`에 싣는다. 회수한 세션은 사용자별로 `kickBridgeSessions`(bound인 세션만 시작)한다 — 진행 중 칸이 비어 뒤 메시지가 바로 갈 수 있다. `kickBridgeSessions`는 `bound`를 보기 전에 앞 5개(`BRIDGE_KICK_LIMIT`)로 자르므로 5개 이하 청크로 나눠 부른다(검토 반영: 같은 사용자의 여섯째 세션부터 kick이 빠지던 것). 응답 모양이 틀리거나 RPC가 실패하면 `errors`만 센다.
- **Send again · 읽기 모델은 바뀌지 않는다:** 회수 뒤 DB가 `expired`가 되므로 개별 · 일괄 Send again이 코드 변경 없이 받는다(`message_resent {from:"expired"}` 한 줄). 읽기 모델은 시계를 보지 않는다 — 회수 전에는 `queued`, 회수 뒤에는 `expired`로 DB를 그대로 보인다. 만료 ~ 다음 cron(최대 1분) 동안은 `queued`다.
- **같은 cron의 실행 sweep 내부 분기와 보관 정리 — 재검토 3 반영:** (1) `sweep_expire`는 외부 효과 단계를 run → 단계 SKIP LOCKED로 쥔 뒤 같은 트랜잭션에서 `execution_retry_internal`로 내부 효과(초안) 단계를 갱신했고, 이 갱신은 후보를 잠그지 않아 초안 단계를 **기다렸다**. 에이전트 run A를 쥔 채 초안 단계 D를 기다리면 D를 쥔 초안 완료(`complete_internal_step`, 산출물 insert의 FK가 Action X에 KEY SHARE)는 X를 쥔 Done을, Done은 A를 기다려 sweep → D → X → A → sweep **3자 순환**이다. 트랜잭션을 나눌 수 없는 한 함수라 내부 효과 후보도 같은 run → 단계 SKIP LOCKED(`array(select s.id … for no key update of r skip locked for update of s skip locked)`)로 쥐어 넘긴다: 이 함수는 어떤 잠금도 기다리지 않는다(못 쥔 초안 단계는 다음 분). 본문은 이 선택 하나만 다르다(T2c). (2) 보관 정리는 run을 SKIP LOCKED로 쥐고 단계를 한 문장으로 갱신해 남이 쥔 단계를 기다렸다. 단계를 쥔 실행기(`begin_call`: 단계 → run → 중단 확인)가 정리가 쥔 run을 기다리면 순환이다. 이제 run마다 하위 트랜잭션에서 run을 `NO KEY UPDATE NOWAIT`로, 지울 단계를 `FOR UPDATE NOWAIT`로 쥔 뒤에 갱신하고, 못 쥐면(55P03) 그 run의 쓰기와 잠금이 되돌아가 **통째로 다음 정리로** 간다 — 일부 단계만 지우고 `text_purged_at`을 적는 일이 없다. 후보 select와 두 갱신문은 원본 그대로다. 대가: 못 쥔 run도 한 번의 `p_limit` 자리를 쓰고, 지운 수(반환값)에는 들지 않는다. 시험: P16(실행기 ↔ 정리, 다른 run은 계속 지움) · P17(sweep ↔ 초안 완료 ↔ Done 3자) · P17b(내부 분기가 남이 쥔 run · 단계를 건너뜀) · P18(receipt 안전망은 Action 행만 기다림). `writeMissingReceipts → write_execution_receipt → write_action`은 첫 잠금이 Action 행이고 그 뒤에는 run · 단계 · 작업 행을 쥐지 않아(읽기만, 원문 행 insert의 트리거는 새 원문이 문맥 멤버가 아니라 아무것도 올리지 않는다) 기다림이 순환의 한쪽이 될 수 없다 — 바꾸지 않았다. 알려진 한계(실행 엔진 안의 기존 잠금 순서)는 `handoffs/oa-f3-notes.md`의 "남는 위험 (실행 엔진 잠금, 후속)"에 있다.
- **경합(요약):** 회수 ↔ lease는 같은 잠금 순서로 줄을 선다(lease가 먼저면 회수는 그 메시지를 건너뛰고, 회수가 먼저면 lease는 `stale/not_prepared`, intent 0). 회수 ↔ Send again은 메시지 잠금으로 줄을 선다. 회수 ↔ Done · 폐기 · heartbeat는 회수가 기다리지 않고 `busy`로 건너뛴다(사용자 경로가 먼저). 회수 ↔ Stop은 메시지 잠금으로 줄을 서고 교착 0이다. sweep ↔ 사용자 경로도 sweep이 기다리지 않는다. 회수 둘이 겹치면 두 번째는 건너뛴다. 실제 PG 시험은 `tests/pg/agent-delivery-fixes.test.ts` P1–P18.
- **알려진 한계:** answer 명령의 답 글 만료(lease 때만 거둠) · 명령 행이 없는 `prepared` 단계(트리거가 active bridge를 못 찾은 경우) · 연결의 bridge가 바뀌거나 bridge가 폐기돼 `lock_bridge_command`가 null인 명령은 회수 대상에서 늘 건너뛰어진다(폐기는 task를 취소하므로 정상 경로에서는 남지 않는다). 이런 후보는 매 호출 창 하나에서 잠금을 시도하고 건너뛴다 — 창 돌리기라 뒤 후보를 막지는 않지만 지워지지 않는 한 계속 후보로 남는다.

## 16. Claude Code adapter (OA D3a)

Mac bridge(11-1절)의 첫 실제 adapter다. 턴마다 사용자의 `claude -p` 프로세스 하나를 띄우고 감독한다. 핵심은 Kit `apple/Packages/TaskforceKit/Sources/TaskforceKit/Bridge/ClaudeCode/`(`#if os(macOS)`)와 의존 0 target `TaskforceAgentWire`(helper 둘의 본체), 앱 번들 helper `Contents/Helpers/tf-agent-hook` · `tf-agent-mcp` · 지킴이 `Taskforce Agent.app`(13장)(Xcode `tool` 타깃, 복사할 때 서명)다. **서버 registry는 바꾸지 않았다**: Claude Code는 초기 등급(쓰기 · 읽기 전용 모두 미검증)이라 서버가 전달하지 않는다. 실제 provider 확인(R1 · R2)과 registry 변경(D3a-s)은 다음 단계다(계약 `handoffs/oa-d3a-contract.md` 4.7 · 5.1).

- **실행:** 인자는 `-p --output-format stream-json --verbose --include-hook-events --max-budget-usd 25 --tools <등급> --strict-mcp-config --mcp-config <mcp> --add-dir <작업 폴더 realpath> --settings <settings> --setting-sources project --permission-mode manual --append-system-prompt <질문은 mcp__tf__ask_user로 한 번에 하나> (--session-id | --resume) <id>`. `--model`은 주지 않는다(사용자 플랜의 기본). 등급 write는 `Read,Glob,Grep,Edit,Write,Bash`, read_only는 `Read,Glob,Grep`. 프롬프트는 stdin, 답 · 닫기 resume는 빈 stdin이다(비어 있지 않으면 보류 뒤 턴이 하나 더 돌아 같은 쓰기가 겹친다, S0 CC-2). 자식 환경은 정확히 `HOME` · `PATH` · `LANG` · `USER`와 spawn marker `TASKFORCE_SPAWN_ID=<spawn id>`(9장 4)이고 PATH는 찾은 `claude` 폴더 + `~/.local/bin:/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin`이다. `claude`는 `~/.local/bin` → `/opt/homebrew/bin` → `/usr/local/bin` 중 처음 있는 것을 쓰고 그 realpath가 이 사용자나 root 소유 · 그룹/모두 쓰기 불가인 일반 실행 파일일 때만 쓴다(셸 설정을 실행해 PATH를 얻지 않는다). `posix_spawn`으로 새 프로세스 그룹 · 앱 fd 물려주지 않음(`CLOEXEC_DEFAULT`) · cwd = 세션 폴더의 빈 `cwd/`.
- **세션 폴더:** `<원장 파티션>/claude-code/<agent_session_id>/`(0700): 빈 `cwd/`, spawn마다 새 `config/<spawn id>.settings.json` · `.mcp.json`(0600, 끝나면 지움, cwd 밖이라 Read로 nonce를 못 읽는다), 상태 파일 `state.json`(Claude 세션 id · 묶였는지 · 열린 보류의 id · 종류 · 입력 digest · 시각 · 대상 지문 해시만). spawn 기록은 `<원장 파티션>/claude-code/lineage/<spawn id>.lineage`(0600, 형식 4: 부팅 id(`kern.bootsessionuuid`) · `keeper <id> <pid>`(지킴이) · `root <id> <pid>`(`claude`) · `responsible yes|no` 숫자만. 띄운 직후 한 번 원자적으로 쓰고(지킴이 · 뿌리 id를 못 읽거나 못 쓰면 띄우지 않는다, 잘린 줄이 있으면 증거 없음), 지킴이가 구성원 0을 증명하고 끝나기 직전에 `<spawn id>.keeper` 끝 기록을, 앱이 끝을 확정하면 `<spawn id>.ended`를 쓰고 앞의 둘을 지운다(읽을 때 `.ended`를 먼저 본다). 앱이 뜰 때 확인된 다른 부팅의 기록은 `.ended`로 바꾼다). 비지 않은 `cwd/`(승인된 Bash가 남긴 파일 등)는 다음 spawn 전에 세션 폴더 안 `cwd.quarantine-<uuid>/`로 옮긴다. 상태 파일에는 비밀값 답을 건넨 적이 있다는 표식(`secret_answered`, 값 0)도 둔다. 계정 삭제는 파티션째 지운다. 사용자 메시지 · 답 · 비밀값 · 도구 입력 · 출력 · stream 원문은 어디에도 쓰지 않는다.
- **훅과 소켓:** settings의 SessionStart 훅은 표식만 내고, PreToolUse 훅(matcher `*`)은 앱 전체 Unix 소켓 하나(`<Application Support>/<번들 id>/Bridge/hook.sock`, 경로가 길면 사용자 임시 폴더, 폴더 0700 · 소켓 0600 · 피어 uid 확인)에 한 줄 묻는다. 요청에는 spawn마다 새 nonce(32바이트) · 세션 id 둘 · 본문을 길이로 바꾼 입력 · 원래 입력의 sha256이 실리고, 응답은 `allow | deny | defer`와 `answers`(ask_user 답) · `command`(다시 만든 Bash) 중 하나뿐이다. 훅은 시작부터 4초(재검토 7, 처음엔 1.5초) 안에 답을 못 받으면 · 소켓이 없으면 · 깨진 답이면 deny JSON(그마저 못 쓰면 exit 2)이고, bridge는 연결부터 1.2초 또는 훅이 실은 절대 기한 − 0.3초 중 이른 때에 deny로 끊는다(재검토 8). 소켓 서버는 bridge가 켜졌을 때만 열고 앱 종료 때 닫는다.
- **결정표:** 로컬 정적 행이 먼저다 — 닫기 모드(모두 deny) · `permission_mode ≠ default` · 답 resume의 보류 id(입력 digest가 다르면 deny) · 허용 도구 집합 밖(`Agent` · `Skill` · `NotebookEdit` · `mcp__evil__*` …) · spawn당 보류 하나 · Read/Glob/Grep은 작업 폴더나 세션 cwd 안만(realpath, 없는 경로는 가장 가까운 조상) · `ask_user`는 입력 검사 뒤 defer(모델이 넣은 `answers`는 버린다) · 작업 폴더 밖 Edit/Write · 백그라운드 · 샌드박스 해제 Bash는 서버를 부르지 않고 정한다. Bash · Edit · Write는 `POST /api/v1/bridge/tool-decision`(1.0초, 재시도 0)로 서버가 정하고, 서버가 읽기 전용 명령을 허용하면 Mac이 넘긴 PATH의 실행 파일이 `/bin` · `/usr/bin` 바로 아래인지 · 경로 인자 realpath가 작업 폴더 안인지 확인한 뒤 명령을 실제 경로 · 작은따옴표 단어로 다시 만든다. 시간 초과 · 2xx 아님 · 등록 전은 defer, 폐기(403)는 deny다. Mac은 Bash · Edit · Write를 서버 판정 없이 허용하지 않는다.
- **질문 · 승인:** 보류는 `result.deferred_tool_use`가 기록한 id를 보고할 때만 질문이 되고(질문 사건은 프로세스가 끝난 뒤에 낸다: 답이 올 때 writer가 하나다), 상태 파일에 id · digest만 적는다. 입력 질문은 `ask_user`의 질문 1–4개(서버 질문 모양과 같은 상한, 담을 수 없으면 훅에서 deny로 고칠 점), 승인은 질문 하나 `approval`(Allow/Deny)이고 질문 줄(머리)은 "Allow Claude Code to edit this file?" · "Allow Claude Code to write this file?" · "Allow Claude Code to run this command?", 글(미리보기)은 Edit/Write `Edit · <상대 경로>` · `Write · <상대 경로>`, Bash `Run · <명령 앞 300자>`다(사용자 결정 Q8, 모양은 DS의 `{label} · {값}`: OA D4b-m-2. Write 머리는 사용자 승인 문구). 답은 열린 보류 id와 종류가 같을 때만 빈 stdin resume로 전달하고 훅이 그 id에 한 번 준다(비밀값도 메모리로 한 번, Q9: Claude Code 기록에는 남고 Taskforce 서버 · 원장에는 없다). 닫기는 닫기 모드 resume로 모든 호출을 deny하고 닫는 id의 결과에서 SIGINT, 끝날 때까지(10초, 넘으면 고아 끝내기) 기다린다.
- **사건:** init → `inputReached`(로컬 전용, 아래) · 새 세션이면 `session_bound`, 진짜 첫 assistant(synthetic 제외) → `accepted`, 같은 메시지의 글 → `message`, 도구 사용 · 결과 → `progress`(2초에 하나), Edit/Write 성공 → 턴 끝에 경로마다 하나의 `artifact`(작업 폴더 기준 상대 경로 · 결과 뒤 sha256), `end_turn` → `turn_completed`, synthetic 로그인 실패 → `failed(sign_in_needed)`, 우리가 보낸 SIGINT의 `aborted_tools` → `cancelled`, 그 밖 실패는 접수 전 `spawn_failed` · 뒤 `agent_error`. 매 spawn 자체 점검: ① 쓴 설정 파일을 다시 읽어 같음(아니면 spawn 0), ② init의 권한 모드 · 도구 집합 · `tf` 연결 · 버전(`>=2.1.241 <2.2`) · cwd · 세션 id, ③ SessionStart 표식이 init 전, ④ 모든 도구 결과 앞에 그 도구의 PreToolUse 훅 시작과 bridge의 소켓 답, ⑥ stdout 한 줄 32MB. 어긋나면 SIGINT하고 실패로 알린다. ④의 예외: CLI는 도구 입력을 훅 앞에서 검증한다("읽기 전에 쓰기", "없는 도구"). 그래서 훅 답이 **없는 오류** 결과가 (Read · Glob · Grep · Edit · Write이거나 init `tools`에 없는 도구)면 아무것도 실행되지 않았으므로 턴을 잇고 모델이 오류를 본다(로그 `claude_tool_refused_before_hook {reason: cli_validated | not_advertised}`, 글 0). Bash는 광고되지 않아도 예외가 아니고, 넘기는 거절은 spawn당 다섯까지다(여섯째부터 ④). 훅이 시작됐으나 답 없이 끝난 호출은 그 훅 시작을 계수에서 뺀다. 훅 답 없는 **성공** 결과와 Bash · `ask_user` 등 그 밖 도구의 오류 결과는 훅을 건너뛴 실행일 수 있어 ④가 그대로 막는다(R1-02 · R1-02b · R1-03에서 실제 CLI로 확인).
- **결과 불명(Q5):** 런타임은 `inputReached`를 받으면 명령의 `inputAt`을 적는다(서버 사건 아님). 접수 신호 없이 끝난 명령의 결과 확인은 `inputAt`이 없으면 지금처럼 `not_received`, 있으면(init 뒤 죽음) `unknown`이다. Claude Code는 transcript를 읽지 않으므로 adapter 결과 확인은 `unsupported` 그대로다.
- **중단 · 고아:** Stop은 정체 확인 뒤 SIGINT(SIGTERM은 쓰지 않는다). 정체 = pid > 1 + 커널 시작 시각 1ms 안 + 소유자 uid + argv의 `config/<spawn id>.settings.json`. 고아 끝내기는 SIGINT → 3초 → (다시 확인) 확인한 pid마다 SIGKILL → 2초 → 확인이고 부모와 자손이 모두 사라진 것을 확인했을 때만 끝났다고 한다(아래 9장 반영). 외부에서 같은 세션을 이어 쓰는 프로세스 찾기(`ClaudeCodeProcessScanner`)는 D4a의 Resume here 보조다.
- **probe:** 설치(찾기) · `--version`의 첫 낱말 `X.Y.Z` · `auth status`의 `loggedIn`만(다른 필드는 읽지 않는다) · managed settings 파일(`/Library/Application Support/ClaudeCode/managed-settings.json`이 있으면 `managed_settings: true`, 서버가 `unsupported`로 둔다). 버전은 실행 파일(realpath · 수정 시각 · 크기)이 같으면, 로그인은 5분 동안 다시 쓰고 `sign_in_needed`를 보면 버린다.
- **앱 연결:** Release adapters는 `ClaudeCodeProcess` 하나(`BRIDGE_ENABLED` NO라 뜨지 않는다), Debug는 `-TF_BRIDGE_FAKE_AGENT YES`면 가짜, `-TF_BRIDGE_REAL_AGENT YES -TF_BRIDGE_WORKSPACE <일회용 폴더>`면 실제 adapter(서버 주소가 loopback일 때만, 폴더는 표식 `.taskforce-disposable`이 있고 저장소 · `~/.claude` 밖이어야 한다), 둘 다 아니면 없음. Release의 `WorkspaceResolver`는 여전히 없어 새 세션은 `spawn_failed`다(폴더 고르기는 D4a).
- **측정 공백(Q17):** bridge 로컬 결정(Read · Glob · Grep · 금지 도구 · `ask_user` · 닫기 · 1초 초과 로컬 defer)은 서버 지표 `tool_call_decided`에 없다. OSLog(`category: bridge`)에 값 종류만 남긴다: `tool_gate {source, decision, reason, ms}`, `claude_spawn {mode}`, `claude_init {mode, ms_to_init, plugins, skills, messaging_socket}`, `claude_selfcheck_failed {check}`, `claude_probe {installed, version_ok, signed_in, managed}`. 명령 · 경로 · 글 · 답 · nonce · 세션 id 원문은 없다. 결정 왕복 p95 · cold start · spawn→init은 R1 · R2가 이 줄로 뽑는다(Debug 전용 실행 장치 `ClaudeCodeEvidenceRunner`).
- **남는 위험:** 작업 폴더가 Documents · Desktop · Downloads · iCloud 안이면 macOS 접근 동의 창이 뜰 수 있다. 지킴이(13장)가 책임 프로세스라 그 창은 Taskforce가 아니라 **"Taskforce Agent"** 이름으로 뜬다(사용자에게 보이는 변화, 온보딩 · 처리방침 문구는 D4a · 코디네이터, R1에서 실제 창 확인). npm으로 설치한 `claude`는 `node`가 PATH 후보에 없으면 버전을 못 읽어 `unsupported`다. 한도 초과 stream 모양은 실측이 없다(지은 규칙). MDM 프로필 등 managed settings 파일 밖의 관리 경로는 보지 않는다. 비밀값 답은 Claude Code 자체 기록(`~/.claude/projects/…`)에 남는다. 셸 쓰기 경로(Bash로 쓴 파일)는 관찰하지 않는다. 1초 초과로 로컬 defer했는데 서버가 lease를 잡았으면 사용자에게 한 번 더 묻는다. 비밀값 가리기는 8자 미만 값과 디코드로 풀리지 않는 변형(base64 · 일부 · 다른 인코딩)을 막지 못한다. 구성원 아래에서 다시 disclaim해 스스로 책임 프로세스가 된 프로세스(다른 앱 실행기 등)는 지킴이의 구성원이 아니다(R1에서 실제 도구로 0인지 확인). 책임 함수는 공개 머리에 없는 libquarantine 함수다: macOS가 바꾸면 물러남(세션 잠금)으로 간다. unique id는 SDK 공개 머리에 없는 `proc_pidinfo` flavor(`PROC_PIDT_BSDINFOWITHUNIQID`)로 읽는다(크기가 맞을 때만 믿는다). 빈 `cwd/`에서 오는 Bash는 서버 파서가 `cwd_outside_workspace`로 미뤄 읽기 명령도 확인 질문이 된다(`swift-fixtures.test.ts`가 지금 결과를 고정, 고치는 일은 D3a-s).
- **검토 반영(계약 8장):** 경로는 realpath로 풀리지 않은 성분에 무엇이든 있으면(끊어진 기호 링크 · 읽을 수 없는 항목) 밖으로 본다. 승인 보류는 대상의 지문(realpath · 장치 · inode · 링크 수, 없으면 조상 폴더의 장치 · inode + 이름)을 상태 파일에 해시로만 두고 재개 때 같을 때만 실행한다(다르면 `target_changed` deny). 하드 링크(링크 수 > 1) Edit/Write와 모르는 입력 키가 있는 Edit/Write/Bash는 서버 없이 승인 질문, 모르는 키가 있는 Read/Glob/Grep과 `..` · 중괄호가 있는 Glob `pattern` · Grep `glob`은 deny다. 서버가 허용한 읽기 명령은 이름이 서버 `COMMAND_FLAGS` 키이고, 원래 명령을 같은 단어 규칙으로 나눈 결과가 서버 `argv`와 같고, PATH에서 찾은 실행 파일의 realpath 이름이 명령 이름과 같을 때만 다시 만든다(`cat → rm` 링크 거절). 승인 카드 글은 줄바꿈 `⏎` · 탭 `⇥` · 제어 · 양방향 · 폭 없는 글자를 `\u{XXXX}`로 보인다(자르는 방식은 9장 11이 바꿨다). 중단 신호 · 자체 점검 실패 뒤의 훅은 모두 deny, 답 resume에서도 등급 도구 집합을 본다. `--resume`은 세션 폴더 상태가 묶은 id만, `claude`는 검사한 realpath로 띄운다(argv[0]은 후보 경로). 비밀 질문의 답 값은 메모리에만 두고 밖으로 나가는 메시지 · 질문 · 산출물 글, 승인 글에서 `[redacted]`로 바꾼다(범위 · 변형 · 서버 요청은 9장이 바꿨다). Stop은 등록부에 없으면 원장 정체로 끝까지 끝냈을 때만 "돌고 있지 않다"이고, 끝(자손 포함)은 자손이 모두 사라졌을 때만이다: 감독하던 자식이 끝나도 남은 자손을 SIGKILL로 끝낸 뒤에 `ended`, 고아 확인도 자손을 본다(자손을 찾는 방법은 9장 4). 같은 세션의 다음 writer(새 턴 · 답 · 닫기)는 앞 프로세스의 끝이 증명될 때만 띄우고, 아니면 `spawn_failed`(런타임은 `close_before` 실패면 턴을 띄우지 않는다). 답 resume의 새 프로세스 정체는 답 전달 전에 원장에 적는다. 열린 요청을 상태 파일에 적지 못하면 질문을 내지 않고 그 호출을 닫기 모드로 거절, `failed(agent_error)`다. 산출물 해시는 일반 파일 · 64MB 이하만, actor 밖에서.

- **재검토 2 반영(계약 10장):** 그룹은 부모가 살아 있고(`same`) 그룹 리더일 때만 믿는다: 부모가 없거나 pid가 재사용됐거나 확인할 수 없으면 혈통과 marker만 쓴다(앱이 멈춘 사이 같은 pid를 쓴 무관한 그룹을 죽이지 않는다). 후보의 소속(시작 시각 · 부모 · 그룹)과 unique id는 커널이 한 프로세스에서 함께 채운 한 세대로 읽고, 목록이 본 시작 시각과 다르면 버린다. 자손은 뿌리보다 뒤에 만들어진(unique id가 큰) 것만이다(벽시계를 보지 않는다). 다른 부팅에 적힌 혈통 파일이면 그 spawn은 이미 끝났다(훑지도 신호를 보내지도 않는다). `NOTE_FORK`가 몰려도 훑기 사이 30ms, 파일 전체 다시 쓰기는 0.5초씩 묶는다(새 id는 11장부터 바로 덧붙인다). 세션 · 원장 루트와 앱 Application Support 안의 Edit/Write는 deny(`app_data`)다. 결과를 돌려주기 직전(마지막 `await` 뒤)에 중단 · 자체 점검 실패를 다시 보고, 바뀌었으면 answers 없는 deny이고 답은 전달로 적지 않는다(`request_closed`). 비밀 질문의 항목 id(값이 아니라)를 상태 파일에 두고 런타임이 이 Mac에서 답한 값인지(`answered_locally`)를 adapter에 알려, 질문이 열린 채 앱이 다시 떠도 그 답 값을 가린다. 비밀값은 결정 입력과 사건 글을 디코드해서도 찾는다(퍼센트 두 방식 · `+`→빈칸 · JSON unescape · 셸 따옴표 풀기 `'"'"'` 포함 · NFC/NFD): 결정 입력에서 찾으면 로컬 카드(서버 0), 사건 글에서는 그 셸 단어를(못 집으면 글 전체를) 가린다. 승인 카드는 유니코드 스칼라로 세어 명령 300 스칼라 이하 + 사유 줄이고, 한 글자에 결합 표시가 2개를 넘으면 `\u{XXXX}×N`, 가운데를 숨기면 `…(+숨긴 수)…`다. **D4a 인계(보강):** 폴더 고르기는 홈 · `~/Library`뿐 아니라 앱 Application Support(`~/Library/Application Support/<번들 id>`) · 원장 · 세션 루트를 품거나 그 안에 있는 폴더를 작업 폴더로 받지 않는다.
- **재검토 3 반영(계약 11장):** 끝은 완전한 증거가 있을 때만이다 — 다른 부팅의 파일 · 끝 기록, 또는 연속 두 번의 완전한 빈 훑기. 있어야 할 혈통 파일이 없거나 읽지 못하면, 자손으로 본 세대를 다시 읽지 못했거나 살아 있는 프로세스의 세대를 읽지 못하면(불완전한 훑기) 끝을 증명하지 못해 `unknown`이고 세션은 잠긴 채다(풀기는 D4a). 뿌리는 뿌리 id로만 뺀다(그 pid를 다시 받은 자손을 빼지 않는다). 훅 응답은 정한 뒤 돌려주기 직전에 await 없이 한 번에 확정한다: 그때 Stop이 와 있으면 answers 없는 deny이고 답은 전달로 적지 않는다(`request_closed`). 비밀값 탐지는 디코드한 형태마다 정규화 전 글자 그대로를 먼저 보고, 셸 줄 이음(`\` + 줄바꿈)과 ANSI-C `$'…'`(`\xHH` · `\NNN` · `\u` · `\U` · 일반 이스케이프)도 푼다. 이 Claude 세션에 비밀값을 건넨 뒤 앱이 다시 떠 가리개가 비었으면 그 세션의 다음 턴 · 답 resume를 띄우지 않는다(`spawn_failed`, 로그 `claude_secret_context_lost`: 값은 디스크에 두지 않는다, 사용자는 새 세션으로). 격리 `cwd/`가 비어 있지 않으면 자체 점검 ①에서 띄우지 않는다.
- **재검토 4 반영(계약 12장, 사용자 결정 책임 프로세스):** `claude`를 `responsibility_spawnattrs_setdisclaim`(libquarantine, `dlsym`)으로 띄워 자기 책임 프로세스가 되게 하고, 구성원은 `responsibility_get_pid_responsible_for_pid(pid) == 뿌리 pid`(그 pid가 지금도 같은 unique id의 뿌리일 때) ∧ unique id > 뿌리 id다. 뿌리가 살아 있는 동안 본 구성원은 혈통(unique id · pid)에 적어 뿌리가 끝난 뒤에도 쓴다. 두 함수 중 하나라도 없거나 disclaim이 듣지 않으면 그 spawn은 구성원을 증명할 수 없다: 끝을 확정하지 않고(`unknown`, 세션 잠금) 자손에 신호를 보내지 않으며 로그 `claude_membership_unprovable {reason}`. 귀속되지 않은 살아 있는 후보가 뿌리 pid나 혈통에 적힌 pid의 그룹에 있으면 그 훑기는 불완전이다. 모든 프로세스 조회(세대 flavor 18 · `KERN_PROC_PID` · 책임 pid)는 있음 · 사라짐 · 실패 3상태이고 실패는 불완전으로만 이어진다. 뿌리 id를 못 읽으면 정체 commit · stdin 전에 SIGKILL · `spawn_failed`(`claude_lineage_unrecorded {reason: root_id}`). 지킴이의 첫 보고로 정체를 대조하기 전에 멈춘 시작은 `root_id`가 아니라 원인 코드를 reason으로 적는다. 보고를 받지 못했다: `report_timeout`(5초 안에 보고 없음) · `report_eof` · `report_read_error` · `report_too_long` · `report_malformed`. 보고는 받았으나 `started`가 아니다: `keeper_failed`(`failed`) · `unexpected_report`(`exited` · `ended`가 먼저 왔다). 둘 다 `claude_start_diagnostic {cause, ended, ended_report, forced_kill, exit_code, signal, wait, abort}`가 고정 코드와 숫자로만 남는다(종료 코드 · 신호가 없으면 -1이 아니라 `none`). - **재검토 7 반영(계약 16장, 재검토 6보다 이긴다):** 닫기 spawn(`close_before` · 비밀 답 소실 · 답 예외 뒤 · Cancel의 버린 요청 · 질문을 서버 모양에 담지 못한 닫기)은 시작부터 생존 판단에 든다(`hasLiveProcess`: 감독 중 · 닫기 중 · 원장 `alive`) — Quit이 확인 없이 바로 끝내지 않는다. Quit · 계정 삭제(`shutdown` · `interruptLiveTurns`)는 먼저 새 spawn을 막고(런타임: 새 실행을 낳는 명령을 lease하지 않고, 이미 lease한 message · 답은 띄우지 않고 `leased`로 둔다, 닫기도 띄우지 않는다. adapter `stopSpawning`: 턴 · 답 · 닫기 · 내부 닫기 모두, 로그 `claude_spawn_refused {reason: shutdown}` · `run_deferred_shutdown`), 감독 중인 실행에 중단 신호 → 감독 · 닫기가 끝나기를 3초 기다린 뒤 감독 중인 것을 끝내고, 이어서 감독 밖 실행도 세션마다 잠금의 지금 실행을 그 세션의 task(살아 있는 것, 없으면 마지막 것)로 끝내고 끝을 증명한다(`endSessionRuns`: 닫기 실패의 고아 · 내부 닫기 실패 뒤의 실행 · 도는 닫기). 다른 훅의 시간 초과는 그 요청을 시간 초과로 정하는 것과 미전달 답을 닫는 것을 답 슬롯 잠금 안에서 함께 한다(소켓은 등록의 `timeOut`으로 정한다, 잠금 순서 슬롯 → 요청): 그 뒤 답 훅의 allow는 닫힌 슬롯을 보고 answers 없는 deny를 받는다. 훅 기한은 시작부터 4초(`HookWire.budget`, Claude Code 훅 timeout 10초 안)이고 요청에 남은 밀리초(`remaining_ms`)를 싣는다. bridge는 연결부터 1.2초와 "읽은 때 + 남은 시간 − 0.3초" 중 이른 때까지만 응답을 확정한다: 그래서 `delivered`(답을 그 훅 응답으로 확정함)는 훅이 끊기 0.3초 전에 정해지고, 훅은 그 여유 안에 읽는다(그 0.3초를 넘게 멈추면 — 시스템 정지 등 — 훅이 끊고 deny할 수 있다: 남는 위험). 접수 전 실패는 `left`가 없어도 그 세션의 지금 실행이 끝을 증명하지 못했고 맡은 다른 살아 있는 task가 없으면 그 task가 맡는다(`alive=false`를 쓰지 않는다). 실행 기록이 있는 task id로 새 message가 왔는데 그 실행을 아직 맡고 있으면(살아 있음 · 감독 · 고아 · 잠금의 지금 실행이 끝을 증명 못 함) 띄우지 않고 거절한다(`task_reused`). 등록부에 남은 spawn이라도 끝을 증명했으면 `sessionRun`은 끝이다. tick · 깨어난 뒤의 확인은 감독 밖 고아도 그 세션의 지금 실행으로 다시 보고 끝을 증명했으면 끝 정산한다(로그 `orphan_ended`). 잠금 자리가 없는 세션 id(UUID 아님)에는 실행이 생길 수 없으므로 끝이다. **남는 위험 넓힘(코디네이터 수용):** 같은 uid의 위조는 앱이 떠 있어도 신뢰 경계 안이다 — `<spawn>.keeper` 기록뿐 아니라 `<spawn>.ended` 끝 기록 위조, 세션 잠금 삭제, 잠금 · 혈통 파일의 부팅 id를 다른 부팅으로 덮기(다른 부팅 = 끝)로 끝 증명을 속일 수 있다. 다른 앱의 실행기가 disclaim으로 띄우고 먼저 끝나 부모가 launchd(1)가 된 프로세스가 지킴이 뒤에 생겨 사는 동안에는 끝 증명이 늦어진다(거짓 끝은 아니다, 고치지 않음).
- **재검토 8 반영(계약 17장, 재검토 7과 다르면 이것이 이긴다):** **실행 등록부 하나** — adapter는 세션의 모든 spawn(턴 · 답 · 닫기 · 내부 닫기 · 지킴이 시작 보고를 기다리는 것)을 띄우기 의도부터 끝 증명까지 한 등록부에 두고, 그 동안 `sessionRun`은 살아 있음이다(위 "등록부에 남은 spawn이라도 끝을 증명했으면 끝"을 대신한다). 내부 닫기가 따라올지는 끝 증명 전에 정해져 등록부에 있고(`unexpectedDeferred`), 따라올 것이 없으면 끝을 증명한 뒤 세션 자리를 먼저 놓고 질문 · 글을 낸다(그 사건을 받은 쪽이 같은 세션에 닫기를 띄워도 자기를 기다리지 않는다). `terminateSessionRun`은 그 세션의 따라올 닫기를 취소하고, 시작 중인 spawn은 `stopped`로 표시해 정체를 받은 뒤 stdin 전에 멈추게 하며(입력 0 바이트 · SIGINT), 등록부에서 빠질 때까지(시간 제한, 시작 보고 5초 포함) 기다린다. 런타임 `hasLiveProcess`는 adapter 등록부(`hasRegisteredRuns`)도 보고, Quit 유예는 등록부가 비기를 기다린 뒤 세션마다 끝낸다. 닫기 실패는 그 세션 잠금 조회 · 고아 기록을 마친 뒤에 `closing`에서 빠지고, 서버 모양에 못 담은 질문의 닫기 실패도 그 실행을 고아로 둔다. 종료가 시작되면 `beginRun` 직전 · 그 뒤(마지막 await 뒤) 다시 보고, 먼저 적은 `start_intent`도 띄우기 전이면 `leased`로 되돌린다(`failed` 0). **기한 하나** — 훅은 요청에 `remaining_ms` 대신 절대 기한 `deadline_ns`(프로세스 사이에 같은 `CLOCK_MONOTONIC_RAW` 나노초)를 싣고, bridge는 같은 시계로 min(연결 + 1.2초, 훅 기한 − 0.3초)를 기한 하나로 쓴다: 보낸 뒤 읽기까지의 지연도 센다. 읽은 때 이미 지났으면 처리기를 띄우지 않고 그 자리에서 시간 초과로 정하고(답 닫기 포함), 처리기의 확정도 기한을 넘으면 받지 않는다(`HookCommit`). 연결마다 전용 스레드에서 처리한다(spawn의 막힘 읽기가 공유 GCD 풀을 채워도 늦지 않게). 그래서 `delivered`는 "훅이 끊기 0.3초 전까지 bridge가 그 훅 응답으로 답을 확정함"이고, 그 0.3초를 넘는 시스템 정지만 남는 위험이다.
- **지킴이 훑기(계약 18장 · 19장 · 19.1 · 20장 · 21장, 위 재검토 5의 "목록과 조회 사이에 사라진 프로세스" 규칙을 좁힌다):** 지킴이 뒤에 시작해 훑는 사이에 사라졌거나 조회 때 좀비인(19.1: 끝났는데 launchd가 아직 거두지 않았다 — 끝나기 전에 목록에 없는 자식을 남겼을 수 있으니 사라짐과 같다. 지킴이 앞에 시작한 좀비는 전처럼 건너뛴다) 프로세스는 같은 스냅숏의 부모가 그것이 구성원일 수 없음을 증명할 때만 불완전이 아니다: 그 자식의 목록 행이 추적 중이 아니고(`P_TRACED` 아님 · `p_oppid == 0` — 추적 중이면 지금 부모는 tracer다), 자식 세대를 읽었으면 그 조회 때도 추적 중이 아니며(`pbi_flags`의 `PROC_FLAG_TRACED`, 21장) 목록 부모 pid의 지금 프로세스가 그 세대의 부모 unique id이고(21장: 목록 뒤 attach → exec · detach 뒤 남은 부모 id를 거른다), 부모가 launchd(1) · 지킴이가 아니고, 지금 살아 있는 그 프로세스가 원래 부모일 수밖에 없으며(좀비 아님. 20장: 벽시계가 아니라 fork 때 전역 카운터로 매기는 단조 unique id 순서로 가른다 — 책임 조회에서 사라졌거나 좀비면(자식 세대를 읽음) 읽은 세대의 부모 unique id와 같고 그 id가 자식 id보다 작음, 세대 조회에서 사라졌으면(자식 세대를 못 읽음) 목록 부모 pid의 지금 프로세스가 지킴이보다 먼저 생김(id < 지킴이 id: 지킴이 전부터 살아 있으니 스냅숏 때도 그 pid의 주인이었다, 시작 시각은 보지 않는다)), 그 책임 프로세스를 읽었고 지킴이가 아니며(부모 세대를 책임 조회 앞뒤로 읽어 같은 unique id · 좀비 아님일 때만 — 그 사이 pid가 다시 쓰였으면 읽은 책임은 다른 프로세스의 것이다), 지킴이가 본 구성원 id가 아닐 때다. 스냅숏은 `KERN_PROC_UID` ∪ `KERN_PROC_RUID`이고, 두 목록이 같은 pid를 다른 부모 · 시작 시각 · 사용자로 말하면 그 훑기 전체가 불완전이다(합칠 때 버리지 않는다). 추적이 끝나면 커널은 원래 부모 pid의 지금 프로세스로 옮긴다(`PT_DETACH`의 `proc_find(p_oppid)`, 없으면 launchd): 그 pid가 다시 쓰였으면 무관한 새 프로세스 T에 붙고 추적 표시를 지우며, 그 뒤 exec이 부모 unique id를 T로 갱신한다(재검토 11). T는 원래 부모가 끝난 뒤 생겼으니 자식보다, 원래 부모가 구성원이었으면 지킴이보다 id가 크다 — 위 순서 조건이 그 경우를 거른다. 그 밖에 책임 프로세스는 부모에게서 물려받고(disclaim이면 자기 자신) 고아는 launchd로만 옮겨지므로, 그 자식은 살아 있었어도 지금 규칙이 구성원이 아니라고 보았을 것이다. 부모를 근거로 쓰는 모든 길 — 세대 조회에서 사라짐 · 좀비 · 책임 조회 중 사라짐 · 다시 disclaim한 자손(재검토 6) — 은 이 조건들을 한 확인(`excusedByParent`)으로 거친다(21장, 재검토 12: 다시 disclaim 길은 추적 표시를 보지 않아, 오래된 tracer가 attach한 뒤 exec한 자손을 구성원이 끝난 뒤 무관으로 보았다). 다시 disclaim한 자손은 지킴이 앞에 생긴 부모(launchd가 띄운 앱 · XPC 서비스 포함 — launchd는 세대를 못 읽어 unique id만 읽는다)면 추적 아님 · 목록 부모 = 세대 부모만으로 무시하고, 그 밖은 모든 조건을 증명해야 한다. 그래서 원래 부모가 끝나 launchd 아래로 간 다시 disclaim한 자손(세대의 부모 id ≠ launchd)은 사는 동안 끝 증명을 늦춘다(거짓 끝은 없다). 남는 위험: 지킴이 뒤 시작 여부는 목록 행에 unique id가 없어 지금도 달력 시각으로 가른다(13 · 14장) — 시계가 뒤로 간 동안 사라진 구성원은 지킴이 앞으로 보여 건너뛰어질 수 있다(20장, 고치지 않음). 조회 하나라도 실패 · 사라짐 · 불일치면 그대로 불완전이고, 조회 실패(`.failed`) · 실효 사용자 바뀜 · 다시 disclaim 규칙, 연속 두 번 완전 · 구성원 0이어야 끝, 증명 못 하면 `unknown`은 그대로다. 그래서 지킴이 전에 시작한 셸 · 편집기 · 상주 빌드 서비스 아래에서 짧은 프로세스가 끊이지 않고 생겼다 사라져도 지킴이가 끝을 증명한다(재검토 5 "남는 위험"의 짧은 수명 지연은 그 경우 없어졌다 — 그 지연은 실제로 세션 잠금과 Stop · Quit 대기를 빌드가 도는 내내 붙잡았다). **생존 쪽 결과(20장):** 지킴이 뒤에 시작한 무관한 부모(세션 중에 시작한 빌드)의 자식이 목록과 세대 조회 사이에 거둬지면 그 훑기는 불완전이라, 그 빌드가 도는 동안은 끝 증명이 늦어지고 빌드가 끝나면 증명된다(거짓 끝은 없다). 그런 빌드의 좀비 · 책임 조회 중 사라짐은 부모 id < 자식 id로 가르므로 막지 않는다. 구성원의 fork 사슬은 사라진 고리의 부모가 구성원 · launchd라 여전히 불완전이다. 파일에서 읽은 혈통(다시 뜬 앱 · 감독 밖 끝내기)은 지킴이가 사라진 뒤 지킴이 기록을 먼저 보고, 없으면 이 spawn 경로 · 이번 부팅 · 형식이 맞는 끝 기록(`<spawn>.ended`)을 본다(19.2): 끝 기록은 끝을 증명한 뒤에만 쓰이고(`forget` · 다른 부팅의 `purge`) 쓰는 쪽은 끝 기록을 먼저 쓰고 지킴이 기록을 지우므로, 그 사이 다른 adapter가 끝을 확정해도 끝을 놓치지 않는다.

- **끝 증명의 경계(계약 22장, 재검토 13):** 지킴이가 증명하는 것은 "책임 프로세스가 지킴이인 프로세스 0"과, 혈통을 아직 증명할 수 있는 다시 disclaim한 자손에 대한 15장 3의 최선 노력이다. 책임을 버리고 launchd 아래로 간 프로세스 — 직접 `open -a` · `launchctl` · XPC로 띄운 것, 부모가 끝난 뒤 launchd 아래에서 exec한 것(고아 뒤 exec) — 는 이 경계 밖이고 Stop · Done이 끝내지 않는다. 커널 조회값(부모 pid 1 · 부모 id = launchd · 스스로 책임)이 사용자가 세션 중에 연 일반 앱과 같아서, 막으면 그런 앱마다 닫힐 때까지 끝 증명이 막힌다. 그래서 21장의 "부모 pid ≠ 1"은 세대 조회에서 사라짐 · 좀비 · 책임 조회 중 사라짐 길에만 쓰고, 15장 3 스스로 책임 길의 launchd 부모는 이 경계에 따라 무시한다.

## 17. 외부 세션 목록 (OA 외부 세션 PR1) — 결정 기록과 위치

Taskforce 밖에서 시작한 Claude Code 세션을 이 Mac의 레일 "On this Mac"에 보이는 일. 계약 `handoffs/oa-external-sessions-contract.md` 16 · 17장(본문의 "서버에 0"을 16장이 뒤집었다). 이어받기(PR2)는 이 장에 없다.

### 17-1. 서버에 가는 것 · 가지 않는 것

- 가는 것: **제목**(사용자 글에 가깝다) · **상태**(6개 말) · **마지막 활동 시각** · **불투명 id**. 가지 않는 것: 대화 본문 · 경로 · 폴더 이름 · Claude 세션 id.
- 불투명 id = `hex(HMAC-SHA256(열쇠, "tf-external-session-v1\n" + 소문자 세션 UUID))`. 열쇠 32바이트는 이 Mac의 파티션 폴더(`external-sessions.key`, 0600)에만 있고, id ↔ UUID 대응은 이 Mac의 메모리에서만 만든다. 서버는 이 값에서 Claude 세션을 찾을 수 없고, 다른 Mac의 같은 세션을 이어 볼 수도 없다. 열쇠를 못 두면 목록을 내지 않는다.
- 상태 6개: `available · running_claude_app · running_terminal · running_elsewhere · unknown · unavailable`. 보이는 이유(폴더 거절 · 버전 · 워크트리 · 읽지 못함)는 서버에 `unavailable` 하나로 접힌다. 이미 이어받은 세션은 `agent_sessions`에 있어 보고하지 않는다.

### 17-2. 표 · 함수 (`20261203000000_external_sessions_list.sql`)

- `external_sessions`: `user_id` + `owner_all` RLS(앱은 읽기만, 쓰기 권한 없음) + `bridges`와 `(id, user_id)` 복합 외래키 + `unique (bridge_id, session_ref)`, `session_ref ~ '^[0-9a-f]{64}$'`, `title` null 또는 1–200자, `state` 6개.
- `report_external_sessions(p_user_id, p_bridge_id, p_sessions jsonb)`: service role 전용, `search_path=''`. **스냅샷 교체**: 이번 목록에 없는 그 Mac의 행을 지우고 나머지를 넣는다(최대 50, 중복 없음, 모양이 틀리면 예외 · 아무것도 쓰지 않음). bridge가 이 사용자 것이고 active가 아니면 `not_found`(route 404). 같은 bridge의 보고는 **소유 확인(`for share`) 뒤에** advisory lock으로 직렬화한다 — 없는 · 남의 · 해제된 bridge id로는 잠금을 잡지 못한다. 보고마다 **모든 행의 `reported_at`을 새로 한다**(내용이 같아도: 보관 14일의 기준이라 건너뛰면 살아 있는 행이 지워진다). "무변경 갱신을 건너뛴다"는 말은 틀렸다 — 부하는 앱이 줄인다(바뀐 목록만, 30초 간격, 6시간 keepalive).
- 보관: ① 스냅샷 교체(7일 창 밖으로 나간 세션 · 사라진 세션의 제목은 다음 보고에 지워진다) ② bridge `revoked`가 되면 트리거 `external_sessions_on_bridge_revoked`가 즉시 삭제, bridge · 계정 삭제는 cascade ③ 보고가 끊긴 지 **14일**이 지난 행은 `/api/cron/retention` → `purge_external_sessions(p_before, p_limit ≤ 5000)`. 함수가 아직 없으면(코드가 먼저 배포) cron은 `external_sessions_ready: false`로 200을 낸다. 제목은 로그 · 지표 · AI 호출 · 관리자 화면에 쓰지 않는다.

### 17-3. route · gate

- `PUT /api/v2/external-sessions`(`authenticateRequest`: Bearer · 쿠키, 쿠키 쓰기는 CSRF). 본문(`externalSessionReportRequestSchema`, strict): `{ bridge_id, sessions: [{ id, title | null, state, last_activity_at }] }`, 제목은 제어 · 서식 글자(방향 바꿈 포함) 없고 앞뒤 공백 없는 1–200자. **본문은 상한까지만 읽는다**: PUT 128 KiB · `shown` 1 KiB. `Content-Length`가 있고 넘으면 읽기 전에 400, 없거나 거짓이면 읽다가 넘는 순간 멈추고 400(끝없는 본문을 다 읽지 않는다). 응답 `{ kept, removed }`.
- gate: `CONVERSATIONS_V2_ENABLED` ∧ `AGENT_ADAPTER_CLAUDE_CODE_ENABLED`가 꺼져 있으면 인증 · DB 전에 404, 베타 명단(`agentBetaUserAllowed`) 밖도 404. 모르는 · 남의 · 해제된 bridge도 404(존재를 알리지 않는다). 새 rate limit 종류는 만들지 않았다(앱이 바뀐 것만, 30초 안에 다시 보내지 않고, 안 바뀌어도 6시간마다 한 번).
- **제목을 올리는 PUT만 전용 gate `EXTERNAL_SESSIONS_REPORT_ENABLED`(정확히 `"true"`, 기본 꺼짐, `src/lib/flags.ts`)가 더 켜져 있어야 한다.** 꺼져 있으면 인증 · DB 전에 404, 저장 0. **이 gate는 처리방침(#169)이 "제목을 서버에 보낸다"고 게시되기 전에는 켜지 않는다.** 구간 값만 받는 `POST …/shown` 지표는 이 gate를 보지 않는다. Mac 레일 목록은 서버 없이 이 Mac 안에서 만들어지므로 이 gate를 꺼도 목록은 그대로 보이고 올리기만 멈춘다.
- 로그는 이벤트 이름 · 오류 이름 · 코드만이다(제목 · id 없음).

### 17-4. 지표

- `external_sessions_shown`(`metric_events` 종류 검사는 `20261129000000`의 목록 + 이 type): 레일 목록이 행 1개 이상으로 보인 날 하루 한 번(UTC 날짜별 부분 unique 인덱스). 앱이 **`POST /api/v2/external-sessions/shown`**으로 `{ rows_bucket: 1 | 2-5 | 6-15 | 16+, held_bucket: 0 | 1-2 | 3+ }`(구간 값만, 글 · 수 0, strict)를 알리면 route가 서버 권한으로 남긴다 — 앱의 열 권한(`type` · `action_id`)과 insert 정책(`app_opened` · `assistant_opened`)은 그대로다. 같은 날 두 번째는 23505를 조용히 넘겨 204다. gate · 베타 명단은 13-3과 같다. **v1 `metric-events`는 동결이라 건드리지 않았다**(`contract-v1-freeze.test.ts`가 그 스키마 지문을 지킨다): 새 지표는 v2다.
- `session_attached` · `session_attach_refused`는 이어받기 PR의 몫이다(남기는 곳 없는 type을 지금 넣으면 등록부 시험이 깨진다).

### 17-4b. Mac이 올리는 방식 · 로그아웃 (Kit `ExternalSessionReporter` · `ExternalSessionSignOut`)

- 올리는 일은 목록과 따로다(실패해도 목록은 보인다). 바뀐 목록만, 30초 간격, 안 바뀌어도 6시간마다. **404(전용 gate 꺼짐 · 베타 밖)를 받으면 6시간 물러난다**(30초마다 두드리지 않는다). **400(`invalid_request`)이면 제목을 모두 null로 해서 한 번 더** 보내고, 그것도 거절하면(또는 보낼 제목이 없으면) 6시간 물러난다. 그 밖의 실패(네트워크 · 5xx · 429 · 인증)는 다음 호출에서 다시.
- 보고는 **훑을 때 잡은 계정(파티션) · bridge**로만 나간다. 보내기 직전의 지금 값과 다르면 버린다(다른 계정의 열쇠로 만든 id가 새 계정의 목록에 섞이는 것을 막는다). 훑을 때 bridge가 아직 없었으면 올리지 않는다.
- 읽은 결과가 "없음"(`~/.claude`가 없다)이어도 빈 목록을 올려 서버에 남은 옛 행을 지운다. 읽지 못한 때(`unreadable`)는 올리지 않는다(잠깐의 실패가 서버 목록을 비우지 않게).
- **Sign Out을 누르면 세션을 지우기 전에**(`SessionStore.onSigningOut`, 합쳐서 3초까지만 기다리고 오류는 삼킨다 — 로그아웃은 막히지 않는다) 이 Mac의 서버 목록을 빈 목록으로 교체하고 열쇠(`external-sessions.key`)를 지운다. 세션 만료 · 다른 기기에서 지운 계정은 누른 로그아웃이 아니라 토큰이 이미 없다: 계정 삭제는 cascade, 만료는 14일 보관 정리가 지운다.
- 로그(OSLog)는 구간 코드뿐이다: `external_sessions_scan_failed {cause}` · `external_sessions_report_failed {bucket: not_enabled|rejected|auth|rate_limited|server|network|other}` · `external_sessions_shown_failed`. 제목 · 경로 · id · 숫자 상태 없음.

### 17-5. Mac이 읽는 것 (Kit `Bridge/ExternalSessions/`)

- `~/.claude/projects/<디렉터리>/<소문자 UUID>.jsonl`: 이름 · 시각 · 크기 + 머리 64 KiB에서 `sessionId`가 파일 id와 같은 줄의 `cwd` · `entrypoint` · `version`, 꼬리 256 KiB에서 마지막 `custom-title` · `agent-name`의 제목. `user` · `assistant` · `last-prompt` 줄의 글은 어디에도 담지 않는다. `~/.claude/sessions/<pid>.json`(문서에 없는 내부 형식, 확인 필요 R4): 이름 `^[0-9]{1,10}\.json$`, 64 KiB, 못 읽으면 신호 1을 건너뛰되 다른 신호가 못 찾아도 `unknown`(막는다). 허용 목록 밖(`.credentials.json` · `~/.claude.json` · `sessions/*.key` · 데스크톱 앱 저장소)은 열지도 나열하지도 않는다.
- 범위: 최근 7일 + 지금 돌고 있는 것(날짜와 무관), 줄 50, 파일 500, 총 읽기 32 MiB, 나열 5만 항목(폴더를 끝까지 읽지 않고 상한에서 멈춘다 — `list`가 `limit`을 받는다). `sdk-*` 출처(`-p` · SDK)는 뺀다. Taskforce가 띄운 세션(세션 폴더 `state.json`의 Claude id, 앱 데이터 안 cwd)도 뺀다.
- cwd는 힌트일 뿐: 평범한 절대 경로(`..` · NUL · 개행 없음) + 프로젝트 디렉터리 이름(영숫자 아닌 UTF-16 단위를 `-`로, 200단위 넘으면 확인 불가)과 정확히 같아야 하고 폴더 규칙을 지나야 한다. 어긋나면 "Unreadable"이고 그 줄의 폴더는 어디에도 쓰지 않는다. 워크트리(`<저장소>/.claude/worktrees/<이름>`)는 저장소 밑 묶음에 "Can't resume here · Worktree". 저장소로 읽힌 곳이 홈이거나 `~/.claude` 안(`~/.claude/worktrees/<이름>`: 사용자가 모아 둔 자리)이면 홈 폴더 이름 밑으로 묶지 않고 일반 폴더 규칙의 결과를 쓴다.
- 실행 중 판정(5.4): 등록 파일(pid 살아 있음 · 같은 사용자 · 시작 시각 1초 안 — pid 재사용은 stale. `procStart`가 2015년 이전이거나 지금보다 하루 넘게 앞이면 단위를 잘못 읽은 값이라 믿지 않고(nil) 살아 있으면 쥔 것으로 본다. `lstart` 글(`Wed Oct 21 04:57:32 2026`)에는 시간대가 없다: 데스크톱 번들 `claude` 2.1.304는 **UTC**로 적는다(KST Mac의 `ps lstart`와 9시간 차이). 그래서 이 Mac의 시간대와 UTC 두 가지로 읽어 어느 쪽이든 1초 안이면 같은 프로세스로 본다 — 이 Mac의 시간대로만 읽으면 살아 있는 데스크톱 세션이 stale로 보여 "Running in Terminal"(argv의 `--resume=`)이나 비어 있음으로 잘못 나왔다) · argv(`--resume` · `-r` · `--session-id`) · 같은 폴더의 등록 안 된 `claude`(`PROC_PIDVNODEPATHINFO`) · 기록이 60초 안에 쓰임. 신호를 읽지 못하고 주인도 못 찾으면 `couldNotCheck`(fail-closed).
- 한계: 이어받기 전이라 두 writer 경합(TOCTOU)은 PR2의 몫이다. 데스크톱이 열린 세션마다 `claude`를 띄워 둔다는 관찰(OB-3)은 실측 전이다. `procStart` 형식(R4)은 데스크톱 쪽만 실측했다(UTC `lstart`, 위); 터미널 CLI 쪽은 실측 전이라 두 시간대로 읽는다.
