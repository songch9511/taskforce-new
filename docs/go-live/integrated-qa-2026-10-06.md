## 담당 판정의 경계

- 명시적으로 다른 사람이 할 새 Action은 기각한다. 화자가 사용자와 동명이인이어도 타인 담당 판정을 되살리지 않는다.
- 담당이 없는 회의 요약에 사용자 연결 근거도 없으면 기각한다. 사용자가 관련 인물로 명시된 담당 미정 항목은 `owner=unknown`인 Review까지 허용하며 자동 배정하지 않는다.
- 문서 생성자 정보는 개인 계획·체크리스트라는 본문 문맥과 함께 사용한다. 공동 회의 기록에는 작성자라는 이유만으로 적용하지 않는다. 문서 문맥은 앞부분과 인용 주변을 합쳐 최대 5,000자로 제한한다.
- 기존 작업의 변경·완료·취소는 새 commitment 차단과 분리한다. 기존 동명이인 담당 보호는 계속 유지한다.
- `pagePeople`에는 실제 참석자가 아닌 People 속성도 포함될 수 있다. 관련 인물이라는 정보만으로 실제 참석 사실을 단정하지 않는다.
- 기존 잘못 생성된 Action은 자동 삭제·재처리하지 않았다.

## 실패를 발견하고 수정한 항목

1. Notion 페이지 작성자·높은 추출 신뢰도만으로 무관한 회의 Action이 자동 반영되는 합성 경로를 재현했다.
2. 첫 수정은 `kind=meeting`만 보호했다. 일반 Markdown 회의록이 `doc`으로 들어오는 우회를 독립 리뷰에서 재현하여 문서 판정을 추가했다.
3. 실제 모델 평가에서 참석자로 명시된 사용자의 담당 미정 항목까지 기각했다. 기존 정답 라벨을 유지하고 Review/unknown 경로를 복구했다.
4. 참석자 보호가 기존 변경 신호에 새 모호성을 붙이거나, 담당 질문이 기존 모호한 `@recipient` 보호를 지우는 회귀를 각각 재현하고 commitment 경계로 제한했다.
5. 화자의 동명이인 여부가 명시적 다른 담당 판정을 덮는 예외를 수정했다.
6. 검색 결과의 Hand off 보조 행 아래에 같은 상세가 중복 렌더되는 문제, 실시간 삽입 후 선택 표시와 Confirm 대상이 달라지는 문제, 출처 아이콘 조회 오류를 숨기는 문제를 수정했다.
7. 새 질문에 대한 모의 응답 누락, Swift 테스트의 반환·동시성 오류, 이전 자동 닫기·기본 제한을 기대하던 테스트는 새 계약에 맞춰 보완했다. 기존 골든 정답 라벨은 변경하지 않았다.

첫 평가의 시퀀스 기한 오류 두 건은 수정 전 `fb1f5bf`의 동일 사례 재실행에서는 재현되지 않았다. 가정적 액션 오탐 한 건은 수정 전 코드에서도 재현됐다. 단일 재실행만으로 모델 변동과 변경 영향을 단정하지 않는다.

최종 코드의 전체 실제 모델 평가는 `npm run eval -- --llm-concurrency 2 --jev-concurrency 4`로 실행했다. 약 $0.142를 사용했고 `coffee-chat-mostly-tentative`, `seq-slack-gap-reply`, `seq-slack-heldout-cancel-hearsay` 호출 3건이 429로 실패하여 exit 1이었다. 완료된 시퀀스에서는 기대 Action 27/27이 일치하고 필드 오류는 없었지만 Review 오탐 2건이 남았다. Ask는 8/8 통과했다.

## 사용자 보고 원문 대조

사용자가 알려 준 세 Action 제목으로 Notion을 읽기 전용 검색하여 같은 회의록의 요약 체크리스트에 모두 있는 것을 확인했다. 세 항목에는 개인 담당자가 적혀 있지 않다. Notion 사용자 검색으로 확인한 Daniel 계정 ID는 원문의 참석자 3명 및 Owner 속성에 없었다. 이는 사용자의 불참·무언급 보고와 일치한다. 페이지 생성자는 fetch 결과에 없어 알 수 없으며 진단에서는 true/false 두 조건을 따로 확인한다. 운영 저장 Action의 source_id를 직접 조회하지 않았으므로 검색된 원문과 운영 레코드의 연결은 아직 별도 확인 대상이다.

회의록 전체 내용과 ID 및 전용 실행기는 저장소 밖의 private QA 폴더에 보관했다. 회귀 테스트에는 민감한 원문 대신 동일한 구조의 합성 사례를 사용한다.

현재 `pageToItem`으로 변환한 원문과 사용자가 보고한 세 항목의 정확한 인용을 개발용 Jev에 순차 입력했다. 세 후보를 모두 `owner=me`, confidence 0.99로 시작했지만 **3/3 `NOT_MY_ACTION` 기각**, 담당 의미는 모두 `unassigned`였다(`judge-v6-meeting`). 비용은 약 $0.00022다. fetch에 표시 이름 매핑이 없어 판정 입력의 참석자 정보와 생성자 정보는 unknown을 유지했다. 원문의 참석자 ID에서 사용자가 제외된 사실은 별도의 Notion 사용자 검색으로 확인했다.

이 진단은 실제 원문에 대한 판정 단계만 실행했다. 추출·embedding·DB 저장·앱 동기화는 호출하지 않았고 기존 프로필의 모든 별칭을 재현하지도 않았다. 따라서 production E2E 통과로 표현하지 않는다. 본문을 포함하지 않는 결과는 `artifacts/integrated-qa/notion-reported-source-probe.log`에 있다.

두 참석자 사례에서 eval이 `owner=me`로 보고한 오류는 실제 저장 오류가 아니었다. production은 `judge.ownerAmbiguous`를 `owner=unknown`으로 바꾼 뒤 병합하지만, 기존 단일 원문 eval은 판정 전 추출 후보의 owner를 그대로 채점했다. 기존 변환을 `withJudgeOwnership`으로 공유해 평가와 저장 경로가 같게 보완했다. 원래의 추출·판정 결과 및 오탐 집계는 보존한다.

## 증거와 남은 범위

로컬 로그는 작업 트리의 `artifacts/integrated-qa/`, 실제 모델 상세 결과는 `evals/results/`에 보관한다. 전체 eval에는 기존 골든셋과 합성 사례를 사용하며 사용자 보고 Notion 원문은 별도 로컬 진단으로 구분한다. 화면 렌더는 실제 SwiftUI 런처 뷰에 `SampleData`를 넣은 offscreen fixture이며 로그인된 설치 앱·실제 포커스 상실·Notion 동기화 E2E 증거가 아니다.

현재 Debug 앱 경로로 GUI 검증을 다시 시도했으나 Computer Use가 `timeoutReached (-10005)`를 반환하여 화면 상태를 읽지 못했다. 이 결과만으로 앱 정지라고 단정하지 않는다. Escape·외부 클릭·Command-Tab을 포함한 실제 설치 앱 검증은 남아 있다.

서명 설치본 업데이트, 기존 운영 Action 정리, main 병합·운영 배포는 이 기록의 로컬 검증과 별도다. DB migration은 변경하지 않았다.
