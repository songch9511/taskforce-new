# 베타 AI 비용 제어

기준: 2026-10-08 KST. 운영 반영은 아래 검증과 배포 기록으로 구분한다.

## 적용 정책

- 기존 `ai_spend_attempts` 원장과 사용자별 누적 $10 한도를 유지한다.
- `ai_budget_policy`의 기본값은 전체 $5/일, 사용자 $3/일, 전체 누적 $50이다. service role만 정책을 읽거나 조정할 수 있다.
- 일일 경계는 UTC 00:00(한국 시간 09:00)이다. 실제 비용이 확인되지 않은 예약액은 날짜가 지나도 모든 한도에 포함한다. 확정 비용은 호출을 예약한 날에 귀속한다.
- 호출 전 모델의 전체 context와 검증된 endpoint 요금으로 최대 원가를 예약한다. 기존 `max_price`, 알 수 없는 요금 차단, provider 초과 청구 시 동결을 유지한다. 예약액은 실제 청구액이 아니다.
- 사용자 삭제 시 원장의 사용자 연결은 제거하되 익명 비용·예약액은 남긴다. 삭제 중인 호출의 정산도 완료할 수 있다. 삭제 후에도 전체 한도를 되돌리지 않는다.

## 호출량과 재시도

- Gmail·Notion 첫 글 원문 수집은 기본 최근 3일이다. `INITIAL_SYNC_LOOKBACK_DAYS`로 1–30일을 지정할 수 있고 잘못된 값은 3일로 돌아간다. 기존 커서와 Gmail 최대 공백 복구는 유지한다. Notion에서 다시 공유된 DB는 기존 14일 복구 범위를 유지하며, 구조화된 할 일 DB의 backfill 범위도 유지한다.
- 후보 판정은 한 번에 최대 3개씩 실행한다. 실패해도 이미 시작한 호출의 종료를 기다리므로 재처리와 호출이 겹치지 않는다.
- 일일 한도에 걸린 원문·구조화된 할 일은 내용을 보관한 채 pending으로 미룬다. 일반 실패 횟수를 소모하지 않고 UTC 다음 날 이후 다시 시도한다. 기존 24시간 처리 만료 규칙으로 지우지 않는다.
- 예산으로 3회 중단됐거나 전체 누적 한도에 걸리면 자동 재시도를 멈춘다. 운영자가 원가·예약액을 확인한 뒤 대상 원문을 명시적으로 재시도해야 한다. 실제 정산 근거 없이 예약액을 0으로 바꾸지 않는다.
- Ask·handoff·누락 신고의 일일 차단은 HTTP 429와 `Retry-After`, 누적 한도는 HTTP 403이다. 새 Apple 소스는 각각의 안내를 구분한다. 이전 설치본에서도 서버 비용 제한은 적용되지만 새 오류 안내는 앱 업데이트가 필요하다.

## 운영 반영 순서

1. PR의 lint·typecheck·전체 테스트·실제 PostgreSQL 잠금 경합 테스트·eval·build를 확인한다.
2. 현재 운영에 `ai_spend_attempts`가 있고 `ai_budget_policy`가 없는지 확인한다. 공유 키 한도나 결제 설정은 바꾸지 않는다.
3. 검증한 `20261030000000_ai_beta_budget_limits.sql`과 `20261031000000_ai_budget_retry_candidates.sql` 두 파일을 순서대로 명시적 transaction으로 적용한다. `supabase db push`는 사용하지 않는다. 이전 로컬 작업의 `ai_spend_ledger` 마이그레이션은 이 배포 대상이 아니다.
4. 정책 값, RLS, 기존 예약·정산 RPC의 service-only 권한, 함수 정의와 보존된 원장 행 수를 다시 확인한다. 예산 정책은 DB에서 즉시 적용된다.
5. PR을 병합하고 해당 merge SHA의 Vercel Production 성공을 확인한다. 앱 안내를 배포할 때는 새 버전의 서명·공증 DMG를 사용한다.

되돌릴 때는 원장을 삭제하거나 기존 마이그레이션을 역실행하지 않는다. 애플리케이션은 이전 코드로 돌아갈 수 있으며 기존 RPC signature와 사용자별 누적 요약은 호환된다. 한도 조정은 명시적인 운영 결정으로만 한다.
